# V3.2-21｜单名学生线索关联人工核实、错误关联撤回及不可变证据链

**独立市场销售技术文档；基线为 Draft PR #24，禁止并入旧教培 CRM 直到全项目最终融合审查。** 仅虚构 PostgreSQL 16、严格员工真实数据库 LOGIN 和中文 Chromium 环境测试。不得合并、上线、读取真实姓名/证件/联系方式或接教务、财务、合同。

## 一、必须区分的三种“确认”

1. `ms.lead_student_association_requests.status='approved_pending'` 仅表示**待核实关联申请经过第一轮主管同意**。此时 `ms.lead_students.confirmation_state='pending_review'`，`confirmed_by=NULL`，不得视为已核实。
2. V3.2-21 `verify` 允许申请人为**既有的一名指定学生**提供新的咨询材料或独立确认凭据，由**非申请人的有效本机构主管**在另一事务复核。批准后状态为 `verified`，只代表该**销售线索与这名学生的业务关联已被人工复核**。不证明该联系人是家长、监护人，不证明同姓学生是兄弟姐妹，也不改变学生法定身份或家庭关系。
3. `student_contacts.verification_state`、`family_memberships`、`crm_identity_links` 与正式销售线索核实**彼此独立**。本版不写这些表，也不创建 `contact_event_students`、商机、学生负责人、合同、课时或资金记录。

## 二、核实与撤回流程

- **提交核实**：仅原 V3.2-20 待核实关联申请人、仍实际负责该学生与正式线索者可提出。必须同时声明该关联对应的原申请 ID、人工核实依据类型（`student_consultation` 或 `independent_student_confirmation`）、虚构核对材料引用、原始证据引用、理由和防重编号。数据库锁定指定线索、学生和关联记录；原转换来源必须存在且线索不得作废、关闭或转化。对于错误关联或权限已变动，拒绝以缓存状态直接核实。
- **独立复核**：只有与申请人不同的有效本机构主管，重新核对身份、学生当前负责人、线索来源、原 V3.2-20 独立批准和原始状态仍为 `pending_review`，才可批准 `verify`。同一学生关联最多一次已成功核实。
- **申请撤回**：原单名学生—线索关联申请人、且仍实际负责线索者可对 `pending_review` 或 `verified` 提出错误关联撤回。即使指定学生的负责人已变化，也允许原线索负责人申请纠错，但不得阅读该学生新负责人的其他档案。不能直接按家庭或联系人推断需要撤回哪些其他孩子。
- **撤回批准**：独立主管仍需检查线索属于当前本机构、申请人仍有线索权限，且**该线索与这一名学生不存在任何下游商机**。已有下游业务时拒绝直接撤回，必须未来跨模块纠错审批。批准后仅把该 `lead_students` 行标记为 `withdrawn`，行仍存在，原先的 `verified` 决定及复核人不可擦除。原始咨询来源、原线索执行记录、其他学生关联完全不变。
- **驳回**：不改变原关联状态，也不写复核效果，但追加不可变决定与中文审计。被驳回后可用新的证据重新发起一次新申请；不允许覆盖原决定。
- **防重复与并发**：同一原关联同一时刻只能有一项待审（核实或撤回）；同一种操作最多一次已批准。相同申请人、相同防重编号和相同业务内容重放返回旧结果；不同内容复用编号拒绝。批准、状态变化、不可变效果、主管决定与审计都在同一 PostgreSQL 事务，任何失败整体回滚。

注意：数据库可以强制记录证据引用与主管独立签字，但**无法自动证明附件真实性**；真正的材料审阅是测试环境模拟的人工责任，不能当作生产级身份认证。本期不存真实儿童身份证件或直接连接第三方身份认证。

## 三、最小数据库权限与接口

新增 SQL `db/migrations/025_independent_student_link_verification_withdrawal.sql`：

- `ms.lead_student_link_review_requests`，`ms.lead_student_link_review_decisions`，`ms.lead_student_link_review_effects` 三表；后两表有不可变更新/删除触发器，新表均启用 RLS 且不给员工 SQL 原表访问权。
- `ms.scoped_lead_student_link_current`：仅线索原负责人可以查看**已明确关联**的指定学生当前最小状态。
- `ms.scoped_lead_student_link_review_requests`：申请人、已审核主管或有有效权限的主管待审请求，**不包含证据原文或学生敏感字段**。
- 仅给员工低权限写入角色赋予 `SECURITY DEFINER` `ms.request_lead_student_link_review` 与 `ms.decide_lead_student_link_review` 的 EXECUTE；真实执行人由受保护 `SESSION_USER` 查出，不相信 HTTP 的员工、机构、权限声明。不给直接 `UPDATE ms.lead_students`、`INSERT ms.family_memberships`、正式合同或财务权限。

HTTP 的严格员工模式接口：
- `GET /api/v1/lead-student-links/current` — 本人指定学生当前关联状态。
- `GET /api/v1/lead-student-link-reviews` — 本人或独立主管最小审批列表。
- `POST /api/v1/lead-student-link-reviews` — 提交 `verify` 或 `withdraw`，服务端严格字段白名单与幂等编号。
- `POST /api/v1/lead-student-link-reviews/:id/decision` — 独立主管批准或驳回。

中文工作台清楚区分“待核实、人工核实、错误关联已撤回”，不在审批表单露出数据库代码。证据只存虚构文字引用，不自动将其他孩子绑定或创建家庭。

- PostgreSQL **001—025** 成功迁移、双机构与真实非所有者 DB LOGIN 隔离、禁止原表 SELECT/UPDATE/DELETE、旧接口不回退。

- Chromium 中文界面：V3.2-20 单学生 `pending_review` → V3.2-21 人工核实 `verified` → 错误撤回 `withdrawn`；数据库始终保留该学生关联行和两个历史效果；另一名学生仍不在这条线索关联中。

## 五、继续保持边界

项目仍以**学生作为主要管理单位，家庭按需关联**。本阶段确认的是指定学生的**销售业务关联**，不是监护身份，也不给学生提供额外教务访问权限。若需要真正的监护人或家庭身份核实、跨员工学生更正/转交、已有商机后的业务撤回，应另立独立模型与跨模块验收；绝不通过删除原始咨询、改写审计或跨系统财务回滚来达成。
