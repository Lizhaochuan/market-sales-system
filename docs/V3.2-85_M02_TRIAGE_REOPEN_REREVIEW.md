# V3.2-85｜M02 关闭异常重新打开、证据更新和再次复核

## 已核实基线
V3.2-84 Draft PR #91 HEAD `d6c787049db66bf587ad4b2d4f61aae38e552275`，隔离 Node CI #43628929505 completed/success。上述结论不代表 PostgreSQL、Chromium 和合同全量验收。

## 范围
新增 `src/cross-module-triage-reopen.mjs` 的 CI-only 内存工单跟进模型。源数据分别来自 V3.2-83 的只读审计链和 V3.2-84 的只读异常报告；只有通过独立源版本、角色和审计校验，才能形成虚构跟进事件。

1. 原审计序号、摘要和新审计序号、摘要都必须在同一机构、同一异常的已核验审计链中存在。新审计必须晚于原记录，且来源修订增大、证据快照摘要变化或撤销摘要变化至少满足其一。不能仅凭新建工单来伪装证据变更。
2. 原工单必须处于 `closed_administratively` 或 `stale_source_reopen_required`。新版来源修订必须与测试框架独立获取的当前版本一致，旧版本、跨机构或没有证据更新的申请一律拒绝。
3. 测试中按 `reopen → rereview → close_administratively` 顺序只追加新事件，核对负责人（财务、教务或销售）、机构与仍有效的角色；最后关闭者须独立于前一步复核人。
4. 事件链包含新旧审计引用、来源修订、状态、责任部门、上一事件摘要及当前 SHA-256；历史重放不会重新流转，幂等键换内容直接拒绝。原 V3.2-84 审核事件保持原样，只记录新的处理历史。
5. 工单状态变化只代表内部模拟追踪，不得自动认可原订单资金归属、课时履约、财务/教务签名、三方联合验收或解除隔离。即使内部工单重新关闭，始终 `hold_active=true`、`handoff_allowed=false`、`compensation_write_allowed=false`、`release_eligible=false`。
