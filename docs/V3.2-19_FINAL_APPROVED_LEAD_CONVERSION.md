# V3.2-19｜最终授权后的正式销售线索创建（仅隔离虚构数据）

**文档类型：独立市场销售技术说明，不并入现有教培 CRM。**

上游：未合并的 Draft PR #22（V3.2-18）。本版仅在 `MS_STAGE=isolated-test` + PostgreSQL 16 虚构隔离数据内演练。必须保持 Draft，不合并 main，不开外网，不对接正式 CRM、合同、教务、收款或真实客户。

## 一、实际业务流程：三阶段，最后一步才有正式线索

1. **候选真实咨询核查**（V3.2-17）：只允许本人历史咨询登记，独立主管审核，不生成正式线索。
2. **转换预审**（V3.2-18）：本人当前管理权、客户拒联、同联系人现有线索、跨员工归因争议必须全部核查。独立主管批准后只表示“条件暂时通过”。
3. **最终转换申请**（V3.2-19）：原员工为自己仍有效的预审提交申请；数据库确认没有被撤销、没变更、没有已存在的正式线索。与原申请人不同的本机构有效主管可批准或拒绝。**批准本身仍没有线索 INSERT。**
4. **员工最后确认**：必须由原申请人以经审批的外部 RSA 签名身份、专属数据库低权限账号发起。数据库在同一事务中重新检查原候选及咨询、预审、最终主管资格、当前联系人管理权、拒绝联系、已有正式线索、未结或成立的跨员工争议，并锁定最终申请、预审和联系人。通过后只创建**一条** `ms.leads`（状态 `unidentified`，来源为原咨询，当前操作负责人为原申请人），追加唯一执行台账和中文审计并提交事务。
5. 本版本不把“线索负责人”自动当成销售业绩归因，不创建 `lead_students`、学生档案、家庭组、销售商机、合同、账单、资金、课时，也不改变原始咨询 `recorded_by`。

同一联系人可涉及多位学生，但线索只来自一次独立实际咨询；**不按家庭人数重复生成线索**。学生仍是核心管理单位，家庭关系仍需逐个核实。

## 二、数据库原子性与防越权

- `023_final_authorized_scoped_lead_conversion.sql` 定义最终申请、不可改写审批决定、不可改写执行台账；员工数据库账号不能 SELECT 原始表或直接 INSERT/UPDATE `ms.leads`。
- 新增唯一约束：同一预审只允许一个最终申请；一次最终申请只执行一次；执行台账在本机构同联系人、同咨询均唯一。老版演示写入逻辑仍为原合同回归保留；**新严格员工模式不提供旧 `POST /api/v1/leads` 的权限回退**。
- 仅通过函数 `ms.request_final_lead_conversion`、`ms.decide_final_lead_conversion`、`ms.execute_final_lead_conversion` 访问。员工身份和组织来自 `SESSION_USER` 的受保护数据库映射；HTTP 提交的组织、人员或角色字段一律不接受。申请人不能自批，主管不能代原员工执行。
- 函数内先锁最终申请，再锁预审和联系人，同一联系人并发执行会串行化，失败的一次只能得到业务冲突。执行的 `INSERT leads`、执行台账、申请状态更新、追加审计是同一 PostgreSQL 事务，任一步失败整笔撤销。
- 一样的幂等操作编号 + 一样的最终申请重放返回同一个 `lead_id`；不同编号再次执行拒绝。审批决定本身不可 UPDATE/DELETE；最终执行台账不可 UPDATE/DELETE。
- 预审许可在创建正式线索**之前**可以由有效主管撤销。若线索已创建，数据库禁止把“撤销预审”伪装成线索回滚：需要未来独立的线索作废/更正审批，不得删掉已发生的业务。
- 审核与最后执行均重新检查用户已拒联、现管理人是否变动、是否已有正式线索、原始事件记录人是否一致以及全部跨员工咨询是否已有独立驳回争议。任何新异议、待审异议、成立异议均停止执行。
- 本版采用单名独立主管作最终审批，与申请人必须不同。**不要求其与先前预审主管也是不同个人**；若要两名不同主管共同签字，需要另列需求与专用数据库测试账号，不能假称此版已满足双主管最终签字。

## 三、接口（均为严格员工隔离模式）

| 操作 | 受限接口 | 身份 |
|---|---|---|
| 最小记录列表 | `GET /api/v1/lead-conversions` | 本人申请、自己已审核的记录，或有效主管待审批 |
| 提交最终申请 | `POST /api/v1/lead-conversions` | 原候选和预审申请人 |
| 最终独立审批 | `POST /api/v1/lead-conversions/:id/decision` | 本机构有效主管，不能是申请人 |
| 最后确认实际创建 | `POST /api/v1/lead-conversions/:id/execute` | 原申请人，只收空对象和幂等键 |

三个 POST 都要求 16—128 字符合法幂等编号，外部 HTTP 只走专属员工数据库 `SECURITY DEFINER` 函数，并与之前的严格身份一致性校验同事务运行。不接受任意 `organization_id`、`student_ids`、`owner_user_id`、`lead_state`、`amount` 或原始 SQL 字段。

## 四、测试合同与不可触碰范围

- PostgreSQL **001—023** 迁移和真实员工数据库 LOGIN 测试，跨机构、越权 SELECT/INSERT、缺少审批、本人自批、经理代执行全部拒绝。
- 一次申请/同键重放、最终批准/同键重放、执行/同键重放以及不同键并发竞争，保证正式线索唯一。
- 外层事务回滚后，线索、执行台账和审计不可残留；批准仍可另行正常执行。
- 执行前预审撤销、拒联、既有线索、管理权变更和新跨员工咨询均阻止新线索。执行后预审撤销不能伪装为历史线索删除。
- Chromium 中文三阶段真实操作，确认审批前正式线索为零、批准不插入、申请人确认后仅一条；原合同 V3.1 完整回归仍须成功。
- 任何失败不得宣称通过，Draft 保持未合并。旧 CRM 所有文档与生产数据完全不动。
