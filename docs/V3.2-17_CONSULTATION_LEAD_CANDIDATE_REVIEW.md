# V3.2-17｜实际咨询转销售线索候选与独立复核

**性质：独立仓库隔离测试技术文档。** 依赖 Draft PR #20，本分支不得合并 main 或生产上线；旧 CRM 不变。

## 一、真正的业务边界

本人记录一次实际咨询后，可基于该咨询提交一次“销售线索候选申请”。**候选不等于正式销售线索。** 独立主管核查通过只表示“候选核查通过”，不会调用旧 `createLead`、创建 `ms.leads`、更改归因、关联学生、开商机、签合同、收款或进入教务。正式转换及业务效果留给未来另行审批与联合验收。

申请人必须同时满足：本机构有效数据库专属员工身份、咨询由本人真实登记、咨询关联的联系人由自己当前管理、未标记拒绝主动联系、该联系人和咨询均不存在正式销售线索、同咨询没有既存候选。提交后不改变原咨询记录人，不能按联系人关联的孩子数量重复提交。

## 二、申请—审核—防重复

* 提交时使用 `ms.request_consultation_lead_candidate(event, evidence, reason, idempotency_key)`。有效同键同内容重复调用返回原候选，异内容或同事件二次申请拒绝。
* 审核只允许本机构当前有效的 `sales_manager` 或 `super_admin`；审核人不得等于申请人。审核重新查验原事件、组织、当前联系人管理权、营销拒绝状态和已有正式线索；如情况发生变化，禁止“候选核查通过”。
* 审核可“候选条件核查通过但不生成正式线索”或“驳回候选”。决策记录追加且禁止 UPDATE/DELETE，中文审计只记录业务状态、不暴露核验材料。
* 已驳回同咨询不允许反复申请，以免规避独立审核；如需纠错，未来应另有正式复核流程。
* 数据库 `SESSION_USER` 固定映射员工、机构，所有写操作仅有 SECURITY DEFINER 函数 EXECUTE，员工无正式线索、候选原表、审计或财务表的直接写权限。
* 查看候选限于本人申请及有效主管的**待审候选**；普通员工仅看本人咨询。列表不含敏感联系方式、学生、家庭、销售金额、证据原文。

## 三、技术交付

- `db/migrations/021_consultation_lead_candidate_review.sql`：申请与不可变决定表；数据库受限只读投影；提交、审核函数与审计。
- `src/scoped-legacy-read-adapter.mjs` / `src/scoped-legacy-write-adapter.mjs`：仅信任员工受限 DB 登录，关闭任何旧宽权限回退。
- `src/app.mjs`：`GET /api/v1/lead-candidates/consultations`、`GET /api/v1/lead-candidates`、`POST /api/v1/lead-candidates`、`POST /api/v1/lead-candidates/:id/decision`。
- `web/index.html` / `web/app.js`：独立中文候选提交、主管审核、当前状态查看。界面明确“未生成正式线索”。
- `tests/security/lead-candidate-review.test.mjs`：真实员工 LOGIN 拒绝原始表、越权、本人自批、幂等、拒绝营销、重复咨询、交接后旧归因、零正式线索断言。
- `tests/browser/contact-custody.spec.mjs`：真实 Chromium 提交候选与主管核查，不生成正式线索。
