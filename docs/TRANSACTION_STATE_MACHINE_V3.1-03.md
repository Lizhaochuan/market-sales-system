## 0. 核心结论

**订单、权威收款事实、订单付款分配、首次成交、退款调整、销售业绩、CRM 课程权益是七种独立业务事实。** 它们相互关联，却不允许简单修改一个“已付款”字段就自动替代所有事实。

- **学生是成交主体：**每个订单默认只有一名学生，兄弟姐妹可分别有订单和销售负责人。
- **真实付款是外部财务事实：**一笔家长付款可能分给多个订单；只有财务权威证明已到账且分配用途被授权确认，才算该订单有效付款。
- **成交判定：**有效订单 + 经核实的订单净已付款达到应付金额 + 无待核实的关键异常，首次生成唯一 SaleEvent；部分付款、待分配、截图或业务人员手动选择状态均不是成交。
- **退款不删除首次成交：**原成交额及发生时间保留，退款及差错单独追加；报表展示原始成交和净调整额，不重复成交。
- **CRM 发放课时与销售成交是两条状态线：**销售系统不直接写 CRM 课时包；仅 CRM 的权威结果可以确定权益已创建。未付清先开课仍属 BP-01，不允许 AI 擅自放行。

## 1. 权威来源和数据流

| 业务对象 | 权威所属系统 | 本系统允许做什么 | 禁止什么 |
|---|---|---|---|
| 学生、联系人、可选家庭 | 新市场销售系统 | 维护销售侧关系与 CRM 学号映射 | 同电话自动合并学生或推断家庭 |
| 商机、报价、单学生订单 | 新市场销售系统 | 生成可追溯金额、版本、负责人快照 | 随意覆盖已批准报价/已确认订单 |
| 实际到账、撤销、退款 | **待确认财务权威** | 接收和核实经过认证的事实投影 | 销售自行声明到账 |
| 收款到订单的用途分配 | 新系统保存分配；审批权按 BP-02 | 在授权审批后计算每订单有效净收款 | 未授权平均分账、重复分配 |
| 首次成交事件 | 新系统受控交易服务 | 只在成交条件满足时写一次 | 界面直接“改为已成交” |
| 销售业绩分配 | 新系统受控业绩服务 | 快照、审批版本、退款后调整 | 因多名销售而加倍机构成交额 |
| 正式学生、排课、课时包 | CRM | 请求权益、查询实际结果、核对 | 直接写 CRM 本地数据库或未经核实当作成功 |

推荐数据流（逻辑顺序，不表示跨系统原子事务）：

    课程报价 -> 学生订单确认 -> 财务实际收款证据
                                   -> 经批准的订单分配
                                   -> 订单净收款核算
                                   -> 首次成交 SaleEvent
                                   -> CRM 权益交接申请（按政策）
                                   -> CRM 实际权益回执 / 待核实对账
    退款/撤销 ---------------------> 订单净额变化、业绩调整和权益复核

## 2. 严格区分的状态

### 2.1 订单生命周期（order_state）

| 当前 | 允许进入 | 必须有的条件 |
|---|---|---|
| draft（草稿） | submitted、cancelled | 课程及金额合法；提交需核对报价版本 |
| submitted（已提交） | accepted、cancelled | 授权审核、最终金额锁定；取消必须检查已收款 |
| accepted（已接受） | closed；特殊取消需专门业务流程 | 通常不可直接删除、重置金额；若已付款使用退款/冲正流程 |
| cancelled（已取消） | 无直接恢复 | 保留历史；新业务重新创建新订单 |
| closed（已关闭） | 无直接恢复 | 权益、财务纠纷均按独立业务调整管理 |

**注意**：accepted 不等于 fully_paid，更不等于已发课时。取消有收款的订单，不应直接关闭并遗留家长退款义务；应要求退款或财务处理计划及复核。

### 2.2 实际收款投影（verification_state）

| 当前 | 事件 | 下一状态 | 影响 |
|---|---|---|---|
| unverified | 权威来源确认到账 | confirmed | 仅表示原始收款属实；不表示分给哪个订单 |
| unverified | 来源拒绝/撤销 | revoked | 不可用于成交 |
| confirmed | 权威来源标记争议 | disputed | 相关订单进入待核实；禁止依靠有争议金额创建新的首次成交 |
| disputed | 来源重新证实仍有效 | confirmed | 按来源版本及证据重新核算；不能重复登记 |
| confirmed / disputed | 来源确认撤销/拒付 | revoked | 使相关分配失去有效付款资格，触发复核和更正 |
| revoked | 相同来源再次确认 | **待人工处理** | 不直接复活；必须验证外部权威更正事件与版本 |

同一外部交易以（authority_system、external_tenant、external_payment_id）唯一识别；不是以手机号、学生姓名或收款截图识别。晚到旧版本不得覆盖已确认撤销或更新后的状态。

### 2.3 订单付款分配（allocation_state）

| 当前 | 事件 | 下一状态 | 原则 |
|---|---|---|---|
| proposed（待核实） | 有授权分配依据且收款已 confirmed | confirmed | 审核原始付款用途，校验金额守恒、学生订单归属 |
| proposed | 撤回/拒绝 | reversed | 不参与已付金额汇总 |
| confirmed | 确认分错订单或业务冲正 | reversed + 新补偿记录 | 不覆盖历史理由；必须通过受控事务、保存原关系 |
| reversed | 任何再次确认 | 禁止 | 新业务使用新记录和新幂等键，引用原撤销依据 |

收款 confirmed 并不意味着付款分配自动 confirmed。一个联系人为两个孩子付款，仅代表一笔收款事实；不得根据同一个家长电话自动把分配复制两份。

### 2.4 每订单付款展示状态（payment_state，派生值）

| 条件 | 展示 |
|---|---|
| 所有可用付款均为零、无重要异常 | unpaid（未付款） |
| 有效净收款大于零且小于应付金额、无重要异常 | partially_paid（部分付款） |
| 有效净收款达到应付金额、无重要异常 | fully_paid（已付清） |
| 关联关键收款有争议、未确认冲正或无法验证的分配 | disputed（待核实争议） |
| 成交后发生退款、撤销或重大财务差错 | adjusted（发生财务调整，展示实际净额及备注） |

**实现规则：payment_state 只能由核算命令/投影更新，不是 UI 任意可写字段。** 已成交后的 adjusted 是业务提示，不代表原成交被删掉；当前净付款和原始成交需要分别展示。若应付金额为零或负数，禁止通过“零额自动全付”产生普通成交；免费课程另行审批政策。

### 2.5 首次成交状态（SaleEvent）

| 逻辑状态 | 触发 | 后续动作 |
|---|---|---|
| not_recognized | 初始；付款条件未满足 | 可继续跟进，但商机不可因手工改阶段计入正式成交 |
| recognized | 已接受订单，财务权威核实，订单有效净收款足额，且无阻断 | **一订单最多一条首次成交事件**；保存金额、负责人、渠道、时间和财务依据快照 |
| adjusted_after_sale | 成交后发生已确认退款、撤销/拒付或需更正事项 | 保留原 SaleEvent；追加财务与业绩调整；实际教学权益另行复核 |

原 SaleEvent 的 recognized_amount_cents 保留原始合法订单金额；退款净额通过单独的已核实调整记录统计。此前退款导致以后重新付清，也**不能产生第二条首次成交事件**。

**成交时间口径待最终确认**：建议同时保存财务权威业务时间、权威确认时间及系统记账时间。是否允许把迟到对账按历史日期计入业绩期，需要业务/财务批准，不由工程自行回填；原 SaleEvent 实际写入时间必须可审计。

### 2.6 退款、拒付与账务更正

| 场景 | 处理 |
|---|---|
| 收到未经核实退款消息 | 记录为 unverified，不改变已确认金额，也不删除成交 |
| 权威确认部分退款 | 退款投影 confirmed，分配到具体学生订单及必要课程明细；更新有效净额与退款业绩调整 |
| 权威确认全额退款 | 原 SaleEvent 保留；净成交额按确定的退款口径调整，可为零 |
| 同一退款事件重复送达 | 用外部退款唯一编号去重；不再冲减第二次 |
| 收款撤销/拒付（chargeback） | 按权威事实追溯涉及订单，禁止继续以该款项确认新成交；已成交的追加差错调整 |
| 同一原付款同时出现退款和撤销描述 | **防双重冲减**：必须识别同一财务经济事件、来源版本、关联凭证；不明进入人工复核 |

**退款如何影响老师已上课程、已消课课时、销售提成，仍是机构规则和现有 CRM 领域规则问题**。系统不得自动在 CRM 中撤销已完成的课程或删除课时流水。

### 2.7 CRM 课程权益交接（fulfillment_state）

| 当前 | 允许迁移 | 证据 |
|---|---|---|
| not_requested | pending | 达到已批准权益开通策略且首次建立唯一订单明细请求 |
| pending | completed、unknown、manual_review | CRM 真实回执；超时为 unknown |
| unknown | completed、manual_review，或以原键继续核实 | CRM 请求状态查询/已存在课时包核查 |
| manual_review | completed 或经授权决定下一步 | 人工查明 CRM 是否真实发课 |
| completed | **不得回到 not_requested** | 如发生退款，另发独立受控权益调整/冻结请求，不重复创建 |
| cancelled | 不自动重建 | 仅未实际交接或受控取消的请求适用，不能隐瞒已经发出的课时 |

状态 completed 必须保存 CRM 正式 package_id、学生 ID 和依据。网络超时、500、响应格式异常属于“结果未知”，不能简单认为失败后换 Idempotency-Key 重试。

## 3. 业务事务及不变量（需要真正代码实现）

### TX-I01：有效收款分配总金额不超原收款

按一笔实际权威确认收款单独锁定并重新核算：

    可分配收款 = 经确认且未被撤销/明确冲减的原始可用金额
    累计分配 = 此收款当前有效的 confirmed 分配总额
    必须满足：0 <= 累计分配 <= 可分配收款

如金额已被分配，在错误更正前不得再分配同一部分。未分配余额属于待处理款，**不是任何学生的成交款**。

### TX-I02：每订单有效净收款

    订单有效已分配 = 该订单确认分配且关联来源仍有效的收款之和
    订单已确认退款/拒付调整 = 有权威凭证且归属本订单的有效扣减之和
    订单有效净收款 = 订单有效已分配 - 已确认退款/拒付调整

任何来源异常都应进入 disputed/manual_review；上述金额仅是计算口径示意，实际实现应有明确唯一的“原付款—退款—拒付”关联，避免一笔经济事件扣两次。

订单结清条件必须同一事务再次核实订单金额版本、付款/退款来源和分配事实。对部分付款、未分配金额、未验证退款均不得提前标为“全额有效付款”。

### TX-I03：订单与报价金额一致

- sales_order.amount_due_cents 必须等于已确认、同一学生、同一商机的订单明细 line_total_cents 合计。
- 订单确认时校验报价版本、CRM 课程价格来源版本与机构授权优惠，禁止销售在客户端直接改应收总额。
- 已形成财务分配后，普通金额变更需创建受控调整，保留原订单及核算依据；不能直接覆盖旧订单价格。
- 兄弟姐妹优惠 BP-04 未明确到各学生和课程明细时，不允许确认正式订单金额。

### TX-I04：正式成交唯一且由服务器生成

同一数据库事务必须：
1. 锁定目标订单及用于结清的有效收款和退款事实（按统一排序防死锁）。
2. 验证订单 accepted、应付大于零、净付款足额、来源均已确认、无阻断争议。
3. 校验不存在该订单原始 SaleEvent；已有的则返回原成交，不创建新的。
4. 写入唯一 SaleEvent（数据库以 order_id UNIQUE 兜底），冻结当时商机负责人、首次来源和本次活动归因快照。
5. 写入审计和事务 outbox，提交后触发报表、CRM 交接任务（但要遵守 BP-01 及付款/权益政策）。

**禁止**在 CRM 预约、权益回执超时后，把“已发权益”当作“成交成功”的替代判断；销售成交与教学权益是独立状态。

### TX-I05：销售业绩金额守恒

一份 SaleEvent 的有效审批版本中：
- 业务分配比例总计为 10000 基点，即 100%。
- 按整数分的金额分配总和精确等于原始可分配成交额，余分按确定性舍入规则处理。
- 同一成交的原始机构成交额只统计一次，不因多个销售、辅助市场活动或一个共享家庭而加倍。
- 退款后的业绩冲回 BP-05 尚未最终批准；不得把“默认按原比例冲回”宣传为已经同意的工资政策。

### TX-I06：CRM 权益发放业务唯一

- 新系统订单明细 order_item_id 必须作为 CRM 的长期领域唯一性凭据。
- 同一业务意图的 Idempotency-Key 只允许一份实际课时权益，哪怕网络反复请求、服务重启或客户端换了提交会话。
- CRM 返回明确权威 package_id 并经状态核实后才标记 completed。
- CRM 未提供真实领域防重与最终结果查询接口前，**暂停自动发课链路**。
- 退款后课程权益是否冻结、调整或补偿，须根据 CRM 已经上课/消课状态执行专门规则，不允许从销售侧直接改 CRM 数据表。

## 4. 并发设计与建议事务步骤

### 4.1 全局一致的加锁顺序（拟议）

所有涉及同一经济事件的交易，先按固定顺序锁定外部权威收款记录，再锁定关联退款/冲正记录，再按 UUID 排序锁定全部受影响的订单。对于跨多个订单的操作，先明确完整对象集合；不得分批用不同顺序获取锁导致死锁。

执行中校验：
- 用户是否对本订单、相关学生、所属机构具有权利；
- 数据版本是否仍与批准版本一致；
- 外部交易编号是否重复、收款是否仍 confirmed；
- 当前有效分配与退款的实际合计；
- 是否已存在 SaleEvent 或 CRM 发课记录。

拒绝事务时必须整体回滚，没有“付款分配成功、唯一成交事件却丢失”的中间落库状态。锁顺序是设计方案，需要在实际 PostgreSQL 和并发测试中验证。

### 4.2 确认付款分配的伪流程（不是可直接执行的代码）

    BEGIN TRANSACTION
      VERIFY finance authority + operator scope + idempotency request
      LOCK receipt / related adjustments / impacted orders in canonical order
      VERIFY receipt confirmed and not disputed or revoked
      VERIFY exact order targets, approved purpose and amount evidence
      VERIFY receipt remaining amount and each order permitted allocation
      APPROVE or REVERSE allocation with immutable compensation audit
      RECALCULATE net paid for each impacted order
      IF order accepted and net paid >= due and no dispute:
          INSERT SaleEvent once (unique order_id)
          INSERT audit and outbox once
      COMMIT
    ON ERROR: ROLLBACK, report accurate Chinese business cause

应执行受控角色授权和审批原版本重校验，不能只靠 SQL 的 CHECK。对高度并发的收款分配需真实测试多进程并发、超时与重试。

### 4.3 财务退款入账的伪流程

    BEGIN TRANSACTION
      VALIDATE authenticated, deduplicated refund authority event
      LOCK original receipt / refund / impacted orders consistently
      CHECK refund amount, source and per-order allocation conservation
      APPLY confirmed refund fact to intended student orders/items
      RECALCULATE order current net paid and any dispute/shortfall
      IF previously recognized:
          KEEP original SaleEvent
          APPEND correction / revenue adjustment / approved credit adjustment
          EMIT CRM entitlement-review task, NOT an unapproved direct hour deletion
      WRITE audit + outbox
      COMMIT

**退款并不等于“撤销原成交记录”。** 原成交报告与净调整报告需要不同数字和时间口径；不能混用。争议退款、缺财务凭证或责任未明确时，不可虚构退款金额。

### 4.4 跨 CRM 发课属于独立 Saga，不是分布式数据库事务

1. 本地业务事务写入已批准的“待发课”业务事件和唯一 order_item_id。
2. Worker 使用独立 M13 服务身份提交 CRM；如果无可核验的正式付款/权益政策，不允许发起。
3. 成功响应：验证正式 CRM 学号、课程、付费与赠送单位、crm_package_id 与源版本，记录 completed。
4. 未得到明确结果：保持 unknown，查询 CRM 的原始业务请求结果，不换键创建第二笔。
5. 确认 CRM 未生成权益且原请求无后续执行风险时，才可走原键恢复/经批准的新业务意图流程。
6. 人工复核要求操作人、依据和时间，可重复运行只读对账，不得重复写权益。

需要 CRM 仓库未来另行实现接口，**本 PR 不修改原 CRM 仓库**。

## 5. 两个学生、一笔付款的可核算案例

| 业务事实 | 哥哥订单 | 妹妹订单 | 机构总计 |
|---|---:|---:|---:|
| 应付金额 | ¥6,000 | ¥4,000 | ¥10,000 |
| 家长第一次真实付款（一个外部交易号） | — | — | ¥6,000 |

**案例 A：财务核实分配哥哥 ¥6,000，妹妹 ¥0。** 哥哥满足其他条件后，首次成交 ¥6,000；妹妹尚未成交。机构真实收款仍只有 ¥6,000，不能认为两笔订单都已付清。

**案例 B：财务核实分配哥哥 ¥3,000，妹妹 ¥3,000。** 哥哥还差 ¥3,000，妹妹还差 ¥1,000；两笔均不确认正式成交。

**案例 C：家长用途未明确。** 两笔订单有效净已付金额仍按已确认分配计算；这笔 ¥6,000 保持待分配，不得根据哥哥先报名或销售负责人不同而私自分给任何人。

**案例 D：哥哥已全额成交后实际退款 ¥1,000。** 首次成交金额仍为 ¥6,000；新增退款调整 ¥1,000；报告在“原始成交额 / 净调整额”口径分别展示 ¥6,000 / ¥5,000 的当前净额，不能再创建第二个哥哥首次成交。是否影响已上课课时和已发提成取决于经批准政策。

这些案例属于设计用模拟数据，不涉及真实客户、银行卡或课程余额。

## 6. 独立审计和用户可读的业务变更

员工不应看到原始 JSON、英文列名、堆栈或仅显示内部编号。以下是**展示示例**，并不证明系统页面已开发：

| 操作 | 人能读懂的展示 |
|---|---|
| 分配已确认付款 | “家长付款 ¥6,000 已核实，其中 ¥3,000 分配至哥哥订单、¥3,000 分配至妹妹订单。两份订单均未付清。” |
| 收款状态变化 | “哥哥订单：原已核实付款 ¥3,000；新增核实分配 ¥3,000；当前已付清 ¥6,000。” |
| 首次成交 | “哥哥课程订单已确认成交，成交额 ¥6,000，成交销售：A老师；记录于财务核实后。” |
| 退款调整 | “哥哥订单经财务核实退款 ¥1,000，原成交额保持 ¥6,000，当前净额为 ¥5,000；已提交业绩及课时权益复核。” |

审批查看应区分“待批准（尚未生效）”“已拒绝（没有生效）”“已批准并实际执行”“已批准但外部系统结果待核实”。敏感财务凭据和家长信息按字段权限脱敏。

## 7. 与 V3.1-01 和 V3.1-02 的接口一致性及发现的设计差距

**以下是新的设计缺口，而不是已修复内容：**

| 缺口 | 现有草案表现 | V3.1-03 建议补齐 |
|---|---|---|
| GAP-T01 | V3.1-01 付款分配使用状态与撤销时间，未设计全量不可修改的调整流水 | 增加不可变资金分配/冲正操作记录，或以追加式财务分录表承载全部变更 |
| GAP-T02 | 退款分配没有完整的外部来源关联校验及防双重扣减设计 | 强制绑定原收款、原订单和财务事件唯一编号，区分退款与同一笔拒付 |
| GAP-T03 | confirmed 状态不足以保证调用时仍有效 | 增加权威版本序号、状态更新顺序及有效性查询/对账 |
| GAP-T04 | sales_credits 缺乏“同一成交只能一份当前批准版本”的跨行约束 | 服务层同事务批准/撤销旧版本，必要时增加唯一约束 |
| GAP-T05 | refund 后 CRM 权益复核接口仍未确定 | 添加受控的权益调整/冻结协议草案，区分已消课和未消课余额 |
| GAP-T06 | 订单/报价/商机与学生的一致性主要靠服务端 | 强化业务命令和可审查的数据库复合约束；多校区前评审租户隔离 |
| GAP-T07 | 没有正式确认真实支付/退款来源的唯一权威 | 先明确 TP-03，默认禁止真实付款自动认定 |
| GAP-T08 | 成交计入哪一天、迟到对账是否追溯影响业绩期未冻结 | 明确实际到账时间、确认时间和入账时间三口径，提交政策评审 |

**处理方式：** 不擅自修改数据库 PR #1 或 API PR #2；在相关 PR 审核时提出修订，并在财务权威和业务规则确认后通过后续迁移/接口版本修订落实。现阶段不能声称这些差距已被代码解决。
