**版本**：V3.1-01（独立技术设计稿，待评审）

> 本文和 SQL 均为新市场销售系统的独立设计产物，不修改现有 CRM 的技术资料、数据库或代码。PostgreSQL 16+ 是参考技术选型，尚未经过技术评审批准。没有实际执行数据库迁移或运行验收。

## 2. 物理结构：55张业务与支撑表

下面列出的名称与 SQL 文件逐一对应。每个新系统内部实体使用 UUID 主键；不把电话号码或外部 CRM 学号直接作为本地主键。

### A. 组织、员工与权限（7张）

| 表名 | 中文作用 | 约束重点 |
|---|---|---|
| organizations | 机构 | 机构名称、状态 |
| campuses | 校区 | 机构归属、同机构内校区名唯一 |
| staff_users | 销售及系统员工 | 机构、用户状态、外部登录映射 |
| role_templates | 预设角色 | 机构内角色编码唯一 |
| user_role_grants | 用户角色授权 | 当前有效角色授权不重复 |
| data_scope_grants | 可查看的数据范围 | 用户、业务对象类别与可撤销授权 |
| field_policies | 字段查看/脱敏/拒绝规则 | 字段保护必须服务端执行 |

### B. 获客渠道、活动及费用（5张）

| 表名 | 中文作用 |
|---|---|
| marketing_channels | 首次来源和本次商机渠道 |
| marketing_campaigns | 具体市场活动、期间与预算 |
| campaign_channels | 市场活动关联多个渠道 |
| marketing_costs | 经审核的实际市场费用 |
| cost_allocations | 费用按实际证据分配至渠道或活动；不能随意平均 |

费用守恒：实际发生费用 = 已确认分配费用 + 尚未分配费用。两个分析维度不能双重累计机构总费用。

### C. 学生、联系人、家庭和 CRM 映射（7张）

| 表名 | 中文作用 | 约束重点 |
|---|---|---|
| students | 独立学生档案 | 学生唯一、负责人独立、版本号 |
| contacts | 家长及其他联系人 | 联系方式加密存储、拒绝联系标记 |
| student_contacts | 学生与联系人关系 | 一个联系人可关联多学生；有效关系不重复 |
| family_groups | 按需家庭关联组 | 单学生默认不建立；应有核实状态 |
| family_memberships | 家庭与学生的关系 | 错误关系可撤销，保留历史 |
| student_owner_history | 学生归属变更历史 | 旧负责人、新负责人及审批原因 |
| crm_identity_links | 与 CRM 学号的核实映射 | 已生效映射按本地与外部学生编号双向防重复 |

**关键说明：**数据库提供家庭关系数据结构，并不代表自动把同号码判为同一家人；只有经授权核实两名或更多属于同一家人的学生，业务服务才激活家庭。共享家长不自动共享学生资料查看权限。

**特殊情况：**学生可能涉及多监护关系，因此此版不擅自把“一个学生最多只能属于一个家庭组”定为业务规则。

### D. 线索、沟通、商机与任务（11张）

| 表名 | 中文作用 |
|---|---|
| contact_events | 一次真实咨询记录 |
| contact_event_students | 一次咨询涉及的多个学生 |
| student_acquisitions | 学生首次获客来源 |
| leads | 未明确学生时可保留的潜在线索 |
| lead_students | 线索与实际学生的核实关联 |
| opportunities | 每个具体学生的销售商机及其负责人 |
| opportunity_stage_history | 商机阶段变化追溯 |
| interactions | 一次真实跟进沟通 |
| interaction_subjects | 跟进涉及的学生/商机/线索 |
| sales_tasks | 员工待办、提醒及自动化任务去重 |
| campaign_participations | 学生或线索参与活动的记录 |

同一真实电话咨询可以涉及两个学生：沟通次数仍为一次，学生接触人数可以为二。首次来源和本次商机来源分别保存。

### E. 课程、试听、报价（6张）

| 表名 | 中文作用 |
|---|---|
| crm_course_projections | CRM 课程和标准价只读视图 |
| trial_bookings | 试听请求、确认、改期及结果未知状态 |
| trial_feedbacks | 真实试听参与和教师反馈 |
| quotes | 每次报价的独立版本与审批状态 |
| quote_items | 课程、计费数量、原价、优惠、报价金额 |
| discount_approvals | 绑定具体报价版本的优惠批准 |

试听已申请不等于 CRM 已确认预约；CRM 标准价改变时不能覆盖历史报价快照。报价有效期保障旧价的规则仍待 BP-03 确认。

### F. 学生订单、财务事实、业绩和权益（11张）

| 表名 | 中文作用 | 核心约束 |
|---|---|---|
| sales_orders | 一名学生对应的报名订单 | 订单状态、收款状态、权益状态分开 |
| sales_order_items | 订单下每门课程的购买明细 | 精确金额和计费单位 |
| payment_receipt_projections | 外部权威收款事实的本地投影 | 来源+租户+真实交易编号唯一 |
| payment_allocations | 一笔实际付款分到多个学生订单 | 有效金额不可重复分配 |
| refund_projections | 已确认的外部退款事实 | 不能由销售虚构退款 |
| refund_allocations | 退款落实到订单及课程明细 | 退款金额须守恒 |
| sale_events | 正式销售成交事件 | 同一订单首次事件唯一 |
| sales_credits | 多销售人员业绩分配 | 每版本合计10000基点 |
| sales_credit_adjustments | 退款后追加的业绩变更 | 原始历史不删除 |
| sale_campaign_attributions | 主活动及辅助活动归因 | 每笔成交最多一个主要活动 |
| crm_entitlement_links | 订单明细与实际 CRM 课时权益映射 | 一条订单明细不能重复发课时 |

金额采用整数分；课程“每次课分钟数”“付费课时”“赠送课时”和“课程次数”各自独立，禁止混淆。

### G. 审批、审计、集成及自动化（8张）

| 表名 | 中文作用 |
|---|---|
| approval_cases | 业务对象及版本绑定的审批 |
| audit_events | 追加式业务变更历史 |
| integration_outbox | 业务事务一起写入待发送事件 |
| integration_inbox | 外部事件去重处理 |
| integration_tasks | CRM 请求键、超时查询、执行状态 |
| reconciliation_runs | 跨系统数据对账批次 |
| automation_rules | 低风险规则和高风险审批配置 |
| automation_executions | 自动化事件执行去重及结果追溯 |

**合计：7 + 5 + 7 + 11 + 6 + 11 + 8 = 55 张表。**

## 3. 字段类型与数据保护

| 类型 | 用途 |
|---|---|
| UUID | 新系统的内部主键 |
| BIGINT | 收款、费用、订单、退款、业绩等金额的整数分 |
| NUMERIC(16,4) | 课时数量、课程计费数量 |
| TIMESTAMPTZ | UTC 时刻及正式确认时间 |
| DATE | 市场费用等日历日期 |
| TEXT | 标准描述、版本标识、外部 ID |
| JSONB | 审计业务快照和证据拓展，不代替主干金额及关系字段 |
| BYTEA | 加密的敏感联系方式及安全查找值 |

联系方式查询只用于找到“待核实候选”，不能用电话号码或其 HMAC 自动认定学生或家庭身份。

SQL 的 created_at 默认值不会自动维护 updated_at，也不会自动增加 version；后续服务端更新命令必须明确处理。

## 4. 已落实的数据库级约束

1. 学生、联系人、商机、报价、订单、收款及发课映射使用明确外键。
2. 同一学生与同一联系人不能重复建立多条当前有效关系。
3. CRM 已核实学号映射在本地学生及外部学号两侧防重复。
4. 同一报名订单只能拥有一条首次正式成交事件。
5. 同一笔成交最多有一项主要市场活动。
6. 同一订单明细只有一个 CRM 权益交接对象与请求键。
7. 同一收款来源及外部交易编号不能重复登记。
8. 同一付款分配至同一订单不能重复留下两条当前有效分配。
9. 业绩比例基点在合法整数范围内。
10. 基本金额、数量不得为负数或无效状态。

## 5. 仍需由事务服务强制的金额与权限不变量

**数据库初始表结构不能单独证明财务交易安全。**

| 编号 | 约束 | 正式实现要求 |
|---|---|---|
| DB-I01 | 付款分配总额不超过一笔有效收款可用金额 | 锁定收款及订单，同一事务检查，测试并发 |
| DB-I02 | 确认退款分配总额不超过真实退款 | 退款行锁、核实来源、交易约束 |
| DB-I03 | 订单合计等于课程明细合计 | 订单确认事务验证 |
| DB-I04 | 报价合计等于明细金额 | 版本锁定和批准验证 |
| DB-I05 | 多销售业绩合计100%，分配金额按分精确相等 | 有效版本同事务提交 |
| DB-I06 | 家庭组至少两名经过确认的学生 | 确认家庭关系时的原子校验 |
| DB-I07 | 学生、商机、报价、订单及组织归属一致 | 服务端对象级权限和关联校验 |
| DB-I08 | 只有权威有效付款才算已付清 | 支付来源验证和订单状态机 |
| DB-I09 | 不能直接写状态绕过正式成交、发课 | 受控领域命令与数据库角色 |
| DB-I10 | 审计只追加、不能无痕覆盖 | 禁止普通业务角色更新或删除审计 |
| DB-I11 | CRM 超时不能重复创建试听预约与权益 | 原请求键、结果查询、对账 |
| DB-I12 | 并发成交最多生成一条初始成交事件 | 行锁、唯一约束、故障注入 |

上述约束未实现并验收前，不能连接真实支付、自动确认成交或自动发课时。

- BP-01：没有全额付款是否可以提前开课、谁批准及权益边界。
- BP-02：家长合并付款如何明确分配给不同学生订单。
- BP-03：报价有效期内 CRM 改价后的处理。
- BP-04：兄弟姐妹优惠如何落实到每名学生、每条订单明细。
- BP-05：退款时业绩冲回及已发提成处理。
- BP-06：机构多校区的归属与授权范围。
- BP-07：历史客户资料导入、保留期限及营销联系授权。

不可因为预先设计了数据表，就宣称这些业务决策已经批准。

## 7. 开发和迁移边界

- SQL 文件面向**新市场销售系统自己的测试 PostgreSQL 数据库**，不是现有 CRM 本地文件数据库。
- 不使用真实 CRM 数据、家长电话、工资或真实支付流水进行设计验证。
- 当前只有初始建表文件，没有生产迁移历史、备份与回滚方案；不得在正式环境直接执行。
- 机构与校区字段已预留，但本版不是完整的多租户隔离实现；跨机构外键隔离仍需进一步安全评审。
- API 与页面开发必须实施服务端字段过滤。审计 UI 必须显示“变更前／变更后”的中文业务含义、人员、金额、单位与原因，不能直接把 JSON 展示给客户或员工。
- 开发要使用独立任务分支和 PR，进入 main 前须审核；不得自动修改现有 CRM 的 main 或 work。
