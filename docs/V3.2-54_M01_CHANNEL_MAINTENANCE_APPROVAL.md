# V3.2-54｜M01 渠道新增、编辑、停用申请与独立主管审批（隔离测试）

> V3.2-53 Draft PR #60 最新 HEAD 已通过 GitHub Actions #43591024917 `completed/success`。本期以该隔离基线实现渠道变更的真实数据库事务，但**只在一次性 CI 的虚构渠道表生效**。不合并、不部署、不接真实财务或 CRM，不新增生产迁移。

## 1. 新增两条可运行安全接口

| 严格员工 HTTP 操作 | 用途 | 最终改变渠道的条件 |
|---|---|---|
| `POST /api/v1/marketing-channels/change-requests` | 登记 `create`、`edit`、`deactivate`，必须有材料、原因及防重复编号 | **绝不直接改变渠道**；只建立 `pending` 记录和不可改写的审计事件 |
| `POST /api/v1/marketing-channels/change-requests/{request_id}/decision` | **另一位当前有效销售主管**审核 `approved` 或 `rejected` | 批准后在同一 PostgreSQL 事务中修改一次虚构渠道；驳回无变更，记录审核事件 |

这两条 POST 仅允许严格员工模式，旧版演示宽权限连接绝不执行。HTTP 请求必须带真实验证的模拟 RS256 身份、固定员工 PostgreSQL LOGIN 对应的批准记录、`Idempotency-Key`。没有经理审批不可更改渠道；经理也不能自己审核自己提交的申请。

## 2. SQL 与数据范围

`tests/sql/create_v3_2_54_channel_change_workflow.sql` **仅由完整 CI 安装到可销毁测试 PostgreSQL**，不放入 `db/migrations`。该文件创建：

- `ms.isolated_channel_change_requests`：仅用于虚构渠道的申请与审批状态、提交者、审批人、依据、变更前快照与防重复编号，拒绝应用员工直接 SELECT/UPDATE。
- `ms.request_isolated_channel_change(...)`：解析员工数据库 LOGIN、固定机构，验证业务输入和目标，生成 `pending` 申请和审计事件 `CHANNEL_CHANGE_REQUESTED`。
- `ms.review_isolated_channel_change(...)`：重新检查当前销售主管角色、同机构及不同申请人、目标是否被并发更改；批准后修改 `ms.marketing_channels`，驳回保持原状；写入 `CHANNEL_CHANGE_APPLIED` 或 `CHANNEL_CHANGE_REJECTED`。
- `ms.assert_isolated_channel_parent(...)`：拒绝跨机构、停用父渠道、自引用、循环或超过 16 层的上级结构。

所有渠道更改均为**不删除历史**：停用仅将 `status` 变成 `inactive`，不能删除渠道、订单、咨询、来源归因、SaleEvent、收付款或消课；父级停用对后代的影响由原 M01 只读目录独立呈现。名称编辑保留原始快照和审计，不代表可改写任何既有首次来源归因。审批时若渠道已经被其他操作更改，使用申请中的旧快照拒绝陈旧修改，必须人工重新申请。

不添加全表数据库权限：原始渠道表、员工登记、审批台账、审计修改及财务表均对现有应用 LOGIN 保持不可直接访问；员工只能调用明确授权的 SECURITY DEFINER 函数。独立管理员仍由数据库受保护的现有 `sales_manager` 角色验证，**JWT 中自称 super_admin 无效**。

## 3. 隔离真实数据库回归

`tests/security/m01-channel-change-approval.test.mjs` 实际使用 PostgreSQL 中两位虚构销售员工与两位独立主管的不同受限写入账号、模拟独立审核的签名身份，验证：

1. **新增**申请前后的渠道表不变；同一防重复编号重复同一内容只返回原申请，改内容返回 409；销售员工尝试自己审批返回 403。另一位主管批准后仅新增一条本机构渠道。
2. **编辑**需记录原快照；另一个旧申请在目标已改后必须拒绝，以免覆盖新的批准结果。跨机构渠道目标、跨机构上级、自引用均拒绝。
3. **停用**只有审批后才将 `status` 设为 `inactive`；不能删除历史记录。审批人不能复用一个新的编号重复执行已完成的操作。
4. 主管也不能审批自己申请，必须交由第二位不同主管批准；纯销售账号不能批准，且与 JWT 的伪造经理声明无关。
5. **驳回**不新增渠道。审计事件同时记录申请与执行/驳回；账户身份撤销后立即拒绝旧 JWT 后续写入。
6. 所有员工受限账户依然不能对原渠道表、请求明细表、资金或销售订单直接读写；严格模式的请求过程中**宽权限数据库连接调用次数始终为 0**。
