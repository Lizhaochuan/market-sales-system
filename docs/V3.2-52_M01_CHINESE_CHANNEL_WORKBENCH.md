# V3.2-52｜M01 获客渠道中文管理页（隔离只读）

> 基于 Draft PR #58（V3.2-51，HEAD `1b2c67e96ab6502c0cf8e82fe7c7d8e00f9aa79d`），其 GitHub Actions #43589267498 为 `completed/success`。此处的“通过”只代表隔离 CI，不代表正式员工权限或生产运营验收。本版自身最新 HEAD 的 CI 仍需独立通过。

## 1. 实际交付

延续现有 `GET /api/v1/marketing-channels`、迁移 001 的 `ms.marketing_channels` 和同机构查询结果，新增演示网页中的“**获客渠道**”导航与只读列表。销售演示账号可以在中文工作台直接查看本机构已有渠道，而不必手工发 API 请求。

- `web/index.html` 新增只读的渠道模块，包含渠道数、当前机构有效渠道数、父子渠道及停用原因说明；**不提供新增、修改、删除、启用渠道按钮**。
- `web/app.js` 仅在**非严格演示模式**中请求渠道接口。严格员工模式不执行渠道 GET，并继续隐藏导航；不能绕过 `STAFF_ROUTE_UNMIGRATED`。
- 用户界面通过 `document.createElement` 和 `textContent` 绘制渠道名、层级、状态；从数据库传来的名称即使包含 `<img>` 或脚本字符，也只能作为普通文字，不能被解析成 HTML。
- 每次读取必须核对 `m01-isolated-channel-catalog-v1`、`isolated_readonly_not_production`、禁止生产集成标志及数量一致性；失败时**清除之前的渠道列表**，显示失败原因，绝不保留上一个成功结果冒充当前有效数据。
- 退出演示账号同时清除内存中的渠道目录和已渲染 DOM，避免下一位使用者看到上一位账号的旧结果。

## 2. 状态语义修正

既有 V3.2-51 返回的 `effective_status` 曾将“渠道自身停用”和“父级停用导致继承不可用”都写成 `inactive_inherited`。本期同时更新 `src/marketing-channel-catalog.mjs`、原有 PostgreSQL/HTTP 测试及隔离 OpenAPI，使其明确区分：

| 数据库渠道状态 | 父级有效状态 | 展示的最终状态 |
|---|---|---|
| `active` | 无上级或上级有效 | `active`：正常使用 |
| `inactive` | 任意 | `inactive`：本渠道已停用 |
| `active` | 上级已停用/继承不可用 | `inactive_inherited`：因上级渠道停用而不可用 |

这个变化仅修正**读出的有效状态语义**，不更新数据库渠道记录、不追溯改写来源归因或已发生交易。

## 3. 真实 Chromium 回归

新增 `tests/browser/m01-channels.spec.mjs`，运行时向隔离数据库已存在的虚构机构插入四条临时渠道（包括直接停用、上级停用、仍处于 active 的子渠道，以及带有 HTML 代码的虚构名称），随后：

1. 使用本地虚构销售员工登录并进入渠道页，检查中文名称、层级、两个停用原因的区别。
2. 检查恶意 HTML 字符串按**普通文字**出现，页面上不存在对应恶意 DOM 节点。
3. 在同一登录会话模拟渠道接口返回 `500`，刷新后必须清空旧渠道名称并显示读取失败；恢复接口后应重新正常显示。
4. 将 Chromium 视口缩小到 390 像素，检查页面可操作且未发生横向溢出。
5. 退出后 DOM 及缓存中的渠道信息均不再可读；结束测试时删除临时渠道，保留既有虚构机构数据。

原有双机构 HTTP 授权、无权限 401/403、跨机构父引用拒绝、环路拒绝等安全测试继续执行；并在静态合同中检查严格模式未获得新的宽表读取授权。
