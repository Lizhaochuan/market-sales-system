# V3.2-04｜员工身份治理、撤销与数据库权限隔离

**项目：** market-sales-system（独立市场销售系统）  
**分支：** `chatgpt/v3-2-04-identity-governance`  
**集成基线：** PR #7（V3.2-03），其上游依次为 PR #6、PR #5、PR #4，均为待审草稿。  
**发布级别：** 仅限本机和隔离 PostgreSQL 16 虚构数据。**不是生产员工认证、权限系统或已完成 CRM 集成。**

## 1. 本阶段真正解决的问题

此前 V3.2-03 已能验证外部 RS256 令牌，并凭预先建立的身份绑定查找系统员工，但仍依赖数据库管理者直接建立/撤销绑定。这样难以追踪谁提出、谁批准和为什么更改。

V3.2-04 补充独立的**身份绑定与撤销审批流程**，在应用层及数据库层记录原始申请、不同主管的审核结果、依据、时间和中文业务审计。同时增加隔离环境专门的低权限数据库角色，测试它不能查看订单/财务/CRM课时、改写审批记录或修改员工角色。

这只是正式身份管理的**可运行基础模块**。正式身份提供商的选择、登录协议全流程、企业账号绑定申请入口、账号生命周期、人事操作授权和机构部署仍未实施。

## 2. 管理者能看到和操作的内容

| 中文页面 | 操作 | 约束 |
|---|---|---|
| 员工身份审批 → 申请绑定 | 选择本机构有效员工，填写可信身份发行方、外部 subject 及中文材料说明 | 申请人不能是身份绑定目标本人；申请阶段不激活身份 |
| 员工身份审批 → 审核绑定 | 另一位主管独立核实，批准或驳回 | 审核人不能是申请人或目标员工；同申请只处理一次 |
| 员工身份审批 → 申请撤销 | 选择已经生效的外部身份绑定，提交撤销原因 | 申请阶段不假装身份已经失效；需第二主管决定 |
| 员工身份审批 → 审核撤销 | 第二位主管批准后，原绑定被撤销 | 撤销后同一有效签名令牌也失去该系统的员工访问资格 |
| 员工身份审批 → 历史 | 显示绑定/撤销、申请人、审批人及中文状态 | 不向网页列表暴露完整外部 `subject` |
| 业务变更记录 | 主管按身份变更申请查看中文审计 | 不显示原始数据库 JSON |
| 学生客户列表 | 跨销售明确授权的学生仍可见，年级显示“已隐藏” | 这只是第一项字段级遮挡，不代表所有字段都实现了策略引擎 |

普通销售不得进入员工身份管理 API，页面也不显示该菜单。系统不会依据外部令牌中的角色自称或客户端提交的员工名称直接授予权限。

## 3. 可运行接口（5项，全部仅隔离环境）

| 方法 | 路径 | 功能 |
|---|---|---|
| GET | `/api/v1/identity/staff` | 查询本机构管理员可选员工 |
| GET | `/api/v1/identity/bindings` | 查看已生效的外部身份关联；不回传 subject |
| GET | `/api/v1/identity/change-requests` | 查询身份变更申请及申请人/审核人/状态 |
| POST | `/api/v1/identity/change-requests` | 申请绑定或申请撤销，不直接变更生效身份 |
| POST | `/api/v1/identity/change-requests/{requestId}/decision` | 不同主管执行不可重复的批准或驳回 |

原先 14+7+2 条独立隔离接口的设计和实现保持原状，新增 5 条后共有 **28 条低风险隔离接口**，不包含收款、订单、正式成交或 CRM 权益写入。参见 `api/openapi/identity-governance-implemented.v3.2.json`。

写请求继续必须提供 `Idempotency-Key`；相同请求键、相同业务内容只返回原结果，换了业务内容却使用旧键必须拒绝。数据库审批事实和实际绑定或撤销在同一个事务写入，不能在审批失败时产生半成功的身份变更。

## 4. 数据库迁移与安全约束

### 007｜身份变更申请及双人审核
- `ms.identity_change_requests`：请求类型（bind/revoke）、同机构目标员工、发行方及外部 subject、请求依据、申请人和当前状态。
- `ms.identity_change_decisions`：独立审核人、唯一请求、批准或驳回、核实依据、中文理由；不可 UPDATE/DELETE。
- 同一外部主体不允许同时存在多份待审核绑定申请；同一现有绑定不允许同时存在多份待审核撤销申请。
- 目标员工须有效且在本机构；审核人与申请人、目标员工必须是不同的人。审核人必须是本机构有效主管。
- 申请一旦完成，只能留下历史，不得重新以新键反复批准或悄悄改变原始申请内容。

### 008｜低风险数据库运行角色（隔离候选）
- 创建 `ms_lowrisk_runtime NOLOGIN`，无正式密码，不等于生产数据库账号。
- 允许读取核心学生/线索/联系人和有限身份审批数据，并按列限制审核状态、身份撤销及幂等回执的业务更新。
- **拒绝**：直接访问销售订单、收款、退款、CRM课时权益；更新员工状态、修改/授权角色；更新或删除中文业务审计；删除身份审批决定；在 `ms` 模式下创建数据库对象。
- 外部身份实际绑定和撤销增加对应 `approval_request_id` / `revocation_request_id`。当受限角色执行时必须存在匹配的批准决定，否则数据库触发器拒绝。
- 上述权限为测试方案。CI 的其他应用测试仍使用测试数据库管理员角色；尚未完成将应用全流程切换为独立低权限 LOGIN、全表租户行级安全策略（RLS）或正式备份/回滚测试。

**数据库管理员的高权限不能靠此方案限制。** 正式上线前必须分离迁移管理员、业务服务账号、审计读取账号，分离秘钥与网络访问权限，并在数据库所有者不参与时重复所有测试。身份审批不能代替真实人事、IT 管理员的授权制度。

## 5. 安全验收与被拒绝场景

| 类别 | 必须验证的效果 |
|---|---|
| 身份绑定 | 未获审核的外部 subject 即使持有真实 RSA 签名令牌也不能进入本业务 |
| 自批保护 | 申请人/身份目标本人无法作出自己的身份绑定或撤销决定 |
| 组织隔离 | 不能将其他机构的员工绑定成本机构身份 |
| 循环审批 | 同一申请一旦批准/驳回不得重复执行；同键同内容重试可读取已有结果 |
| 账号撤销 | 第二位主管批准撤销后，旧外部身份令牌立即无法访问 |
| 员工停用 | 管理者停用账号后，同一张未过期旧令牌不能继续获得任何员工权限 |
| 角色撤销 | 主管角色撤销后，即使旧令牌仍有效，也不再能够审核身份变更 |
| 隐私 | 网页不向其他员工返回外部 subject；跨负责人明确授权学生的年级显示遮挡 |
| 数据库角色 | 低风险角色不能读财务表、修改员工角色、改写审批日志或未经批准直接绑定身份 |
| 浏览器 | 真实 Chromium 完成主管甲提交、主管乙审核，随后按相同分权规则撤销 |
| 旧模块 | V3.2-01/02/03 的学生管理、咨询、商机、家庭核实与中文审计回归不受影响 |

**自动化测试、真实业务人工核验与生产安全评审是不同层次。** 不能以 GitHub Actions 全绿代替第三方身份供应商接入、人工审核证明、渗透安全评估或老师/家长端现场验收。

## 6. 本阶段仍然开放的阻断

1. **真正生产员工登录尚未完成：** 身份供应商尚未批准，OIDC Authorization Code+PKCE 登录、JWKS 轮换/可信发现、MFA、人事离职事件同步、紧急停用会话及浏览器会话防护仍待设计和实现。
2. **身份关联材料核实仍依赖人工：** 外部员工 subject 由主管输入，尚无受信任 HR/IT 目录核验、受控邀请和证明留存流程。
3. **数据库实际运行账号尚未全面切换：** 独立角色能拒绝某些高风险 SQL，但它本身不能替代数据库 RLS、数据库管理员权限分离、审计防篡改和多机构严格隔离。
4. **跨学生和字段访问仍不完整：** 本轮只实现跨负责人授权的年级遮挡，正式联系人隐私、全部课程/金额/家庭数据字段尚无完整权限策略引擎。
5. **家庭关系的撤销与材料隐私仍需业务决策：** 已核实家庭如何拆分、纠错、保留证明和审计还未关闭。
6. **正式财务/教学接口不允许开放：** 财务权威收款、退款、业绩归因和 CRM 课程权益继续受到此前未批准的业务与技术阻断。
