# V3.2-15｜员工身份目录低权限隔离与跨销售联系人管理权独立审批

**状态：** 独立市场销售仓库中的虚构环境开发版本。本阶段继续基于 V3.2-14 PR #18，所有上游 PR 与本轮 PR 均保留 Draft，不合并。**不修改** `Lizhaochuan/edu-management-system` 的代码、数据库和技术文档。

## 一、为什么这一阶段要同时修复身份和联系人交接

在 V3.2-13/14 中，学生、联系人、单学生待核实关系和真实咨询的原有 POST 路径已迁移到员工级非所有者 PostgreSQL 账号。但是**原 HTTP 请求入口依然用较宽的旧业务数据库读取身份证明、员工状态及角色**。如果把这部分误认为全面最小权限，会留下实际管理风险。

另一方面，教培机构会出现两名销售交换联系人跟进责任的场景：不能把数据库历史字段 `contacts.created_by` 直接改掉，更不能把联系人管理权交接解释为所有孩子、线索、咨询、家庭关系与财务归因一起交接。

本轮真实实现两项独立保护。

## 二、核心安全改动 A：严格员工身份目录不再通过旧业务数据库查询

新增 `018_strict_function_only_auth_directory.sql`：

- `ms.resolve_strict_verified_staff(issuer,subject)` 是唯一允许严格模式身份目录账号调用的业务函数。函数在受信任的数据库所有者上下文中核对：外部身份与员工的绑定未撤销、两名主管批准记录一致、员工和机构有效，以及**数据库中实时生效的角色授权**。
- 函数只返回必需的员工 UUID、机构 UUID、员工中文显示名称及生效角色代码；不会把外部 subject、员工完整资料、手机、核实材料、薪酬、客户、财务表提供给应用账号。
- `ms_strict_auth_directory_reader` 角色仅有此函数的 EXECUTE；`ms_strict_auth_login` 是独立非所有者 LOGIN，无原始员工、身份绑定、角色、客户、审计、财务的 SELECT/UPDATE/INSERT 和建表权限。
- `src/strict-auth-directory.mjs` 启动前检查登录账号的权限，拒绝超级用户、BYPASSRLS、表级员工身份读取权和其他高权限账号。
- `src/app.mjs` 在 `strictStaffMode=true` 时**根本不再建立旧业务 DB 连接**：先验签受信任 RSA 外部身份，只从函数-only 目录获取当前员工上下文，后续业务 GET 走个人只读账号，POST 走本人独立低权限写账号，权限错配直接拒绝。
- `src/server.mjs` 严格模式不创建旧业务连接池，只允许本机管理员提供 `DATABASE_URL_AUTH_DIRECTORY`，启动前完成真实账号审查。缺少目录配置、使用 DB owner 或直接员工表 SELECT 权限都拒绝启动。
- 虚构演示模式依旧保留原演示路径和自动化回归，**不代表生产正式登录**。正式企业 IdP/OIDC Code+PKCE/MFA、受信任 JWKS 自动轮换、HR 生命周期与高可用部署尚未完成。

**安全边界：** 目录返回的是查询瞬间的已批准员工身份；每次真正写业务时仍在同一员工专属 PostgreSQL 会话重新校验身份绑定。不能用令牌中伪造的 `role=super_admin`、`staff_id`、`org_id` 获取任何授权。

## 三、核心安全改动 B：只交接当前联系人管理权，不改写历史和学生归属

新增 `019_independent_contact_custody_approval.sql`，包含 `ms.contact_custody_requests`、`ms.contact_custody_decisions` 和 `ms.contact_custody_assignments`，并为当前管理人及有效独立主管提供受限制的 SQL 函数：

| 操作 | 只有什么情况下可以执行 | 结果 |
|---|---|---|
| 当前管理人申请交接 | 员工已批准绑定，实际当前管理该联系人，接收人为同机构其他有效员工 | 仅生成**待独立审核**申请；联系人并未被交接 |
| 独立主管批准/驳回 | 主管有数据库实时有效经理角色，且不是申请人、接收人；申请仍待审、原管理权未发生变化 | 审批被不可变审计记录；批准时只变更联系人**当前管理人** |
| 新管理人登记后续咨询 | 联系人已正式批准交接，接收员工自己的专属数据库账号和本人签名身份同时有效 | 新咨询由接收人记录；**原咨询依旧属于原登记员工** |
| 新管理人将联系人关联到自己的学生 | 新员工同时是该联系人的当前管理人和该学生当前负责人 | 只能新增**该名学生的一条待核实关系**，不建立或合并家庭 |

具体限制：

- 原始 `contacts.created_by` 是历史事实，**完全保留**。过去 `contact_events.recorded_by`、学生负责人、`student_contacts`、线索、商机及其归因、家庭成员、订单/收退款和 CRM 课时全都不转移。
- 变更后，原创建人不再仅凭 `created_by` 永远获得无条件查看或写入权限；但如果原员工仍拥有某名独立学生且学生与该联系人关联，他仍可根据**那名学生自己的授权**看到最小化联系人姓名，**不是交接回来也不是分享其他孩子资料**。
- 接收员工的旧咨询记录仍不可查看，他只能记录从本人实际负责开始发生的新咨询。一次实际咨询只保存一次，不因家长关联两个孩子而复制。
- 审核人不能审核自己发起或接收的申请；有效主管角色由数据库保护的角色授权决定，而不是请求中的员工自称主管。
- 所有申请/审核必须提供中文理由、虚构核验依据与有效防重编号。相同编号/内容重试安全返回原结果，改变内容或重复审核拒绝；审批记录有不可变触发器，不能原地篡改。
- 普通员工只能调用受保护 SQL 函数，没有三个交接基础表的 SELECT/INSERT/UPDATE/DELETE；申请及结果的最小中文展示走员工专用只读视图，**不返回原始材料或儿童隐私字段**。

## 四、实际中文操作入口

原 `web/index.html` 中“家长与联系人”页面新增了 **联系人管理权交接（独立主管审批）**：

- 当前管理人选择具体联系人、同机构接收员工，填写中文交接理由和虚构材料说明，再提交待审申请；
- 申请与接收员工，以及有合法审批资格的主管，可在自己的严格模式页面查看最小业务状态，不会看到私人证明；
- 独立主管能在页面中批准或驳回；审核批准后相应联系人可以被接收员工看到并用于后续本人咨询；
- 仍没有正式统一企业登录；仅在本机隔离模式中使用测试管理员预先签发且已审批绑定的临时 RSA 签名身份，凭据只在内存、刷新/退出即失效。

**安全不是依赖按钮隐藏：** 即使 HTTP 直接绕过中文界面调用审批，数据库也会拒绝申请人、接收人自批、普通员工冒名、其他机构目标、已失效接收员工和非当前管理人的操作。
