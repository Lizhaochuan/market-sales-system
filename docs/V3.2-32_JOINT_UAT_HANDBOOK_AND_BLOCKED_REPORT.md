# V3.2-32｜财务、教务、销售与信息安全联合联调 UAT 手册（隔离演练）

**文档状态：正式业务联调前的工作清单，不是联调批准书。**
**项目：** 独立市场销售系统（`Lizhaochuan/market-sales-system`）。
**依赖：** V3.2-31 Draft PR #36，最新验收提交 `38f2317c9ade617077fc7ee9c6a10d4a0170528d`。
**使用范围：** 只使用虚构来源与脱敏引用，不接通真实财务、CRM，不能修改原订单、资金或课时，不能解除 `hold_active`。

## 1. 要解决的问题

截至 V3.2-31，16 项真实财务/CRM 联调准入条件已经定义，但它们尚未有**真实业务权威签署、生产只读访问凭证及独立安全验收**。没有一个来源已获得真实访问资格。

V3.2-32 将财务和教务两份**同机构**虚构来源申请组合成一份只读联合验收报告；列出销售 3 项、财务 4 项、教务 4 项、信息安全 5 项。每项都写明负责人角色、需要提交的证据、手工验收标准、失败时的处理方式。共享的销售/安全缺失事项同时统计财务和教务来源申请，以免遗漏一方。

**注意：** `missing_events=0` 只代表尚未登记缺失事件，绝不表示已取得权威证据。报告全部 16 项固定 `production_verified=false`，真实连接、执行和解除隔离的标志也始终为 `false`。

## 2. 数据、权限和可追溯性

- `db/migrations/035_joint_integration_uat_readonly_report.sql`：增加 `ms.readonly_joint_integration_uat_report(finance_request_uuid, academic_request_uuid)`。只读取现有 16 项清单、不可变的缺失证据事件以及两来源异常事件数量，**不写入**任何业务表。
- 函数以保护的 PostgreSQL `SESSION_USER` 映射为唯一员工机构身份，且要求为本机构有效的独立 `source_security_reviewer`。财务、教务、销售或普通业务账号无权直接取得跨领域联合报告。
- 两个来源申请必须属于**同一机构**，一个为财务、另一个为教务；交换顺序、重复同一来源、访问机构 B、缺任意申请全部拒绝。
- 新增 `ms_joint_uat_report_reader` 只授予测试安全审核员这一专门函数的 EXECUTE，不能直接 SELECT 新旧财务、合同、学生、课时或原始审批表。
- `src/joint-integration-uat-report.mjs`：从已经受限的联合查询响应生成可供负责人阅读/审查的中文 Markdown 工作清单；明确列明 16 项、责任人角色、所需材料、验收条件及失败处理。
- 生成器验证 16 项编号、部门分布、字段类型和全部禁止执行标志。缺少一项、重复一项、伪造已批准或改成 `execution_allowed=true` 时拒绝渲染，不能生成误导性“验收通过”报告。
- 文档使用 SHA-256 生成**本地报告快照比对指纹**；该值不是签名、不是证据真伪检查，也不代表来源认证。
- 原始缺失事件仍由 V3.2-31 的追加记录留痕，不允许覆盖/删除；本阶段未创建独立持久报告版本，也不能替代未来正式 UAT 签字。

## 3. 责任与提交材料

| 部门与条目 | 需要谁负责 | 最少材料 | 失败处理 |
|---|---|---|---|
| 销售 3 项：合同主体、归因规则、解除责任 | 销售负责人、合同签约责任人和业绩审核人 | 目标学生独立确权、原合同/订单及 SaleEvent、业绩补偿政策、R01—R10 终验责任分配 | 保持原订单、历史、佣金和学生归属，不解除隔离 |
| 财务 4 项：权威负责人、账套映射、最小只读账号、资金对账 | 财务负责人、收付款权威所有人、财务系统管理员 | 正式来源责任人、账套/订单/收退款/拒付映射、只读权限证明、完整水位与经济事件守恒 | 不依据手工备注改款、不重新发起退款、不修改付款归属 |
| 教务 4 项：CRM 权威负责人、学生课包映射、最小只读账号、课程余额 | 教务负责人、CRM 所有人、课包/实授核对人 | CRM tenant、学生和课包唯一映射、只读权限、实上与剩余课时版本、超时结果查询流程 | 不重复发课、不删除已上课记录、不把 unknown 当作未执行 |
| 信息安全 5 项：信任锚、持久防重放、水位完整性、异常恢复、独立 UAT | 独立信息安全负责人和运维，财务/教务配合 | 可信证书发行/撤销、受众、分布式幂等、全量分页/高水位、演练报告与权限日志 | 不启用真实服务凭证，继续隔离并人工升级 |

## 4. 联调前应按顺序开展的真实 UAT（均未执行）

1. **负责人确认：** 财务、CRM 系统所有人提供真实的只读来源授权政策，由合同、销售、信息安全责任人分别确认。此阶段不能把虚构来源审核或 CI 结果当作其签名。
2. **身份及租户映射：** 每个机构分别确认账套、CRM tenant、学生 ID、课包 ID、合同主体；不得因为同一家庭或联系人合并两位学生的经济权益。
3. **只读权限验证：** 经正式批准的隔离联调环境中，正向查询成功，负向请求尝试退款、修改付款分配、订单改绑、发课、消课、改学生时必须被拒绝。敏感字段最小化、日志脱敏。
4. **业务权威核对：** 财务检查收款、退款、拒付、订单归属与金额守恒；教务查询课包、已授、已消、排课与剩余课时。每份证据包含独立来源版本、水位和查询人。
5. **故障及重复消息：** 检查超时 unknown、缺页、签名错误、序号断档、密钥撤销、迟到退款、已发课回执未返回、两机构混淆。任何一项不确定都必须维持人工复核。
6. **独立跨模块复核：** 销售、财务、教务、安全分别记录发现、失败证据和复验结果；真正在未来获得独立业务授权时，还必须设计单独的受控补偿和解除隔离机制，不能复用本期虚构来源的审批按钮。

以下项目目前**不能提交到模拟数据库作为生产批准**，只供将来正式流程设计：

```text
检查编号（例 finance_reconciliation）：
```

**绝不附带：** API 密钥、支付账号完整编号、儿童身份信息、真实合同原文或未脱敏日志。不得上传生产凭证到 GitHub。

## 6. 验收证据和停工条件

必须以本 PR 最新 HEAD 自动化验收为准：
- PostgreSQL 001—035 全部迁移成功，联合报告只读且仅独立安全角色可查，两机构不能互看。
- 16 项无遗漏、不能伪造已批准；跨机构、领域混淆和数据库原始表更新尝试均拒绝。
- 来源故障计数、共享销售/安全缺失事项按两份来源分别统计并汇总；报告生成只看受限查询结果。
- Node 全量、安全和已有业务流程，以及 Chromium **旧中文页面**、V3.1 合同回归全部通过。**本阶段尚未新增正式 UAT 管理页面**。

任何 CI 失败只能保留 Draft 并修复；即使 CI 成功，也**只说明隔离技术实现完成，不能宣布真实联调已通过**。
