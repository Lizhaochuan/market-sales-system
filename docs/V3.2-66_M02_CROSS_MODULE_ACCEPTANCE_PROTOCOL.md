## 不可替代的授权事实

V3.2-65 的销售人员证据齐全，**并不等于**财务接收、预算授权、教务实际履约核实或跨模块解除隔离。V3.2-66 只增加基于已受限、只读销售证据视图的 `ms.scoped_isolated_campaign_cross_module_acceptance_prerequisites`：若销售包未齐，返回 `blocked_sales_packet_incomplete`；已齐则返回 `blocked_trusted_finance_identity_missing`。任何情况 `hold_active=true`，`release_eligible=false`。

三方需要独立完成以下**未来准入条件**，现在均未获得外部授权：
- **销售**：保留原报告人材料、独立销售主管签名审核、事件时间线与证据摘要；仅形成待交接的最小化材料包，不伪造财务签收。
- **财务**：必须由外部财务权威配置实际信任链（签名颁发者、机构/员工稳定映射、撤销与失效检查、权限版本）、在独立系统签收指定材料摘要和快照版本，并以不可改写事件记录明确的接收/退回/待补正决定。预算审批、支付、营销费用与成本分摊另须独立合法授权，不能从“已签收”推导。
- **教务**：必须由外部教务权威验证学生关联、原始履约证据、课时、相关业务影响，提供独立签名核验结果；若涉及错绑且已有订单/收退款/实际履约，继续 `hold_active`，并确认原订单、支付、SaleEvent、课时与补偿记录保全。销售、财务、教务不能一人自审，也不得复用同一角色或未经批准的员工凭据代签。

## 仅供未来实现的证据交接协议（无运行入口）

`spec/v3-2-66-proposed-acceptance-envelope.schema.json` 明确定义将来可能需要的交接包结构：协议版本、机构/交接/异常 ID、固定材料摘要、原历史保全标志、幂等防重复值、按来源分列的事件摘要，以及销售/财务/教务三方分别签名的人员标识、接收记录、证据摘要、处理决定与签名时间。**这是草案，不是实际已认证、已签名或已发送的交接包**。后续落地需真正跨模块技术评审：签名算法与密钥生命周期、角色冲突检查、重放/乱序/重复防护、证据版本一致性、拒绝状态补偿、机构隔离、可撤销身份、历史事件只追加、操作和法律授权边界。不得直接用用户输入填入三个 `accepted` 值冒充验收。

## 当前隔离交付

- `GET /api/v1/marketing-campaigns/finance-incidents/acceptance-prerequisites` 只供经数据库身份双重核验的隔离员工读取本机构、自有或已有权限范围内的升级异常；保持最多 100 条和越权整体拒绝，无 POST/PUT/DELETE 解除入口，不暴露附件、签名、证据原文、审核理由或请求键。
- 中文工作台仅显示当前硬阻断；前置条件投影失败时清空旧数据并停止升级后追加功能，不出现“财务已批”按钮。
- 对照真实 PostgreSQL/HTTP、Chromium 和设计合同证明：销售包未齐/已齐都不解除隔离，财务/教务未认证，活动仍 `draft`，禁用资金及发布；外部接口不可调用，不能靠篡改 HTTP 返回让浏览器展示放行。
- 生产迁移仍 **001—038**，无 039。正式财务/CRM OpenAPI 仍 `proposed-unimplemented`，16 项外部准入、R01—R10 未验收。

学生为主要管理单位，家庭按需关联。涉及已下游订单、收付款或教务履约的真实错绑持续 `hold_active`，保留原始订单、收付款、SaleEvent、课程履约与后续可追溯补偿历史，不覆盖原记录。

`finance_authorized=false`、`execution_allowed=false`、`production_integration_allowed=false`、`release_allowed=false`、`merge_authorized=false`、`deploy_authorized=false`。市场销售技术文档单独保存；未经跨模块正式验收不合并、不部署、不修改原 `edu-management-system`。
