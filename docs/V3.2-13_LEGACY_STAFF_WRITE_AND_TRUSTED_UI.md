# V3.2-13｜原学生和联系人创建接口迁移至员工专属数据库写入

**独立仓库：** `Lizhaochuan/market-sales-system`，以 V3.2-12 PR #16 为基线；所有依赖 PR 保持 Draft。  
**定性：** 实际实现的**隔离员工严格模式**，不是正式 IdP 接入、生产登录、真财务或教培 CRM 联合验收。

## 1. 这一次不再只是新建另一条接口

V3.2-12 已实现独立的新路径 `POST /api/v1/lowrisk/students` 和 `POST /api/v1/lowrisk/contacts`，但**原中文工作台**仍向旧的 `POST /api/v1/students` 和 `POST /api/v1/contacts` 发送请求，可能通过机构级数据库账号写入。

本阶段为**这两条原路径**提供可选且拒绝回退的安全执行方式：

| 原中文工作台的操作 | 严格模式下的实际数据库执行 |
|---|---|
| 保存学生档案 `POST /api/v1/students` | 本人专属、仅能执行 `ms.create_scoped_student` 函数的数据库账号 |
| 保存联系人 `POST /api/v1/contacts` | 本人专属、仅能执行 `ms.create_scoped_contact` 函数的数据库账号 |

两种创建都先对外部 RSA 员工令牌验签，再确认身份已有正式的独立审批绑定。数据库 `session_user` 被固定映射到真实员工及机构；令牌即便自称“管理员”或自报其他机构，也不能改变实际归属。

**唯一允许的员工操作是为自己新建学生和联系人。** 学生默认独立；没有证据表明两个孩子属于同一家庭时，不创建家庭单位。联系人不会自动关联全部孩子；创建不会迁移他人销售线索、商机、成交归因、金融订单或 CRM 课程课时。

### 不回退要求

- 服务端明确启用严格员工模式后，原有两条 POST 不再调用旧 `handle(...createStudent/createContact)` 或旧的机构级 `api_write_receipts`。
- 员工专用连接池缺失、错配、员工离职/身份撤销、签名过期或签名不可信：**拒绝**。绝不调用权限更广的旧机构连接重试。
- 学生写入不接受 `owner_user_id`、`organization_id`、财务或课时字段。即使是主管也不能利用“新建学生”绕过客户负责人转交审批。
- 联系人写入仅接受称呼、拒绝主动联系标记；手机号码、微信号等未开放的个人信息由接口拦截。
- 两种写入复用 016 号迁移的真实数据库事务幂等与并发保护，相同员工/操作编号/内容只创建一次；重复编号对应其他内容或业务直接冲突。

## 2. 可信连接池与入口

`src/scoped-legacy-write-adapter.mjs` 为**原有两条 POST**实现新写入适配器。`src/app.mjs` 支持可信服务器端 `scopedWritePools` 映射，早于旧收据与旧业务逻辑执行。使用同一专用 PostgreSQL 连接进行最小权限预检、有效身份复核和真正创建。

`src/strict-staff-pools.mjs` 在启动时检查每一名员工的独立读账号与函数-only 写账号：

- 两类数据库账号均不能是超级用户、绕过数据库权限的账号、拥有学生/联系人原始表或财务读取权限的账号。
- 两类账号必须映射到**同一名有效员工、同一家机构**。重复映射、缺失、人数不一致、机构错配会阻止严格服务启动。
- 读写账号分离，用户不能通过浏览器、JWT、HTTP 参数或 SQL 的自定义变量选择其他人的数据库账号。
- 启动时只接受本机管理员提供的数据库连接配置；不能把生产数据库所有者账号冒充为员工连接池。

原独立服务器 `src/server.mjs` 增加隔离模式开关。仅在 **`MS_STAGE=isolated-test` 且 `MS_STRICT_STAFF_MODE=1`** 时启用；同时要求 `OIDC_ISSUER`、`OIDC_AUDIENCE`、`OIDC_JWKS_JSON` 和可信本机环境配置的 `MS_STAFF_READ_URLS_JSON`、`MS_STAFF_WRITE_URLS_JSON`，后两者必须是分别对应各员工的 PostgreSQL URL 数组，不能在网页输入或存储。全套配置缺失时拒绝启动，不能静默进入“既像安全版又是演示版”的状态。

**隔离模式不等于生产身份连接。** 这里的可信 RSA 公钥仅使用预先配置的虚构测试身份签名；还没有企业 IdP 的标准授权码+PKCE、MFA、JWKS 轮换、企业员工目录或正式会话治理。

## 3. 在原中文工作台上真正操作

原 `web/index.html`、`web/app.js` 现在额外提供“已批准员工签名身份（仅本机测试）”输入。虚构环境管理员签发的签名令牌可以打开**原本的学生/联系人中文界面**，与之前的学生共享审批页面采用相同的测试身份机制，但没有宣称已合并成正式单点登录。

在严格模式中：

1. 系统提示“严格员工权限测试模式”。原演示口令登录已被服务端禁用。
2. 员工使用已签名、已审批的外部测试身份，签名凭据只在页面内存中存留。刷新/退出消失，不写 URL、Cookie、localStorage。
3. 原中文工作台仅显示“工作概览、学生客户、家长与联系人”，原“保存学生档案”“保存联系人”按钮仍使用**原有 POST 路径**，但服务器从员工专属数据库最小权限函数完成创建。
4. 学生列表和联系人列表通过上一阶段已迁移的员工只读视图返回。即使同机构的另一位销售登入，也看不到本人未获授权的学生或联系人。
5. 咨询、商机、家庭核实、身份管理、财务和其他**尚未完成同等级迁移的旧路径**在服务端严格拒绝，导航对应入口隐藏。导航隐藏只是体验；安全控制始终在服务器和数据库。
6. 原虚构演示模式未启用严格开关时仍按此前模式运行，不应该将其用于真实客户。

- `src/scoped-legacy-write-adapter.mjs`：原两条客户创建接口的安全适配器；
- `src/strict-staff-pools.mjs`：服务器端员工读写池同人同机构一致性预检；
- `src/app.mjs`、`src/server.mjs`：拒绝回退、原接口真实接管和严格模式启动；
- `web/index.html`、`web/app.js`、`web/styles.css`：原中文工作台员工签名测试模式及已实现业务入口；
- `tests/security/legacy-scoped-writes.test.mjs`：真实 PostgreSQL 16 + HTTP + RSA + A/B 员工连接池，测试原始 POST 操作、未审批/身份撤销拒绝、冒名、并发幂等、防重冲突、无宽权限回退、原始审计与家庭/财务不被意外写入、严格关闭未迁移入口；
- `tests/browser/strict-employee.spec.mjs`：真实 Chromium 在原中文工作台使用测试签名员工身份，点击原有两个“保存”按钮，检查员工隔离、单学生家庭原则、移动窄屏、安全凭据保留和未迁移导航关闭；
- `api/openapi/legacy-scoped-lowrisk-implemented.v3.2.json`：原路径在严格隔离模式中的机器可读接口；
- `docs/V3.2-13_LEGACY_STAFF_WRITE_AND_TRUSTED_UI.md`：本独立说明。

验收必须持续包含 PostgreSQL 001—016 迁移、既有双机构和双主管的权限回归、家庭核实、V3.2-09–12 已完成的员工级只读/授权/低风险新接口、真实 Chromium 中文业务测试和 V3.1 技术合同回归。**以 GitHub Actions 对 PR 最新 HEAD 的 SUCCESS 和实际测试计数为准**，未通过前不标记完成。

## 5. 明确尚未完成

1. 虽然原**两条 POST**可以严格运行，但更早的咨询、线索、商机、联系人绑定、家庭审核、员工身份管理与审计等老路径仍未全部迁移到独立 SQL 最小权限；严格模式把这类接口关闭了，**不是所有功能均已完善**。
2. 严格模式的主数据库连接仍被用于外部身份映射与当前员工角色的只读核对，并未完成主数据库的全面去高权化。真实生产还须把这些读取收敛到最小只读身份目录。
3. 此次“已批准外部身份”仍需本机测试管理员手工提供 RSA 测试签名凭据，**未实现正式 OIDC 登录、PKCE、MFA、员工目录同步、会话续期和安全令牌下发**。
4. 先前独立学生共享/转交审批控制台仍独立使用测试签名凭据，尚未统一为正式生产 SSO。
5. 真实儿童及家长资料的法律合规审核、材料留存、系统上线、生产 DBA 审计、灾难恢复、正式跨系统业务审查仍未完成。
6. 正式财务收款、退款、结算、销售成交业绩以及教培 CRM 课时开通/消课/退课等高风险事项继续关闭。
