# V3.2-116｜M02 审核失效通知：签名 outbox 与负向回执隔离契约

## 已核验上游

基于 V3.2-115 Draft PR #122，HEAD `ed692c703c7bff585d9056c0b553320dfb04ed44`；GitHub Actions #43666196819（隔离 PostgreSQL 永久 HOLD）和 #43666196810（M02 聚合安全审查）均为 `completed/success`。V3.2-115 只能创建和审查**一次性测试数据库**中的暂停记录；生产自动事件触发器、可靠投递和真实外部审批尚未实现。

本期建立分层模型：**已持久 HOLD 事实 → 可重试的本地 outbox 消息 → 模拟独立接收方签署的“已收到但继续阻断”回执**。此阶段绝不等于实际跨系统消息可靠交付，更不产生财务、教务或学生纠错交接授权。

## 实现内容

1. `src/cross-module-hold-outbox-protocol.mjs` 提供 `createIsolatedHoldOutboxProtocol`，暴露 `publish`、`acknowledge`、`inspect` 三个入口。只接受 `organization_id`、`incident_id`、`student_id`、`hold_sequence` 四个严格字段，禁止调用方携带任何 `hold_active=false`、`finance_authorized=true` 或 `handoff_allowed=true` 的自述授权。
2. 消息发送前读取 V3.2-115 的 SQL HOLD head 和完整哈希事件链，核对指定事件 `HOLD_PENDING_EXTERNAL_AUTHORITY` 且处于完整来源历史中，再验证**临时测试 Ed25519 来源密钥**签名的机构/异常/学生作用域、HOLD 序号/摘要、来源 epoch/修订/撤权序号和有效期。签名证明的提供方由本次测试自行生成，**不是生产可信根或真实员工身份**。
3. 消息的不可变摘要绑定 HOLD 事件和测试签名证明。一次性 PostgreSQL `v106_isolated` 数据库中，`fixture_hold_outbox` 表仅允许按机构/异常/学生及 HOLD 序号递增插入，不可 UPDATE/DELETE。同一个序号重复入队、第二条先于第一条入队、跨机构测试角色及原 HOLD 不存在时均拒绝。测试环境在一笔 `SERIALIZABLE` 事务内校验已持久 HOLD 并插入本地 outbox。
4. `acknowledge` 验证**另一套独立的临时测试 Ed25519 接收方公钥**，签名仅准许 `delivery_status=fixture_received_still_blocked`；必须绑定同一作用域、HOLD 序号、消息摘要和接收者标识，有效期不能过期。负向回执按相同序号顺序独立入库；后续序号在前序回执缺失时拒绝确认。不存在正向“业务已交接/已批准”的回执格式。
5. `inspect` 在 outbox 缺失、尚无回执、已有负向回执以及数据库不可用时全部返回 `hold_active=true` 和所有业务授权为 false。测试回执只能证明本地 SQL 保存了测试接收声明；回执丢失、网络不确定、重复提交也不能被解释为解除暂停。

## PostgreSQL 和权限边界

新增 `tests/fixtures/v3-2-116-m02-hold-outbox.sql`、`tests/helpers/v3-2-116-m02-postgres-hold-outbox.mjs`、`scripts/v3-2-116-setup-hold-outbox.mjs`。SQL 只在一次性 GitHub Actions PostgreSQL 16 测试库 `v106_isolated` 执行：

- outbox 与负向回执均为只插入、可读取的独立表；采用 `FORCE ROW LEVEL SECURITY`，只有预设测试机构 A/B 的受限账号可读写自己的行。
- `SERIALIZABLE` + 机构/异常/学生作用域锁保障同一消息或同一负向回执的本地并发处理。序号跳跃、重放和双写不会产生两个成功结果。
- 严格限定消息内容为摘要及最少必要元数据，不接触原订单、资金、SaleEvent、课时、补偿或员工真实凭据。
- 源 HEAD 与消息的校验发生在 outbox 事务内，但**V3.2-115 HOLD 本身先于本事务提交**。因此 HOLD 创建和 outbox 入队并非同一笔原子创建事务；真实系统宕机于两者之间时，可能需要重扫补发。消息投递与对方真实系统事务也并未原子合并。

实际可靠交付仍需真实生产 outbox 生产者、工作任务领取/重试、失败回收、消息持久队列、身份授权与真实接收方、签名密钥治理，以及来源变更后的因果屏障。上述内容**本阶段没有开发，也没有连接第三方系统**。
