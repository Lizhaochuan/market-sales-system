## 二、身份认证原则与安全边界

1. **机构员工身份与外部令牌是两件事。** 外部身份服务只证明“这枚令牌由指定发行方签发、代表指定 subject”；本系统内部授权表决定该 subject 是否属于某个现有有效员工。令牌不能自行指定“我是主管”“我是某个机构”的权限。
2. **明确的签名白名单。** 当前实现只接受指定发行方、受众、可信公钥 ID（kid）的 RS256、RSA 2048 位及以上公钥。拒绝伪造签名、未知 key、错误 audience/issuer、过期/未生效和无绑定员工身份。
3. **不自动注册。** 若外部 subject 没有活跃绑定，返回拒绝，而不是创建员工或自动将其并入家庭/客户。
4. **绑定可以撤销。** `ms.staff_identity_bindings.revoked_at` 生效后，下次请求立即拒绝；同样的签名令牌也不再有机构业务访问权。
5. **员工状态和角色持续核查。** 服务每次操作查 `staff_users.status` 和数据库角色授权，不依据前端按钮是否隐藏决定业务权限。
6. **最小功能原则。** 目前仍然使用 `MS_STAGE=isolated-test` 与本机 `127.0.0.1` 监听。原演示口令登录只作用于虚构演示账号，不能用于正式员工。

### 配置示意（只用于隔离测试）

系统支持以下配置变量，但**没有在仓库中保存真实公钥、账号、口令或生产连接信息**：

- `OIDC_ISSUER`：受信任的 HTTPS 外部身份发行方；
- `OIDC_AUDIENCE`：本销售业务专用的令牌受众；
- `OIDC_JWKS_JSON`：由可信配置渠道传入的公开签名公钥集，不接受客户端任意传入。

三项必须同时提供，缺任何一项拒绝启动。出于安全原因，本阶段只实现基于已配置公钥的签名验签，**不自动从未知 URL 下载或信任任意公钥**。

**尚未实施：** 实际身份供应商选型与开户、登录跳转/PKCE、正式会话管理、签名公钥轮换和可信更新、机构安全管理员的绑定审批、跨组织管理、真实多因素认证和正式安全审计。因此即使代码能够验证 RSA 令牌，也不能宣布“正式员工认证已经完成”。

## 三、家庭关系两人审批

### 3.1 工作流程

1. **主管甲提交**：选择两名或以上独立学生，填写关系证据编号及家庭显示名称。系统保存 `pending` 和 `requested_by`，不会因此给销售顾问扩展其他孩子的访问权限。
2. **不同主管乙复核**：核对实际关系材料，在中文工作台填写独立复核凭据编号、原因，选择批准或驳回。
3. **服务端再次核对**：申请尚待审核、当前账号确实是本机构有效主管、审查人不同于申请人、家庭成员至少两名不同且都属于本机构。
4. **同一事务处理**：写入唯一 `family_review_decisions` 审批事实；批准时更新家庭及成员核实状态，驳回时更新为 `rejected`；同时追加中文审计和防重复回执。
5. **只读历史**：主管可在业务变更记录按家庭申请查看申请和审核前后状态。

### 3.2 必须永远保持的限制

- **自己不能审批自己**：前端会提示并禁用按钮，但最终拒绝由后端和数据库双重检查，任何人通过 API 直接调用也不例外。
- **一份申请只能得到一次最终决定**：唯一约束阻止用新请求键生成第二次审批；同一请求键同一内容仅返回原结果。
- **审核历史不可无痕修改**：`family_review_decisions` 禁止更新与删除。业务数据库账号也需要正式的最小权限配置，不能允许管理者随意修改底层表。
- **没有审批记录不允许直接改为“已核实”**：数据库触发器要求决定先存在；不支持绕开流程修改状态。
- **同家长或相同联系方式不证明亲属关系**：必须有明确人工证据；本系统暂不自动验证身份证、户籍或其他真实身份文件。
- **已核实家庭也不能自动越权**：学生负责人、商机负责人和学生数据范围继续独立。家庭关联不是通行证。
- **一旦驳回，仍保留原申请和中文驳回原因**；重新提交真实新证据应另建新业务申请，不能修改旧审批事实。

### 3.3 用户实际看到的变化

| 操作 | 中文界面显示 |
|---|---|
| 主管甲创建 | “家庭关系：待核实；申请人：模拟销售主管” |
| 主管甲试图自批 | “申请人不能审批自己的家庭关联申请” |
| 主管乙批准 | “家庭关系：已核实；审核人：模拟第二主管” |
| 主管乙驳回 | “家庭关系：已驳回”，保留审核原因 |
| 查看历史 | “原状态：待核实 → 新状态：已核实/已驳回”，显示中文实际业务内容 |

内部数据库 UUID 和 JSON 结构不应替代这些业务描述。

## 五、验收矩阵

| ID | 场景 | 预期 |
|---|---|---|
| AUTH-01 | 合法 RS256 外部令牌、已绑定有效员工 | 能以数据库员工权限读取本人信息 |
| AUTH-02 | 令牌使用另一发行方或错误受众 | 401 拒绝 |
| AUTH-03 | 令牌签名被篡改、alg=none | 401 拒绝 |
| AUTH-04 | 令牌过期或过早生效 | 401 拒绝 |
| AUTH-05 | 未绑定外部 subject | 403 拒绝，不能自动注册 |
| AUTH-06 | 管理员撤销外部身份绑定 | 原签名令牌不再获准访问 |
| RBAC-01 | 普通销售查看家庭核实审批 | 403 拒绝 |
| RBAC-02 | 家庭申请人与审批人相同 | 前端禁用，服务端 403，数据库触发器拒绝 |
| RBAC-03 | 未经授权直接更新家庭 verified | 数据库拒绝 |
| RBAC-04 | 独立主管批准两个真实同机构学生关系 | 仅该申请标 verified，写审批人和中文审计 |
| RBAC-05 | 已审核申请重复审批 | 新意图拒绝；原键重放返回原结果 |
| RBAC-06 | 删除或改写历史审批行 | 数据库拒绝 |
| RBAC-07 | 第二位主管驳回 | 记录 rejected，不创建已核实成员 |
| GUI-01 | 主管甲提交、切换主管乙批准 | Chromium 中文页面中完成操作 |
| GUI-02 | 销售 A/B 无法越权审查家庭 | 页面禁用，服务端再次拒绝 |
| GUI-03 | 查看家庭中文审计 | 中文申请、决定、原因和业务前后状态，非 JSON |

**验收证据边界：** 自动化 HTTP 和 Chromium 仅验证隔离虚构数据的流程，不等于真人实际核验了亲属证明或真机 GUI 验收。只有 GitHub Actions 实际运行通过且记录 SHA 后，才能将自动化场景标记 PASS。

## 六、下阶段必须处理的问题

1. **生产身份登录阻断：** 选定受信任的员工身份服务，落实 OIDC 完整登录、会话/令牌生命周期、密钥更新、紧急账号停用、账号与员工关系审批。
2. **生产数据库权限阻断：** 业务服务不能拥有无限 DDL、修改审核历史或绕过审计的高权限；迁移由独立受控账号执行。
3. **亲属关系证明阻断：** 确认机构具体需要哪些材料、谁可以查看、多久保存、撤销已核实家庭时怎么处理。
4. **多机构及字段级权限阻断：** 进一步进行所有数据表隔离/脱敏和安全审查，不能只依赖页面隐藏。
5. **真机及人工业务验收：** 真正有设备和业务授权的同事检查中文页面所有变更值，不让底层代码暴露。
6. 订单、财务、退款和 CRM 实际课时仍保持未启用，直到 BP/TP 决策、正式接口和联合验收通过。
