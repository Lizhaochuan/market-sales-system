# V3.2-27｜财务与 CRM 权威接口合同草案 + 只读拒绝执行预审

**性质：** 在独立市场销售仓库实施的 PostgreSQL 16 隔离、虚构数据安全预研。上游 V3.2-26 Draft PR #31，已验收基线 `99ac41158bdd64732962fa9b78fa1cd5fc5ac067`。不修改原 edu-management-system/CRM 技术文档、不合并、不部署，不操作真实订单、资金、课时或学生归属。

## 1. 核心边界：数据格式合格 ≠ 来源已被认证

本阶段**没有连接真实财务系统或 CRM**。只给出未来对接需要遵守的**候选数据合同**和最低验证形状，并提供只追加的候选摘要登记及显式**拒绝执行**的只读检查。因此，无论接口候选返回 `unverified_response`、`source_not_connected`、`result_unknown` 或 `disputed`，状态都不升级为“资金已确认”、“课时已调整”、“执行已完成”或“可以解除隔离”。

- 财务领域：收款原始交易、订单分配、退款、拒付/冲正，必须区分同一真实经济事件，不能双计收/退款。
- 教务领域：CRM 学生与课包身份、请求幂等、是否已经创建权益、授课/消课/排课/剩余权益及超时后的最终结果。
- 销售领域：合同主体、旧订单及 SaleEvent/佣金历史、目标学生独立确权、版本变化和三方独立审批仍受 V3.2-24—26 规则约束。
- 只有**学生为主单位、家庭按需关联**；同一联系人或同家庭不意味着有权转移其他学生的订单和款项。

## 2. 隔离合同的候选信封（版本 v3.2-27-readonly-v1）

定义在 `src/cross-module-authority-contract.mjs`，目前用于纯函数严格解析及虚构负面测试；它没有对外 HTTP 接口、后台消费、密钥或外部连接。

```json
{
  "schema_version": "v3.2-27-readonly-v1",
  "department": "finance",
  "source_kind": "finance_receipt",
  "source_system": "fictional_finance",
  "source_tenant": "fictional_org_a",
  "source_object_ref": "receipt:fictional-001",
  "source_revision": "v1",
  "reported_status": "unverified_response",
  "observed_at": "2026-11-14T05:20:00.000Z",
  "facts": {
    "currency": "CNY",
    "amount_cents": 5000,
    "original_record_ref": "order:fictional-001"
  }
}
```

模拟 CRM：
```json
{
  "schema_version": "v3.2-27-readonly-v1",
  "department": "academic",
  "source_kind": "crm_entitlement",
  "source_system": "fictional_crm",
  "source_tenant": "fictional_org_a",
  "source_object_ref": "package:fictional-001",
  "source_revision": "v1",
  "reported_status": "result_unknown",
  "observed_at": "2026-11-14T05:20:00.000Z",
  "facts": {
    "student_ref": "student:fictional-a",
    "package_ref": "package:fictional-a",
    "delivered_units": 10,
    "consumed_units": 2,
    "remaining_units": 8
  }
}
```

**解析规则：** 必须精确匹配允许的字段和版本、受信调用侧传入的部门与来源租户、来源系统允许名单，禁止多余字段或客户端自称 `verified` / `authenticated` / `execution_allowed`。财务金额须为非负安全整数、人民币分；教务数量须为非负安全整数且已消数量不得超过已提供数量。时间采用规范 UTC ISO，拒绝超期、未来及非法日期。解析输出固定所有 `source_authenticated`、`financially_reconciled`、`crm_reconciled`、`execution_allowed`、`release_allowed` 为 `false`。

对规范化候选计算 SHA-256，只能判定**本地候选字节是否一致**，**不能**证明付款权威来源、银行确认、教师实授或外部系统已经执行。数据库只登记严格字段、摘要、来源版本和**未认证状态**，不保存银行卡、身份证、儿童姓名和外部原文；候选禁止 UPDATE/DELETE。

## 3. PostgreSQL 030：仅候选、仅只读阻断

- `cross_module_untrusted_source_candidates`：以机构、manifest、对应业务范围项目、部门、类别、系统、租户、外部对象引用及来源版本登记**无权威效力的候选记录**。
- `record_cross_module_untrusted_source_candidate`：只有财务/教务的有效独立人员可以在本机构有效 `hold_active`、最新三方同版签署仍有效、已封存且本地来源未变化时登记候选。只允许受限的明确字段，来源类别与该部门清查对象匹配；相同员工防重键同内容重放返回原记录，原键变内容或相同来源/版本重复登记拒绝。
- `cross_module_readonly_authority_gate`：仅给有权查看该机构清单的员工返回中文阻断原因、局部统计和固定 `execution_allowed=false`、`release_allowed=false`。判断旧方案、未封存清单、遗漏明细、人工复核欠缺和本地指纹变化；**无论检查通过多少条，它都不能返回允许执行**。
- `scoped_cross_module_authority_candidate_counts`：按机构与有效员工身份显示财务/教务**未认证候选数量**及固定的拒绝标志，不包含外部账户、具体学生或原业务金额。
- 不增设真实收款同步、退款/冲正、CRM 写接口、补偿派发、外部回执“已验证”判定或解除销售隔离的存储过程与角色。

## 4. 将来接通真实权威系统必须先达成的独立接口协议（本期全部未接入）

| 条件 | 财务权威源 | 教务/CRM 权威源 |
|---|---|---|
| 身份与租户 | 机构金融账套/合同主体映射；受保护服务凭证，绑定真实权威来源及机构 | 机构、学生唯一 ID、外部 CRM tenant、package_id 映射，绑定正式服务身份 |
| 来源真实性 | 服务端验证来源签名、渠道身份、授权受众及有效期；不信客户端给出的 issuer/role/source | 同左；不得用家长手机或销售推断学生身份 |
| 版本与水位 | 收款、退款、拒付、分配状态及权威修订版本；必须有可查询水位/分页完成信号 | 发课请求业务幂等键、实际课包状态、排课、实上、消课、余额和可信修订水位 |
| 对账规则 | 唯一真实经济事件、金额守恒、不可双重退款/确认、跨订单合并付款用途需法律凭据 | unknown 不能视为未开课；已上课历史不删除，余量须与课包版本一致 |
| 幂等及重放 | 经济事件不可因重试双计，业务幂等键保留；按原事件引用做追加补偿 | 发课/消课不得更换幂等键重试；通过权威结果查询判定超时后是否真正执行 |
| 失败处理 | 超时、未知、冲突版本、退款争议与迟到消息维持隔离 | 结果未知、无 package_id、版本改变、课时余额冲突全部阻断 |
| 合同签字 | BP-02、BP-05、TP-03/04、合同主体/退款政策由财务及签约责任人批准 | BP-01、TP-05、CRM 权益处理/保留历史由教务与源系统负责人批准 |

**权威验收不能以 GitHub CI 通过替代。** 后续若引入正式连接，应先完成 API 级来源认证、双机构联调、有限可见字段、回执签名/信任链、重放/时钟偏移/迟到消息测试，再讨论受控补偿执行事务。真实资金与课时执行始终需要额外专用角色、审批、领域补偿命令及审计，而不是复用 029/030 的候选登记角色。

## 5. 不可变历史、并发与安全解除隔离

- 030 全部候选记录只追加，保留原始单据、SaleEvent、付款分配、退款、试课和消课历史；源修订版本变化只能追加新的未认证候选，不可覆盖旧候选。
- 未完成权威对账、真实可信执行回执、最终三部门执行后验收和 R01—R10 全部通过，**禁止解除隔离**。
- 旧误报 `release_verified` 只能用于关联本来正确且没有资金订单影响的原流程；真正错绑、有下游订单的案件保持 `hold_active`。
- 本地指纹只是已缓存事实的变化检测，不能代表外部完整账务/课时水位；不许靠静态候选哈希或人工凭据提升权威等级。
- 实际操作人必须从受保护 PostgreSQL SESSION_USER 映射，测试使用虚构的独立非所有者数据库 LOGIN；双部门同人代签、跨机构、普通销售直接调用金融读写均必须拒绝。
