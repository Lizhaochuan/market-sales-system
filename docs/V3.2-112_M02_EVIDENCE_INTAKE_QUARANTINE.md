# V3.2-112｜M02 真实责任人确认与证据接收协议（隔离实施）

## 基线和结论

基于 V3.2-111 Draft PR #118，HEAD `77cf2f6a06473e87d22d41fa6f0b7681e4a39d6b`。隔离 PostgreSQL/Node CI #43663893399 与 V3.2-100 聚合 CI #43663893339 均 `completed/success`。

V3.2-111 已建立六方责任矩阵与模拟独立签署一致性校验，但**无人被实际任命**，也没有收到可证明真实身份、组织授权、财务/教务签字权的外部证据。因此 V3.2-112 不会“确认”实际责任人：本阶段提供的是**真实材料未来进入流程前的接收协议和待核验隔离账本**。即使已接收一份材料，其唯一状态仍为 `PENDING_INDEPENDENT_VERIFICATION`，不能被当作 `APPROVED`。

## 一、六方材料接收要求

| 预期责任方 | 接收的元数据类型 | 正式升级前必须由真实第三方确认 |
|---|---|---|
| 市场销售 | 学生主键、原关联/异常、订单与 SaleEvent 历史摘要 | 学生归因责任人、原订单快照及不可改写追溯 |
| 财务 | 资金归属、收款/退款对账摘要 | 真正财务角色任命、真实账簿及独立撤权证明 |
| 教务 | 课时权益、履约对账摘要 | 真实教务签字权、课时权益原始凭证及撤权 |
| 身份安全 | 机构与人员角色、密钥生命周期及撤销摘要 | 人员与机构的可信身份来源、独立签署信任根 |
| 跨模块协调 | 版本向量、跨域屏障及不确定提交处理声明 | 三方共同认可的原子交接协议、真实回执责任人 |
| 数据库审计 | 持久水位与租户审计取证摘要 | 真实受限角色、企业数据库事务与不可篡改审计验收 |

所有岗位责任人仍为 **UNASSIGNED（未指定）**，不得将提交人自行填写的 owner_id 当成已经批准的任命。未来的外部审批须由真实组织按独立授权程序进行；不能通过提交 JSON、修改状态位或测试签名绕过真实审核。

## 二、可执行证据接收契约

新增 `src/cross-module-evidence-intake-quarantine.mjs` 的 `createIsolatedEvidenceIntakeQuarantine`，只收**测试元数据声明**，不接收原始学生姓名、联系方式、财务凭据、附件或可执行文件。字段包括：

- 机构 ID、异常 ID、**学生 ID**（主要管理单位）、家庭 ID（仅实际兄弟姐妹按需关联），提交请求 ID；
- 六个预期责任岗位之一、**未经证实**的候选负责人 ID 和提交人 ID，要求候选负责人和提交人文字标识不同；
- 来源系统、证据类型、来源修订版本与撤销序号、原业务历史 SHA-256 摘要、证据 SHA-256 摘要、可选 V3.2-110 负向通知摘要；
- 声明时间、失效时间、`claimed_approval_state=UNVERIFIED_SUBMISSION`、`fixture_only=true`。

来源类型与岗位必须严格配对；禁止额外传入 `finance_authorized`、`handoff_allowed` 或 `APPROVED` 等字段。**这里提交的所有摘要、角色和来源都是未认证的自述**；即便关联了 V3.2-110 的 SHA 摘要，也没有通过真实系统校验原始证据、签名权威或因果来源。

接收成功后的回执永远是 `BLOCKED_EVIDENCE_RECEIVED_PENDING_EXTERNAL_VERIFICATION`、`intake_recorded=true` 和 `PENDING_INDEPENDENT_VERIFICATION`；它只是接收事件的技术回执。查询接口也只能返回阻断及最新事件摘要，不生成批准操作、收款、课时变更或交接。

## 三、一次性 PostgreSQL 接收账本

在 GitHub Actions 一次性 `postgres:16`、数据库 `v106_isolated` 创建 `v106_test.evidence_intake_events` 及 `evidence_intake_heads`：

- 机构 + 异常 + **学生**复合分区，单调事件 sequence、前链事件摘要和请求 ID 去重。两个不同机构的受限角色通过 PostgreSQL FORCE RLS 隔离；角色不能更新或删除事件表，不能读写模拟付款业务表。
- `SERIALIZABLE` 事务及作用域 advisory lock 将插入事件和推进 head 放在同一次 SQL 提交中；失败整体回滚，重复、并发和乱序拒绝。
- 接收下一份材料前，必须回读上一个事件并校验其摘要与 head 相同；COMMIT 后也重新回读事件与 head 确认是否持久。若提交成功但回执丢失，只返回不确定阻断，不能假装没有提交。
- **仍存在的边界：** 测试角色可以修改可变 head（接收端会检测不一致），企业级不可抵赖审计、管理员与密钥托管独立信任根未实现。测试模式不提供文件存储、病毒检查、隐私政策/保存期限、真实审批应用界面或正式数据库迁移。

生产系统、真实业务数据、`edu-management-system`、`src/app.mjs` 和 `src/server.mjs` 不参与。临时 SQL 位于 `tests/fixtures/`，**不是迁移 039**。

## 四、自动回归与正式升级条件

`tests/integration/v3-2-112-m02-evidence-intake-quarantine.test.mjs` 提供 14 项场景：接收单条、六方全部岗位、伪造已批准、跨来源代签、家庭按需关联、同一请求重放、两个连接并发、第二份材料追加事件链、SQL 事务失败、COMMIT 后回执丢失、跨机构数据库角色、不可修改事件/业务表、账本指针篡改、失效和时钟回退。专属 CI 同时复跑 V3.2-111 的 13 项证据责任测试、V3.2-110—106 的一次性 PostgreSQL 事务回归、V3.2-105 的真实准入缺口审查及 V3.2-82—99 的 18 阶段聚合安全测试。

后续真正将一个候选负责人标记为“已被机构确认”以前，必须另行取得并**独立核验**：可确认的组织身份/责任人任命依据、签署公钥和有效期、真实权限来源、撤权事件、两人复核/责任划分、材料签名及业务真实性与完整历史对账。财务、教务与销售不可相互代签；安全与数据库人员也不得替三方作出业务决定。若任一外部来源不可访问、拒绝签字、撤权、版本回退或交易不确定，必须保持隔离。

**本阶段没有一个真实外部证据通过审核。** 16 项外部准入、R01—R10、六种独立业务权威、正式 PostgreSQL/Chromium/合同及真实三方 UAT 均未确认；合同仍 `proposed-unimplemented`。财务授权、教务授权、资金/课时补偿写入、交接及解除隔离持续为 false，`hold_active=true`。原订单、付款、SaleEvent、课时和补偿历史一律保留，不原地覆盖；学生为主单位，家庭只按实际需要关联。

继续 Draft，不合并、不部署，市场销售技术文档与既有 CRM 技术文档分别维护。**V3.2-113** 可建设“待核验材料完整性审查与独立审核人员指派”的非生产契约，但必须将真实信任根与业务交接保持硬阻断。
