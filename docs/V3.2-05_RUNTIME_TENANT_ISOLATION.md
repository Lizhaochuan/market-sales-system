# V3.2-05｜隔离服务数据库账号分权与机构数据行级隔离

**仓库：** market-sales-system（市场销售系统独立开发）  
**前置版本：** V3.2-04 PR #8，以及其所依赖的 #7、#6、#5、#4。  
**交付范围：** 独立 PostgreSQL 16 测试库、Node 22 HTTP 服务和虚构机构/员工。  
**结论边界：** 本阶段是**生产身份与数据安全的准备性验证**，不是生产身份供应商集成，不是正式 CRM 数据库改造，也不代表多租户安全已完成。

## 一、本阶段的实际目标

V3.2-04 已创建受限数据库角色 `ms_lowrisk_runtime`，但原业务 HTTP 测试仍由具有表所有权的测试账户运行。这不足以证明普通业务服务器在真实低权限数据库连接下可运行。V3.2-05 首次补充非所有者 LOGIN，在该账号下实际发送 HTTP 请求、数据库写入与读取，并测试组织 A 与组织 B 无法从业务服务相互查看核心学生。

## 二、数据库权限实际设计

### 009 号隔离迁移

- `db/migrations/009_isolated_tenant_rls.sql`：第一批行级安全策略，指定已授权的 `ms_lowrisk_runtime` 角色和业务机构编号；同时修订 V3.2-04 身份绑定约束，使 **继承低风险角色的 LOGIN** 不能通过不同的 `current_user` 名称绕开独立审批。
- `tests/sql/create_isolated_runtime_login.sql`：仅 CI 使用，为虚构测试库创建 `ms_isolated_api` 非所有者 LOGIN，口令来自测试环境变量；**不得当作正式员工或数据库生产凭据**。
- `src/runtime-preflight.mjs`：受限账号启动安全闸；正式生产服务认证仍未实现。
- `src/app.mjs`：验证员工身份与所属机构后，在数据库事务范围内写入机构上下文。绝不从用户提交的 `organization_id` 或未验证令牌字段直接接受租户编号。
- `tests/security/isolated-login-tenant-rls.test.mjs`：真实非所有者连接、双机构隔离、RLS 拒绝跨机构写入、事务结束清除机构上下文、禁止财务及未经授权的身份绑定。
- `.github/workflows/v3-2-core-api.yml`：完整迁移至 009；使用 PostgreSQL 16 测试实际 LOGIN；继续执行此前所有后端、浏览器、身份治理和合同回归。

### 关键安全限制：普通自定义 GUC 不是绝对租户边界

PostgreSQL 的普通自定义会话参数 `ms.tenant_org` 可以被具有 SQL 执行能力的数据库角色自行修改。因此当前 RLS 策略是**防误查和保护参数化业务 API 的纵深防御**，不能单凭此作为已遭数据库凭据泄漏或任意 SQL 执行后的强隔离安全保证。

正式多租户部署必须另行设计受控且不可由普通运行账号伪造的租户上下文、完整关系表行级政策、角色和函数 `SECURITY DEFINER` 审计、连接池重置行为、数据库账号轮换与备份恢复。该风险视为**生产上线 P0 阻断项**，不可因 CI 全绿而关闭。

此外，低风险业务 LOGIN 仍然可能从有 SELECT 权限但**尚未加 RLS 的间接关联表**读到数据，尤其是家庭成员关系及学生-联系人关联；本版本只在列明的第一批核心表实现策略，**不是全库防泄漏声明**。实际数据库使用者不得取得任意 SQL 访问能力。

## 三、正式身份供应商接入仍未开始

此前已实现的 RS256 令牌验签与员工身份映射只是服务端的信任适配器。要让员工真正登录，还必须由项目负责人正式决定身份供应商、企业账号发放和离职收回管理，实施 Authorization Code + PKCE、OAuth/OIDC 标准状态参数和回调 CSRF 保护、MFA 策略、可信 JWKS 获取及轮换、员工映射审批，并在正式环境实际演练账号停用与异常处理。

没有得到这些条件和生产安全审查前，服务继续强制 `MS_STAGE=isolated-test` 和本机 `127.0.0.1`，不能发布至公开域名。

## 四、验收证据要求

| 编号 | 隔离测试场景 | 预期 |
|---|---|---|
| RLS-01 | 非所有者 LOGIN 运行 | 非超级用户、非 BYPASSRLS、无法建表、不能读财务 |
| RLS-02 | 数据库管理员用作受限运行账号 | 启动前权限检查拒绝 |
| RLS-03 | 没有设置机构事务上下文 | 读取学生应返回零行 |
| RLS-04 | 机构 A 创建学生、联系人 | 成功；A 查询可见 |
| RLS-05 | 机构 B 独立登录创建学生 | 成功；不能看到 A 的学生 |
| RLS-06 | A 查询 B 的学生 | 不返回 B 的资料 |
| RLS-07 | A 上下文直接写入 B 机构学生 | PostgreSQL 行级策略拒绝 |
| RLS-08 | 同一连接池完成事务后读取 | 不能继承上一次机构范围 |
| RLS-09 | 非所有者修改员工角色、读取正式订单或绕过外部身份审批 | 拒绝 |
| REG-01 | 既有学生/联系人/线索/商机、主管审批 | HTTP 和数据库合同回归保持通过 |
| REG-02 | 中文网页与窄屏交互 | 真实 Chromium 自动化回归 |

**测试级别区别：** 后端 HTTP + PostgreSQL、Chromium 自动化 GUI、真人操作与生产安全审查必须分别记录。当前版本仍缺真人、真机及正式跨系统业务验收。

## 五、下阶段 V3.2-06 的优先方向

1. 设计数据库不可伪造的机构信任边界并完成子表 RLS 覆盖测试、权限审查和安全复核。
2. 将业务服务运行时真正改用独立低权限账号完成**所有**写接口，而不只是当前测试用例；检查事务和连接池异常清理。
3. 明确正式员工身份供应商及配置责任，落实登录生命周期与绑定人的双人审核。
4. 建立家庭关系已核实后的拆分/撤销规则、隐私保护与完整中文审计。
5. 真实 CRM 课程价格、试听、收款与课时等高风险接口继续关闭，不触发自动成交或开通权益。

## 六、项目独立原则

所有新提交必须以当前 Git SHA 对应的实际 GitHub Actions 为证；**没有通过的日志，不得标记为完成**。
