# V3.2-31｜真实财务 / CRM 联调前的最终准入阻断清单

**性质：真实联调前的准入条件核查与虚构证据缺口登记；尚非真实来源认证、生产业务审批或联调。**

**上游基线：** V3.2-30 Draft PR #35；经 CI 验证 SHA `195873907b6892010c9aec29079ca249a9a5776e`。只影响独立市场销售系统，不修改原 CRM（edu-management-system）或其技术文档。所有新增对象仍使用虚构测试来源和隔离数据库。

## 一、核心结论

V3.2-29 的两人 `fixture_ready` 只表示虚构来源材料完成了两项模拟检查；V3.2-30 的来源异常复核只表示模拟工作人员登记了故障。以上任何测试及 GitHub CI 通过都不能替代真实财务、CRM 系统所有人和信息安全负责人正式批准。

因此 V3.2-31 的读取函数和投影，**始终固定**：
- `production_integration_allowed=false`：不能进行真实只读 API 联调；
- `execution_allowed=false`：不能修改学生、原订单、收款归属或 CRM 课时；
- `release_allowed=false`：真正错绑且已产生下游业务的案件不能解除隔离。

本阶段没有任何可以将上述状态改成 `true` 的接口、字段、角色、事件或迁移。

## 二、必须由哪些部门提供证据

新迁移 `034_preintegration_authority_hard_gates.sql` 定义 16 项不可覆盖的准入检查。

| 部门 | 必须解决的事项 | 实际责任归属 |
|---|---|---|
| 销售（3 项） | 合同签约主体/正确学生、销售归因/佣金历史调整政策、跨模块最终隔离验收 | 销售业务负责人，合同相关事项另须签约责任人确认 |
| 财务（4 项） | 财务权威系统负责人、机构账套/订单资金用途、最小只读服务权限、经济事件和退款对账 | 财务负责人及真实支付系统所有人 |
| 教务（4 项） | CRM 权威负责人、机构/学生/课包映射、最小只读服务权限、实授/消课/余额权威对账 | 教务负责人及 CRM 系统所有人 |
| 信息安全（5 项） | 来源身份/签名信任、持久防重放、完整水位与分页、异常恢复机制、跨机构独立验收 | 信息安全负责人，并与财务教务各自联审 |

资金权威的确认必须涵盖实际收款、退款、拒付、分配、同一款项为多学生支付等。教务权威必须涵盖已上课程不可删除、结果未知不得再次发课、剩余权益与原课包版本一致。一个家庭有多个孩子，不自动把孩子合并为一个客户单位；学生是主要管理单位，家庭仅在真实有需要时关联。

## 三、本阶段新增的不可变审计与访问边界

- `ms.integration_required_checks`：只读的 16 项责任清单；每项 `production_verified=false` 由数据库 CHECK 强制固定。
- `ms.integration_missing_evidence_events`：只能追加一项**仍然缺失**的证据。可记录未确认负责人、政策未获批、权威来源不可用、租户未核实、无只读凭证、未建立可信签名、水位未知、财务/教务未对账、验收未执行、恢复机制未批准等。**不允许登记“已通过”**。
- `ms.record_integration_missing_evidence`：根据 PostgreSQL 登录身份的机构、有效职务和来源领域进行限制。财务审核人不能替教务/安全填写；销售只能确认销售事项；信息安全人员只能确认安全事项。
- `ms.readonly_integration_hard_gate`：按申请分别给出 12 个适用关口、中文要求、未获证据数量和永久阻断结论。不会返回真实银行卡、儿童身份、合同原文、财务账号或访问密钥。
- `ms.scoped_integration_readiness_summary`：提供本机构必要范围内的最小只读概况。其他机构不允许访问。
- 原始准入清单和缺失事件禁止 UPDATE/DELETE，防重复操作键同内容幂等、异内容拒绝；新版本不得回填或覆盖旧审批历史。
- 新增 `ms_integration_gap_writer` / `ms_integration_gap_reader` 只具有受限函数及概况视图的权限；既有低风险写入账号不获得新权限，也不能查询原始清单或修改资金/CRM 记录。

### 必须说明的技术边界

这不是“将审批变为自动完成”。本阶段的持久记录只能指出**尚未解决**的证据。未来如取得真实授权，必须设计**新的、独立验证且可撤销的权威审批机制**，而不是通过手动修改本阶段的 CHECK、补填备注或直接把 12 个清单项目勾选为完成。

## 四、模拟验收场景

1. 一个财务来源申请，即使 V3.2-29 的领域和安全两次 `fixture_ready` 都存在，真实联调仍阻断。
2. 学生合同/销售责任人、财务、教务、信息安全分别只能记录自己部门的缺失证据。
3. 机构 B 无权读取、登记机构 A 的来源准入缺失；原申请人不得伪造其他人身份。
4. 同键同内容重复提交返回原记录；同键不同内容报错。旧事件和 16 项静态清单无法 UPDATE/DELETE。
5. 直接插入 `production_verified=true` 或其他“已批准”数据被数据库拒绝。
6. 即使缺失证据记录数量为零，也**不代表真实条件已经满足**；`production_integration_allowed` 永远 `false`。
7. 已有实际订单/资金/课时的错绑案件继续 `hold_active`，旧 V3.2-23 误报解除规则不受本期准入表影响。
8. 原 PostgreSQL 001—033、所有 Node 安全/业务、既有 Chromium 中文页面和 V3.1 设计合同继续回归。

## 五、正式联调前必须由人工提供什么

需要实际财务和 CRM 两边的**独立责任人**提供正式签署的接口负责人、最小权限只读账号申请流程和准入环境说明；信息安全提供可信来源证书/受众/密钥撤销、持久防重放及审计保留方案；销售与签约责任人确认错误学生关联、历史合同和退款处理政策。

在收到这些真实材料前，可继续推进纯模拟的权限撤销、来源故障恢复演练及正式 UAT 用例说明；不可以把虚构 API 或 CI 成功当作生产资格。不要在仓库填写真实 API key、真实财务地址、私人银行凭据、儿童姓名或监护人隐私数据。

## 六、交付及下一步

本阶段验收应以最新 Draft PR HEAD 的 PostgreSQL **001—034**、真实受限数据库登录、16 项跨部门权限负例、Node 全量、Chromium 旧中文页面及 V3.1 合同回归日志为准。**不包含本阶段的新 UI 页面**；旧页面通过只是回归证据。

后续建议 V3.2-32 优先建设**业务负责人可直接阅读的联调阻断报告与 UAT 操作手册**，输出逐项签署清单、待提交证据、失败截图要求和跨部门验收模板；仍不放开真实连接、资金、课时或隔离解除。
