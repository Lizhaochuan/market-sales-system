# V3.2-18 | 正式线索转换预审、跨员工归因争议与审计撤销

**技术文档单独维护，独立仓库，仅虚构 PostgreSQL 16 / 本机严格员工身份测试。** 依赖未合并 Draft PR #21。本版本不进入旧教培 CRM、不接真实身份和业务、更不开放正式 `ms.leads` 写入权限；联合最终验收通过后才评估融合。

## 核心原则

* “一次实际咨询”是唯一业务事件单位。关联同一联系人、家庭或多名学生，均不自动创造多条咨询、线索或销售归因。学生是主要管理单位，家庭仅按需关联。
* “候选核查通过”只表示候选可信，不代表“可转换”。“转换预审通过”也**不是正式销售线索**，不能变更联系人管理权、既有咨询记录人、学生负责人、历史商机、合同、订单、财务和课时。
* 不得从同一联系电话或同一联系人推断多个学生是同一家庭；未核实学生关系、已拒绝联系、重复正式线索、机构冲突、归因冲突均不得悄悄转化。
* 当前权利必须在提交和审核两个数据库事务中分别重新检查；已审批状态随后失效时，读取 `effective_status` 会动态告警，绝不能缓存成永久的“可转化”凭证。

## 一、转换预审（非正式转换）

1. 只能由先前已独立审核通过的候选申请人提交 `conversion-readiness`。同时检查本人当前仍是该联系人管理人、拒联状态和现存正式线索。一个候选仅一次申请；相同幂等编号重放返回原记录，不允许新证据冒用旧编号。
2. 有效本机构独立主管（非申请人）复核，可选“预审条件通过，但仍不生成线索”或“驳回”。要通过时，数据库重新检查联系人当前管理权、拒联、同联系人正式线索去重，并逐条核查由其他员工记录的该联系人咨询是否**已经独立裁决为异议被驳回**。尚有待审异议、支持异议、未经核实的跨员工事件一律拒绝通过。
3. 所有预审决定追加不可改写记录。原申请人不得自批。读接口按专属数据库员工身份投影本人或当前有效主管待审记录，不暴露证据正文与学生敏感资料。
4. 如主管发现此前通过的预审有问题，可通过 `revoke` 撤销**预审许可**；记录新的不可更改撤销事件，不修改以前的通过证据。它不代表撤销实际线索，因为本版本根本不创建正式线索。旧状态保留以供追责。
5. 如果通过后联系人转交、客户拒联、出现新的正式线索或新的跨员工真实咨询，`effective_status` 动态显示“已失效，必须重新审核”。即使页面上显示历史审批通过，也没有任何正式转换 API/数据库授权会消耗它。

## 二、跨员工咨询归因争议

* 员工可以仅在自己确实登记过**同一联系人**的另一笔咨询事件时，对其他员工已通过候选审核的候选提出争议。本人不能争议自己的候选，亦不能引用他人、别的联系人或其他机构的咨询。
* 可发现列表仅暴露候选标识、联系人称呼、自己的咨询 ID 与咨询方式；普通员工不能读取原申请人完整证据、对方学生档案或其他机构信息。
* 有效独立主管裁决“支持异议”或“驳回异议”，不能由争议申请人或候选申请人审批，不能直接转交负责人、自动生成新线索或重写原咨询记录人。
* 如果异议成立，该候选的原归因预审不能通过；如果被驳回，仅表示允许继续进行独立转换预审，不代表已经给原申请人发放业绩。
* 已裁决争议不可篡改；拒绝依靠重复提交来冲掉原判断。本阶段不实现“分成”“自动归因判定”“投诉复议改判”或正式责任转移，这些均需后续独立规则与授权。

## 三、授权矩阵（数据库层）

| 行为 | 自己的有效员工 DB 登录 | 当事人/其他员工 | 独立有效主管 |
|---|---|---|---|
| 查看本人符合条件候选 / 预审 | 只读最小列 | 无此资格 | 仅待处理及本人已复核 |
| 申请转换预审 | 候选申请人、当前联系人管理人 | 禁止 | 不代申请 |
| 用本人咨询提出跨员工争议 | 确有历史独立事件才可 | 不能伪造别人的咨询 | 不代申请 |
| 审核本人预审 / 自己的归因争议 | 禁止 | 禁止 | 本机构独立审核（不能是争议双方） |
| 归因争议记录的证据、决定原表 | 无 SELECT / UPDATE / DELETE | 无 SELECT / UPDATE / DELETE | 也没有原表授权，只能经最小函数 |
| 撤销已通过预审 | 禁止 | 禁止 | 有效主管、追加不可变新决定 |
| 正式销售线索创建 / 修改 | **关闭** | **关闭** | **关闭** |
| 学生、兄弟姐妹、家庭、收款、课时 | 不因预审授权 | 不因争议授权 | 不因审核授权 |

数据库真实执行主体与组织由受保护的 `SESSION_USER` 映射，不相信客户端提交的组织、角色或负责人。写操作仅授予 `ms_scoped_lowrisk_writer` 对五个限定 `SECURITY DEFINER` 函数的 EXECUTE；不给员工原始表 DML；真实合同、财务、教务仍完全隔离。

## 四、交付物

* `db/migrations/022_conversion_preflight_and_attribution_dispute.sql`：预审/争议/不可改写决定四表、三项最小只读视图、五个受限函数、中文审计。
* `src/app.mjs`：受控员工接口 `GET/POST /api/v1/conversion-readiness`、`/decision`、`/revoke`、`GET/POST /api/v1/attribution-disputes`、`/eligible`、`/decision`。
* `src/scoped-legacy-read-adapter.mjs` 与 `src/scoped-legacy-write-adapter.mjs`：专属员工账户强制匹配、白名单字段、幂等请求、严禁广域 SQL 回退。
* `web/index.html` / `web/app.js`：全部中文业务文字与清晰的“预审非正式转换”说明。
* `tests/security/conversion-preflight-attribution.test.mjs`：真实员工数据库账号的无原表访问、跨员工归因挑战、管理人交接、幂等、防自批、争议成立阻止归因、动态失效、撤销不可变与正式线索零写入。
* `tests/browser/contact-custody.spec.mjs`：真实 Chromium 从咨询候选到跨员工争议、独立裁决、转换预审和撤销全过程。

## 五、后续条件

本阶段仅设计并实操**转换条件复核**，不执行真正的 `ms.leads` INSERT。正式转化需要以后另外实现专属函数、额外一层业务授权、客户意愿和重复性实时核验、双重主管责任链、失败回滚、历史归因争议再裁决与财务教务跨模块验收。

最新 GitHub Actions 对 **本 PR 最新 HEAD** 必须验证 PostgreSQL 001—022、非所有者登录双机构隔离、所有 Node/安全/业务回归、Chromium 真实中文界面、V3.1 合同回归；有失败必须保留 Draft、不宣布完成。
