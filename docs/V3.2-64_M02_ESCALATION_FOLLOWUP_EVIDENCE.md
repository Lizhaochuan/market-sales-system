# V3.2-64｜M02 人工升级后的证据补充、销售/财务交接边界与持续阻断

> 基线 V3.2-63 PR #70 HEAD `65573d350dc5cc50150a2e1ebdff9b5fead94d06`；GitHub Actions #43614602899 completed/success。依然仅为虚构 PostgreSQL 隔离环境。

## 业务及审批责任

- **销售原报告人**：只能在本人报告的、已经由独立销售主管人工升级为 `manual_escalated` 的异常下，追加虚构佐证材料索引与中文原因。不得修改原报告、审核结论、活动、预算或历史。
- **独立销售复核人**：原事件中 `reviewed_by` 且仍拥有有效本机构销售主管角色时，才能追加独立销售侧核验或“仍需外部财务授权”的提示。其职责仅止于销售侧核查，不代表财务确认。
- **财务部门**：真实受理人、签名身份、待办确认、预算审批、付款、成本分摊和实际投放权限尚**没有接入**。所谓 `external_finance_requirements_pending` 仅是内部准备资料标签，不是已送达财务。
- **教务与跨模块**：不改变学生、订单、支付、SaleEvent、课时或跨模块责任。错误学生关联存在下游订单/收退款/履约时继续 `hold_active`，保留原始记录。

## 隔离实现与验证

- 新建 `ms.isolated_campaign_finance_escalation_followups` 追加型记录表，写入仅允许已审核 RS256 员工签名+专属函数写入数据库账号。数据库身份决定销售报告人/独立审核人角色；不接受客户端自报角色，禁止其他主管、其他机构或失效身份追加。
- 仅 `manual_escalated` 可追加；每次保存需有限的 `note_type`、2–200 字符证据索引、2–400 字符中文说明与防重复编号。相同键与正文只能返回原始记录；改正文会冲突；重试不能生成额外审计。
- 严格员工 `GET /api/v1/marketing-campaigns/finance-incidents/follow-ups` 最多 100 条，返回记录 ID、相关事件 ID、提交角色、标签、时间、当前持续阻断状态，不返回底层证据、说明、请求键或审计 JSON；读失败时清空旧数据。
- `POST /api/v1/marketing-campaigns/finance-incidents/{incident_id}/follow-ups` 仅追加，不具有批准、驳回、解除、发布、授权资金等动作。
- V3.2-63 时间线新加 `CAMPAIGN_FINANCE_ESCALATION_FOLLOWUP_RECORDED` 事件；原登记、升级和佐证核查结束的历史状态完整保留。此事件的历史状态固定 `manual_escalated`。
- 经由 PostgreSQL/HTTP、浏览器和静态合同验证：不得由原报告人自行升级；外部财务身份未配置；新增证据后 `readiness_status` 仍然是 `blocked_active_incident`，即便原快照恢复正常。
- 最终正式迁移仍 **001—038**，没有 039。市场销售模块技术文档独立保存，未经 CRM 跨模块验收不融合。
