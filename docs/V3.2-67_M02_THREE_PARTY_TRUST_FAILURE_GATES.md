# V3.2-67｜M02 三方签名证据可信验证规则、失效处理与补偿边界

> 基线 V3.2-66 Draft PR #73 HEAD `8ece89a955038acd94d674edf57b724dd5a0e0ce`，Actions #43617160948 completed/success。此阶段仍仅虚构隔离 PostgreSQL/Node/Chromium，不存在真实财务、教务信任链，也不执行数字签名验真。

## 未来必须逐项满足的可信验证规则

销售、财务、教务三方各自对**同一机构、同一学生及业务范围、同一冻结快照/证据摘要/版本**出具明确签署。正式联调必须事先在外部权威系统中核准可信颁发方、受众/用途、签名算法、key ID 与钥匙轮换、员工组织映射、职责分离及审批权限。对三方每一签署，须由真实验证器验证签名覆盖的不可改写规范序列化消息、签名时间、机构、证据摘要及不可重用 request_nonce；检查凭据撤销、过期、重放、乱序、跨机构、跨版本以及相同人员的自审。绝不可相信客户端提供的 `verified=true` 或 `accepted` 文本，不能仅凭 schema 校验得到“已验证”结论。

**当前证据草案 V3.2-66 缺失独立签名字节、真实 key ID、撤销列表及权威验签服务**，因此即便声称三个 accepted，运行时也必须继续拒绝。本阶段只提供结构/矛盾预检查与只读阻断信息，非真正验签；具体的生产算法、有效期、时钟容差及信任端配置必须由三方审批后才能确定。

## 失败分类与隔离规则

- 销售包不完整：`blocked_sales_packet_incomplete`，不能发出跨模块验收申请。
- 销售包齐全，但缺失外部财务可信颁发者/签名验证/撤销及重放登记：`blocked_external_finance_trust_chain_unavailable`。**绝不因形式齐全推导授权已生效。**
- 将来若有签名无效、已撤销、过期、旧版数据、重复请求、审批人角色冲突或财务拒绝，应记为可审计的拒绝/补正事件；保留原始证据与指向的摘要，保持 `hold_active`；不重试高风险写入、不得复用已使用的防重复编号，也不得用直接 UPDATE 替代纠错事件。
- 任何财务/教务交接超时、未知处理结果、异步重复通知都视为状态**未知/阻断**，不得当作成功；之后需通过权威只读状态查询+独立审核确认。没有完成正式接口联调前，不能自动发补偿。

## 失败补偿及跨模块责任边界

- **销售**负责追加材料、记录失败原因和时间线，不得撤销财务或教务原始事实。
- **财务**对真实订单、收付款、退款和成本的冲正负责；授权后只通过不可改写的补偿事件/对账凭据调整派生余额，不改原始支付、订单和历史。
- **教务**对学生归属、排课和实际消课进行独立核验；涉及错绑但已有履约/订单/收退款的，必须保留 `hold_active`，补偿只可采用带来源与签名的增量事件，不可覆盖原始上课记录。
- **三方共同验收**至少确认版本一致、证据来源一致、原始记录保全、两个以上独立职责、拒绝/重放/超时的最终权威状态、补偿链完整且财务及教务签署有效。核验条件未全满足，`release_eligible=false`。

当前只读 `ms.scoped_isolated_campaign_cross_module_trust_failure_gates` 及 `GET /api/v1/marketing-campaigns/finance-incidents/trust-failure-gates` 仅返回本人/已授权机构范围的两类拒绝、`failure_disposition=reject_preserve_originals_escalate_manually`，并显式标记**验签、撤销检查、重放检查、快照绑定、财务/教务接收、补偿写入和原记录改写均不可用**。受限读数据库最大 100 条，出错清空旧记录，工作台显示始终阻断。新增 `src/cross-module-signature-preflight.mjs` 为离线纯函数，只筛出结构矛盾，**无可信密钥或授权结果，不提供任何 release 成功分支**。
