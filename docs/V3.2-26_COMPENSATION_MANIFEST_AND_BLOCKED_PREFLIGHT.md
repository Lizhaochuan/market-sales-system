# V3.2-26｜跨模块补偿清单、外部对账人工引用及禁止执行预审

**交付性质：独立市场销售系统中的 PostgreSQL16 隔离实现草稿；不属于实际跨系统纠错执行。**
**上游：** V3.2-25 Draft PR #30（最新已验收基线 `9fad3f50bfd77bb7ede427424e93bd846f04224c`）。只新增市场销售独立仓库文件，不修改 edu-management-system 与旧 CRM 技术文档。

## 一、核心结论

V3.2-25 三方不同自然人批准正确学生关联的**拟议方案**后，本期可生成“不可改写的补偿范围清单”并登记销售、财务、教务预期处理方式，要求每个原始关联对象都有明确的拟议动作或人工复核结论。

但是：**正式财务权威、合同更正方案、外部付款冲正、CRM 权益回执、已上课时、真实执行人员授权均未在本阶段打通**。因此，本期新增的“预审结论”在数据库层面**永远为阻断**，不存在实际执行授权、原始归属改写、发课或解除隔离的数据库函数。

## 二、新增数据对象（migration 029）

| 表 | 作用 | 改写权限 |
|---|---|---|
| `cross_module_compensation_manifests` | 绑定 V3.2-25 最新三方已批准方案、指定原错误学生与目标学生；保存当时影响计数和本地关联摘要指纹 | 只追加、禁止改写 |
| `cross_module_compensation_scope` | 自动列举原线索—学生关联实际涉及的本地业务记录；保留每条对象类型和原始 ID | 只追加，禁止修改或删除 |
| `cross_module_compensation_items` | 每个清查对象只允许一条拟议处理：继续保留待核、合同/业绩核对、财务冲正/退款评估、课时/实上核对等 | 只追加，禁止 UPDATE/DELETE |
| `cross_module_compensation_seals` | 原申请人逐条填完整份清单后封存；封存再次核对本地对象指纹 | 只追加，禁止重复封存 |
| `cross_module_external_evidence_notes` | 财务、教务不同人员分别记录**未接通/人工参考/结果未知**的外部证据说明 | 只追加；不接受“已执行”“到账属实”“课包已调整”等确认值 |
| `cross_module_execution_preflight_blocks` | 第三位未参与前序审核的销售主管留存**禁止执行的预审结论** | 数据库 CHECK 固定 `blocked_external_authority`；`execution_allowed=false` 与 `release_allowed=false` |
| 两个受限视图 | 呈现清单总体状态与分条清查范围 | 员工仅可读本机构必要对象和中文说明，无原始银行金额或敏感身份 |

用户界面如展示：
- “待登记补偿明细”——仅有清单范围，未完成逐项说明。
- “补偿方案清单已封存”——仅本地拟议清单齐备，不代表已经补偿。
- “财务外部证据：人工参考，未获得权威核对结果。”
- “教务 CRM 权益：结果未知，不得重复发课。”
- “独立预审已记录：暂不允许执行、更换学生订单、变更资金或解除隔离。”

## 三、自动清查的本地范围

### 销售
原学生与该条正式线索对应的商机、报价和报价明细、折扣审核、订单与订单明细、首次成交、销售业绩及其审批版本。

### 财务
已关联上述订单的收款分配和收款投影、退款分配及退款事实、分配历史及外部经济事件链接。**含其他学生共用同一笔付款时只记录本案关联到的财务凭据，不因此授予其他孩子档案读取权。**

### 教务
原商机试听预约与反馈、订单明细对应的 CRM 权益映射。**本地无记录 != CRM 确认未发课。** 如果某部门本地无对应关联记录，则自动生成“本地暂无关联记录、外部仍须核对”的独立检查项，避免无记录被误认为已经核实成功。

本地指纹取有关对象 ID、数量、订单状态和版本、现有收退款分配状态与部分来源版本、CRM 权益回执状态；封存和最终预审前必须重新比较。其作用是**发现本地资料发生变化并阻止复用旧清单**，不是外部银行余额、课程剩余课时或实际履约的权威证明。数据库字段未覆盖的变化或外部尚未同步的事实，仍须依赖后续真实权威核对。

## 四、流程与权限

1. 原申请人处于 V3.2-23 确认 `wrong_student_confirmed` 且 `escalate_manual` 的有效 `hold_active` 案件；V3.2-25 同一最新版已经由销售/财务/教务三位不同自然人全部批准、资格未撤销；本地影响数量仍与批准时一致。此后才允许申请新的补偿清单。
2. 数据库自动列举可枚举本地关联记录；原申请人对每一项记录补充拟议动作和人工凭据，不能任意指定其他学生、其他机构或其他订单 ID。
3. 必须逐项覆盖且本地指纹未变化才可封存。封存后禁止在旧清单追加、覆盖或删除；需要修订必须另建新方案版本，重新三方审核。
4. 财务和教务分别使用已经建立的专属、受限真实 PostgreSQL LOGIN 登记人工证据/外部结果未知。两个部门不能互签，任何人不能同时充当两边的审核人。**这些不是接通支付平台/CRM 的正式外部接口，不允许填“权威已确认执行”。**
5. 第三位独立销售主管在最新计划、完整本地清单、三方资质仍有效、两个部门人工说明已留存、指纹未变化时，可追加一条**被外部权威阻断的预审记录**。该主管必须与案件申请人、原隔离审核人、V3.2-23 双主管以及 V3.2-25 销售计划签署人不同。
6. 数据库强制 `external_finance_verified=false`、`external_academic_verified=false`、`execution_allowed=false`、`release_allowed=false`。原 `hold_active` 不改变，原订单学生、财务事实与 CRM 权益均不自动变动。

新增函数都仅授予专门的 `ms_cross_module_plan_writer`；执行人员仍由受保护 `SESSION_USER` 关联机构与真实员工身份。原销售低风险角色不增加新审批能力；新项目员工仍不能直接 SELECT 或 UPDATE 财务、订单、合同和教务业务表。

## 五、并发、幂等和变更失效

- 方案、清单、每条拟议补偿、封存、部门人工备注和阻断预审分别有防重复编号。同员工同编号同内容重放返回原记录；同编号不同内容拒绝。
- 新版本方案、学生关系/订单版本、付款分配、退款等本地影响新增或变化，均须重新核查；本地指纹不一致则封存/预审拒绝。
- 新的财务/教务权威事实可能迟到，且旧范围快照可能不反映全部实时外部余额。**不能因为旧预审记录存在就永久视为最新**，不得通过刷新页面把旧阻断状态展示成已经成功补偿。
- 一份补偿清单只对应一个指定学生的错绑案件。一个家庭中其他孩子不会自动合并、变更其合同或课时。
- 数据库 owner/部署维护角色不属于普通员工角色的保护范畴，真实运维需另行分权、备份、日志和最终集成审计。

2. Node 逐条补偿、重复编号、跨部门／跨机构、第三独立主管、晚到资金变更、不可变历史测试通过；
3. 原 V3.2-23 双主管释放误报回归、V3.2-25 三方批准回归和其它 Node 全量检查通过；
4. Chromium 中文旧页面业务回归和 V3.1 既有合同回归通过；V3.2-26 新的正式业务页面**尚未实现**，旧 Chromium 通过不能表示它有正式操作页面；
5. 以上任何失败均需修复并对最新 HEAD 重测，未通过前不得声明完成。

## 七、尚未打开的实际纠错能力

当前不含真实财务对账服务、业务资金冲正、订单更正、合同作废、新课包开通、教学权益调整、对账成功回执、解除隔离函数或生产部署。V3.2-26 的“预审”只是**禁止执行的检查结果**。正式的执行授权与真实的财务/CRM 权威确认必须在未来独立版本中实现，并须先解决 BP-01、BP-02、BP-05、BP-06、TP-03/04/05/07/08 与合同法务政策，不得凭模拟审批自动授权实操。
