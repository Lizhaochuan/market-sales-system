# V3.2-08｜员工身份审批实时路由与同机构学生权限隔离

**状态：独立、隔离测试候选；并非正式员工登录或生产级 CRM 系统。**  
**代码仓库**：Lizhaochuan/market-sales-system；以前一阶段 V3.2-07 PR #11 为基线。  
**项目要求**：学生为基本管理单位；家长、家庭按核实后关联；真正的财务收款、退款、成交事件与 CRM 教学权益均保持关闭。旧教培 CRM 仓库的代码和技术文档不得提前融合。

## 一、本阶段解决的两个实际问题

**问题一：身份审批结果与路由登记不同步。** V3.2-07 的网关使用由管理员预先录入的静态 `issuer + subject → 上游地址` 清单。即使数据库中的身份绑定已批准，网关仍可能因为清单未更新而拒绝；反过来，静态映射已撤销但还没刷新，也会产生管理差异。

**本阶段**新增受控的数据库只读路由目录，以数据库中的**真实、有效、已经通过两人审批**的身份绑定决定机构，再依据管理员预设的 **机构 ID → 本机机构服务地址** 选择独立数据库连接池。它每次请求重新查询，不缓存已撤销的身份。

**问题二：同一机构内的业务数据库角色仍能查询过多基础字段。** 仅有机构行级限制不等于每名员工只能查询自己的学生。本阶段新增单独的员工专属数据库登录身份和只读视图，让销售 A 与销售 B 在同一机构内也拥有不同学生访问范围。

## 二、交付内容与安全边界

## 三、可信身份路由的批准依据

一枚 JWT **只有真实 RSA 签名、正确 issuer、audience、subject 和有效时间**，才可能进入下一步。路由目录仅在以下条件同时成立时返回机构编号：

1. 外部 `issuer + subject` 与当前有效身份绑定完全相同，且没有被撤销。
2. 绑定的目标员工属于有效机构，且该员工状态为启用。
3. 对应身份变更申请 `action=bind`、`status=approved`，且审批人和申请人及目标员工均不同。
4. 独立审批决定记录与申请一致，决定为批准。
5. 真实机构 ID 仅用于从已经配置好的机构服务列表选择本机目的地。客户端的 Host、URL、`org_id`、角色声明与 Cookie 不能增加机构权限。

若尚未审核、明确驳回、员工已停用、绑定已撤销、审批信息不匹配、未在目的地白名单内，网关全部拒绝；**绝不能默认选择第一家机构**。

机构后端仍独立执行令牌签名核验、有效员工绑定验证、数据库真实 `session_user` 所属机构行级保护。即使可信路由配置错误，也不能跨机构直接查看学生档案。

**测试数据说明**：用管理员测试账号生成且符合原有审核触发器的申请、不同主管审核事实、绑定/撤销状态。测试可以证明数据库只读目录按照审批结果实时变化，不能代替真实人事部门查看原件、身份供应商签约或正式双人审批培训。

## 四、同机构两名销售的最小可见字段

测试中的销售 A 和销售 B 属于同一个机构，但使用不同的受限 PostgreSQL 登录身份。受保护映射表 `database_principal_staff` 由迁移管理员维护，而非通过客户端可写的会话参数决定员工。

| 场景 | 数据库应返回 |
|---|---|
| 销售 A 查看专属学生 A | 学生 A 的编号、姓名、机构 |
| 销售 A 查看销售 B 未共享的学生 B | 不显示 |
| 销售 B 查看自己负责的学生 B | 学生 B 的编号、姓名、机构 |
| 为 B 明确授权查看学生 A | B 在视图中新增可见学生 A |
| 撤销 B 对学生 A 的授权 | B 立即无法再看到学生 A |
| B 试图读取学生 A 的年级、基础表、家长联系资料 | 数据库拒绝 |
| A/B 伪造 `ms.staff_id`、`ms.tenant_org` | 不改变数据库原始身份和可见学生 |
| A/B 试图查询财务或审核历史 | 数据库拒绝 |

**注意：** 当前仅新增一个可运行的**学生目录只读视图模式**。旧市场销售 HTTP 服务仍运行在组织级低风险账户中，具有比该视图更宽的权限。不能称机构内全部学生、联系人、商机或财务字段已实现员工级数据库隔离。

## 五、自动化测试及人工验收界限

GitHub Actions 需要使用 PostgreSQL 16 执行 **001—012 号全部迁移**，运行原有核心业务、员工身份/家庭双人审批、A/B 机构隔离、真实 Chromium 中文页面与技术合同回归，并新增上述两项真实数据库 HTTP/SQL 安全测试。

验证必须包含：请求仍在 pending 不生效；独立审核通过后不重启网关立即生效；独立审核撤销后即刻禁止访问；同机构授权前后学生可见性正确；不存在直接读取基础表和年级的权限。

**只有与 PR HEAD 同 SHA 的 GitHub Actions 实际成功日志，才能把本阶段称为“隔离测试通过”**。GitHub 自动化并不等于人工 GUI 检查、真实身份供应商接入或生产安全合规。

## 六、尚未解除的生产阻断

- **正式身份与登录**：尚无正式企业 IdP、OAuth/OIDC Code + PKCE、MFA、可信密钥轮换、真实员工生命周期与登录回调。
- **动态租户路由运维**：本次是只读数据库权限验证和固定本机路由；正式目录同步、HA、重试/限流、TLS、变更审批、离职事件通知、密钥管理尚未完成。
- **所有员工业务 API 最小权限**：只读员工目录不意味着原有 HTTP 服务已改为员工单独的 SQL 角色；联系人、商机、财务、家庭证明及全部关联表的员工级最小 SQL 访问仍要逐表设计。
- **个人信息保护**：外部 subject、联系方式、亲属证明材料的最小留存期限、访问记录与合规政策未完成。
- **真实 CRM 与财务接入**：课程标准价、试听权威预约、现金收付确认、部分付款权益、退款追溯、成交归因和教务发课都继续受到此前 BP/TP 阻断；不允许把设计中的接口当作已实现交易能力。
- **版本依赖与文档合并**：本阶段基于 PR #11，前面 PR #4—#11 均保留评审依赖，不提前修改原 edu-management-system 的技术资料。完成真实集成与联合自动化、人工验收后再考虑文档融合。
