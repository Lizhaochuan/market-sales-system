# V3.2-23｜跨模块学生纠错：第二名主管独立核查、安全解除误报隔离与真实错误交接

**独立市场销售技术文档。** 依赖 Draft PR #26；适用范围仅 PostgreSQL 16 虚构数据库、员工受限 SQL LOGIN 与 Chromium 中文实操。**禁止直接合并至现有教培 CRM、部署或接入真实学生、合同、教务和资金。**

## 一、边界与结论

V3.2-22 已在发现某一特定 `lead_id + student_id` 下游商机可能认错学生时创建纠错案件，并锁定后续销售推进。当前 `ms.opportunities` 直接绑定 `student_id`；它的报价、订单、试课、收款分配、退款分配、销售确认以及外部课时权益可能已有独立的权威历史。因此**不能靠销售侧修改一条学生关联就连带改写这些记录**。

V3.2-23 增加一轮独立判断，但根据真实接入能力仅实现以下两个**明确区分的结局**：

1. **确认为误报**（`original_student_valid`）：原学生与销售线索的关联有新的独立核对材料；没有报价、订单、收付款分配、退款分配、试课、销售确认或课时权益链接，且下游影响数量没有变化。第一名主管先批准隔离后，**与原员工和第一名主管都不同的第二名本机构有效主管**才能在新事务中审核，通过后将案件从 `hold_active` 改为 `released`，解除针对该学生销售推进的隔离。**学生关联、商机及销售历史均不改写**。
2. **确认确有错误或需要外部处理**（`external_action_required`）：第二名独立主管批准后追加“跨部门人工纠错交接”的不可变记录，状态清晰显示为“需要外部处理”，但原案件仍为 `hold_active`。**隔离不解除；仍没有把商机转给另一个孩子或修改订单、资金、业绩、合同及教务数据。** 真实纠错需下一版本有权威模块的核对及更正接口。

“跨部门人工交接已登记”不是“财务已调整”或“学生纠错已经完成”。证据引用在虚构测试中只代表有记录，不能证明外部证据的真实性。

## 二、准确的权限模型和三人分离

| 环节 | 执行人 | 约束 |
|---|---|---|
| 初始纠错报告 | 原线索和具体学生的申请销售 A | 当前机构、有效原始线索、指定学生；启动销售隔离 |
| 第一轮隔离确认 | 主管 M | 本机构有效主管，不能与销售 A 相同 |
| 第二轮误报解除或跨部门交接 | 第二位独立主管 N | **不能是销售 A，也不能是第一位主管 M**；数据库按 `SESSION_USER` 绑定身份，每笔均留不可变审核和审计 |
| 真正跨模块业务纠正 | 真实合同/支付/教务等权威模块 | **本版没有实现，不得擅自表示已处理** |

新增 CI-only 角色 `ms_write_reviewer_2` 和 `ms_read_reviewer_2`，对应虚构本机构第二名主管。只获得现有受限角色的可执行函数权限与最小只读投影，没有原始表读写权限。正式环境不得照搬 CI 演示用户和密码。

## 三、数据库 027

- 修改 `ms.lead_student_downstream_correction_cases` 状态检查，允许经第二名独立主管且满足安全条件的 `released`。原 `pending` 或 `hold_active` 继续由 V3.2-22 数据库销售推进触发器隔离；当且仅当释放条件通过后，误报对象才可正常推进既有商机。
- 新表 `ms.downstream_correction_reconciliation_requests`：某案件有且只有一笔进行中的第二轮申请，记录处理方向、独立核实引用、中文理由、事务中生成的下游影响快照、状态与幂等编号。
- `ms.downstream_correction_reconciliation_decisions` 和 `ms.downstream_correction_reconciliation_effects`：两个追加式、不可 UPDATE/DELETE 的决定及效果台账。数据库触发器拒绝篡改；申请与批准/驳回都写中文审计。
- `ms.scoped_downstream_reconciliation_eligible` 与 `ms.scoped_downstream_reconciliation_requests`：只显示本人相关或有效主管待审的**最小学生名称和影响数量**，不开放实际财务余额、外部支付编号或身份敏感字段。
- SQL 受保护函数 `ms.request_downstream_reconciliation` 与 `ms.decide_downstream_reconciliation`：原负责人及角色有效性校验、行锁、重复防护、再次计算影响范围，与申请快照精确比较。只开放最小执行权限；员工不能通过原始 `UPDATE ms.opportunities` 或 `UPDATE ms.sales_orders` 绕过。
- **安全解除条件：** 除已存在的一个或多个商机外，报价、订单、收款分配、退款分配、试课、销售认定与外部权益计数必须全部为 0。否则即使第二名主管试图批准也失败，申请及隔离状态原封不动；可由第二主管驳回申请后补充材料。
- **真实错误：** 追加不可变交接记录后保持 `hold_active`，V3.2-22 保护继续，不解除限制，不自动改写资金及任何学生关系。
- 所有审批和结果在事务内原子提交；旧审计和历史不删除。无外部财务连接，也不把“数量为零”等同于真实权威系统零余额。

## 四、严格接口与中文操作界面

| 接口 | 操作 |
|---|---|
| `GET /api/v1/downstream-reconciliations/eligible` | 本人已完成第一轮主管隔离批准、可以提出第二轮核查的指定学生案件 |
| `GET /api/v1/downstream-reconciliations` | 仅本人提交、自己审核或权限内待审的第二轮最小业务记录 |
| `POST /api/v1/downstream-reconciliations` | 原销售员工提交“原关联核实正确”或“确认错误需跨部门处理”，附两份证据引用及中文理由 |
| `POST /api/v1/downstream-reconciliations/:id/decision` | 第二名独立主管批准或驳回；按数据库现状安全执行或持续隔离 |

中文界面明确区分：`等待第二名独立主管审核，隔离保持`、`已核实误报且无下游业务负担，隔离解除`、`已登记跨部门人工处理，隔离继续保持`。不向员工呈现 SQL 源码。
