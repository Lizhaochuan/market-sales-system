# V3.2-12｜中文学生授权工作台与员工专属低风险客户登记

**状态**：独立市场销售仓库隔离开发版，依赖 V3.2-11 PR #15 和全部更早草稿；非正式环境，不可直接上线。  
**仓库边界**：仅修改 `Lizhaochuan/market-sales-system`。原教培 CRM `Lizhaochuan/edu-management-system` 代码、数据和技术文档不改动。真正集成、联合测试与人工验收通过之前，两边技术说明继续独立。

## 一、这一阶段真正可操作的功能

### 1. 中文学生授权审批工作台

`web/access.html`、`web/access.js`、`web/access.css` 组成新的、**本机隔离的中文员工操作页面**。启动独立权限服务后访问本机 `/app`；不需要员工阅读数据库代码或手工调用 HTTP 请求。

实际操作有三项：

| 员工操作 | 页面显示和业务效果 |
|---|---|
| 提出授权申请 | 选择本人负责的学生、接收员工、**临时共享或正式负责人转交**，填写中文原因与虚构测试证据。临时共享可选择 1 / 7 / 30 天；申请提交后显示“待独立审批”，没有立即改变学生权限。 |
| 独立审核 | 显示中文学生姓名、接收员工、操作类型和状态；有效且独立的主管能批准或驳回，申请人/接收人自批由数据库拒绝。 |
| 当前共享与撤销 | 显示本人相关共享的“有效 / 已到期 / 已撤销”状态、接收员工和到期时间；本人负责或获授权的指定共享可立即撤销。 |

页面选项来自 **2 条新增的受限制数据库函数**：`list_student_access_choices()` 只返回当前员工本人负责的学生姓名、编号；`list_student_access_staff()` 仅返回同机构其他有效员工姓名、编号。这两个函数不会给网页返回年级、家长联系方式、家庭证明、签名身份 subject 或完整员工资料。

**重要的真实边界**：

- 这里是一张**新的隔离权限业务工作台**，不是现有 V3.2-02 演示工作台已完成统一登录与全部菜单整合。它使用本地演示管理员预先发放的 RSA 已签名员工测试凭据，在登录输入框粘贴后立即清空；凭据只保留在页面内存，刷新或退出即清除，绝不放入 URL、localStorage、Cookie 或业务日志。
- 仍没有正式 IdP、OAuth/OIDC Code + PKCE、MFA、真实 HR 身份与生产会话。此测试凭据输入方式**不得用于生产**。
- 页面源码只包含固定中文文本和无害静态样式，业务值一律使用 `textContent` 填充，避免把学生姓名当 HTML 执行。服务器设置 CSP、仅本机监听、严格固定资源路径、不向外暴露源码目录。
- 浏览器只能看到当前数据库员工真正获准的申请、学生与授权；即便网页文字显示“审核”，没有有效独立主管角色也会收到拒绝。

### 2. 低风险学生和联系人登记，改为员工数据库专属写入

先前原有销售工作台的学生、联系人创建路径仍部分走机构级运行账号。为安全推进，V3.2-12 增加了**另外两条独立可运行的只写业务 API**，先证明它们不需要给普通员工原始客户表写权限：

| 实际接口 | 允许的业务字段 | 严格禁止 |
|---|---|---|
| `POST /api/v1/lowrisk/students` | 学生姓名、可选年级、可选学校 | 指定别人为负责人、合并家庭、自动添加商机、扣课时、创建订单、执行付款 |
| `POST /api/v1/lowrisk/contacts` | 联系人称呼、是否拒绝主动联系 | 手机号码、微信号、原始身份证明、未经验证的亲属关系、与其他孩子自动关联 |

**学生默认独立管理**：新学生自动归属于真实登录的员工；没有其他已核实的兄弟姐妹关系，就不会生成家庭单位。联系人不会因为由某名销售登记而自动成为任何学生的家长。

**数据库授权**：`ms_scoped_lowrisk_writer` 只拥有两条受保护函数的 EXECUTE，以及判断本员工身份是否有效所需的只读函数调用；不授予学生/联系人基础表 SELECT、INSERT、UPDATE，亦不授予身份审批、审计改写、财务或 CRM 课程权益权限。业务数据在 `SECURITY DEFINER` 函数内部基于受数据库保护的 `session_user` → 员工映射写入。

**幂等保护**：每次写入必须带有效防重复编号。函数在一个数据库事务内取得同员工同编号的事务锁，核对 SHA-256 请求指纹；相同操作和参数只会返回原来的学生/联系人编号，不会重复生成。不同内容复用编号会拒绝，并保持审核历史与业务表不变。

**个人资料最小化**：手机号、微信、电话密文等任何未开放字段在 API 请求验证阶段即被拒绝。返回只含必要编号和中文姓名/联系偏好，不返回年级、学校等隐私字段；新建操作的中文审计也不记录敏感年级与学校。

### 3. 没有改变的高风险业务

本阶段**绝不**开放真实收款、退款、部分付款权益、成交确认、销售奖金、教务收费单价、正式排课或 CRM 课时开通/扣减/撤销。

正式负责人转交仍需要独立主管审核，不能通过“新建学生”请求擅自设置 `owner_user_id`。原有线索/商机负责人、业绩归因、销售预测金额、任何已核实家庭、兄弟姐妹及家长关联均不受新建/共享/转交操作的隐含改变。

本机独立授权工作台按 V3.2-11 的方法配置 `MS_STAGE=isolated-test`、员工专用 PostgreSQL 登录与受信任 RSA 公钥，使用 `node src/student-access-server.mjs` 启动，访问 `http://127.0.0.1:3300/app`。它必须由管理员签发虚构的员工测试凭据，且该员工在数据库中具有已通过独立审批的有效身份绑定。

低风险写入服务使用**另一类只能执行指定函数的员工数据库账号**，按相同受信任签名身份配置运行 `node src/scoped-lowrisk-write-server.mjs`，默认只监听 `127.0.0.1:3400`。它尚未接入既有中文演示工作台的学生/联系人创建按钮，不能将新 API 的成功误认为旧入口已完成数据库权限迁移。

## 三、隔离自动化验收要求

- PostgreSQL 16 从 001 到 016 的全部迁移成功，前述身份、销售、家庭核实、并发和跨机构安全回归持续通过。
- 真实低权限数据库账号只能执行指定写入函数，不能通过原始表 SELECT/INSERT/UPDATE、读财务或修改审计；员工 A/B 不因客户端自报主管身份或别的机构编号而改变所属范围。
- 正确 RSA 签名但尚未完成身份审批，不得创建任何学生或联系人；绑定撤销后旧 JWT 立即拒绝。
- 同一员工同一防重复编号两次同时提交，只生成一条客户记录；复用编号提交不同内容、不同业务操作均返回冲突。
- 对联系人提交手机号、微信号，对学生提交其他负责人、课程权益或其他不允许字段，必须由 HTTP 拒绝。
- 实际 Chromium 完成 **A 提出学生共享 → 独立主管审核 → B 撤销自己的共享 → A 再申请正式转交 → 主管批准**，证明浏览器可操作且负责人变化与数据库一致。
- 中文页面使用文本安全渲染，窄屏无横向溢出，测试输入令牌不持久化；旧工作台所有原有中文业务回归继续通过。
- 原 V3.1 技术合同回归和所有员工身份/双主管权限安全回归完成，最终 CI 的 SUCCESS 必须与 **本 PR 的当前 HEAD 完全一致**。

自动化测试只能证明本机虚构环境的代码行为，不能替代真实员工手工核验、生产 OIDC/HR 接入或真正的跨 CRM/支付业务联合验收。
