# V3.2-07｜可信身份路由实验与学生目录字段最小授权

**状态**：隔离环境实现候选，依赖独立市场销售系统的 V3.2-06 PR #10。不得生产部署或直接修改旧教培 CRM。  
**业务原则**：学生是主要管理单位；家庭必须按真实多个学生关联并经独立审核；不同学生的商机、归因和消费仍分别记录。  
**文档边界**：市场销售技术说明只在 `market-sales-system` 保存，直到真实跨系统集成、联合测试与人工验收完成后才融合原有 CRM 文档。

## 一、为什么必须增加这一步

V3.2-06 已能保证数据库账号 `session_user` 只能访问管理员预先绑定的机构。但此前的两个独立 HTTP 服务需要人工选择端口，**没有在访问入口完成“真实员工身份 → 正确机构数据库服务”的可信选择**。客户端若自行决定机构路由，仍有被伪造机构参数或请求头引导到其他连接池的危险。

与此同时，机构行级隔离不等于机构内部字段最小权限：当前用于核心业务的 `ms_lowrisk_runtime` 角色仍有较宽的基础表 SELECT 权限。即使业务页面只显示某个员工被允许的学生、隐藏其年级，发生任意 SQL 执行问题时，同机构内仍可能泄漏超出员工授权的数据。

V3.2-07 **只完成两项局部、可证明的隔离实现**，不宣称已经建立完整生产身份系统或全库员工级数据库隔离。

## 二、可信签名员工路由（只在本机演示）

代码：`src/isolated-identity-gateway.mjs`

| 阶段 | 必须满足的规则 |
|---|---|
| 1. 签名 | 使用服务端预配置可信 RSA 公钥验证 RS256 JWT 签名、issuer、audience、时间及 subject |
| 2. 查路由 | 只能凭**已经验签的 `issuer + subject`** 在管理员预设的精确映射中选定机构服务 |
| 3. 固定目的地 | 仅允许预先列明的本机 `127.0.0.1` 或 `::1` HTTP 服务，不能由客户端输入 URL、组织编号或转发 Host 决定目的地 |
| 4. 防污染 | 不把 Cookie、`X-Organization-ID`、`X-Forwarded-Host`、角色自报等任意客户端头传给机构后端 |
| 5. 二次授权 | 机构后端再次验签，并实时通过**机构受限数据库**检查员工身份绑定有效、未撤销、员工已启用和业务记录权限 |
| 6. 双重隔离 | 机构后端的真实 PostgreSQL LOGIN 固定映射到该机构；数据库 RLS 继续拒绝其他机构记录 |
| 7. 失败即拒绝 | 无映射、未知 subject、错误签名、撤销身份、错误机构连接或目标上游服务不可用，不回退到默认机构 |

**重要限制**：当前路由登记信息由可信测试配置以静态表提供。真实人员绑定审批通过后，尚未开发同步到受控路由目录的机制；静态映射更新、密码与公钥轮换、正式 IdP、HA、TLS 终结、限流、OAuth 登录跳转及跨机构员工属于多个机构的身份切换政策均未实现。**目前不是生产网关**，强制 `MS_STAGE=isolated-test`，仅本机监听。

路由登记只决定向哪个机构发请求，**不直接授予任何员工权限**。即便路由目录滞后，数据库中解绑的外部员工仍被机构后端拒绝。反过来，数据库已有新绑定但路由目录未更新，入口仍会拒绝，须由正式运营流程同步。

另一个限制：机构选择流程尚无正式的独立 HR/IT 身份与租户目录。不能将测试用静态映射替换成来自前端的 `org_id`、未经验证的 JWT claims、Host、Referer 或 Cookie。正式入口必须落实动态信任目录与多机构成员关系授权。

## 三、学生目录只读字段投影

代码：`db/migrations/011_student_directory_read_projection.sql`

建立独立只读角色 `ms_student_directory_reader`，仅授予受保护的 `ms.student_directory_public` 视图 SELECT 和安全租户映射函数 EXECUTE。此视图只投影：

- `student_id`：学生档案标识。
- `display_name`：学生显示名称。
- `organization_id`：学生所属机构标识。

**不提供**学生年级、其他家长联系方式、商机金额、收费、课程信息、员工身份目录或原始数据库日志。SQL 视图自身按原始 `session_user` 与机构绑定过滤，同时使用 `security_barrier=true`。

测试创建两个**独立的只读数据库登录账号**，A/B 各自只能看到自己机构的学生展示信息；访问基础 `ms.students` 表、联系人表、财务、敏感年级列以及写入都必须由数据库拒绝。读者角色不能继承宽权限 `ms_lowrisk_runtime`。

**尚未完成的区别**：以上是一个**真实可测试的只读投影模式**，并没有把所有现有销售 API 切换到该账号，也没有让所有员工拥有不同数据库登录名。生产级员工级最小权限必须继续设计可信员工授权上下文、查询视图、安全函数以及个人可见范围，不能以这一只读视图宣布所有客户隐私权限完成。

## 四、实际自动化测试与证据分层

新增两个 Node 22 / PostgreSQL 16 端到端测试文件：

1. `tests/security/trusted-identity-routing.test.mjs`：真实生成 RSA 2048 签名，授权 A/B 外部主体，以统一隔离网关通过两套不同数据库 LOGIN 创建及查询学生；尝试伪造组织/角色声明、请求头和签名；撤销身份后确保旧令牌被拒绝；误把 B 主体路由至 A 服务时也被二次授权拒绝。
2. `tests/security/directory-field-projection.test.mjs`：真实创建两个只读数据库登录、读取受限学生目录；拒绝直接读取学生基础表、年级、联系人、财务以及跨机构记录；验证手动设置旧 GUC 仍不能绕过机构隔离。

同时继续执行现有 001—011 全套数据库迁移、身份与家庭双主管审批、幂等防重、中文审计、Chromium 中文页面和 V3.1 合同回归。**只有 GitHub Actions 对应最新 PR HEAD 的实际通过日志，才能标记自动化测试 PASS。**

不能以 HTTP/SQL 测试代替真实用户操作、正式登录服务集成、人工家庭关系材料核验或 CRM/财务联合验收。
