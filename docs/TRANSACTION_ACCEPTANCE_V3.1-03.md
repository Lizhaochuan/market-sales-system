## 5. 执行方法与证据

- **静态检查**：检查 JSON 状态是否存在、每条 from/to 是否在定义内、转换事件及 guards 完整、数据库与 API 版本引用存在。只能报告 STATIC PASS，不是业务用例 PASS。
- **数据库测试**：隔离 PostgreSQL 初始迁移、唯一约束、事务死锁、版本冲突、金额整数分，至少涵盖并发 2、10 和 100 任务批次。需要测试过程和最终状态证据。
- **受控服务测试**：测试模拟财务权威先后事件、撤销、退款、乱序、重复，测试调用者权限和付款用途审批。人工确认不等于支付平台自动验证。
- **CRM stub 合同测试**：先用模拟 CRM 测 idempotency、响应丢失、原键查询、资源冲突、权益防重；真实 CRM 实现后再做双系统 E2E。
- **GUI 实测**：检查员工看到的业务提示与前后值；有微信小程序/真机的场景，由另一台设备的现场同事根据实际可访问环境验收，不能以代码单测代替。
- **每项记录**：用例编号、测试环境 SHA、虚构数据编号、执行过程、预期、实际、PASS/FAIL/BLOCKED/NOT RUN、脱敏证据和问题链接。
- 禁止把真实手机号、付款凭据、教师工资或密钥推送到 GitHub。

## 6. 生产准入：一票否决

在以下条件全部满足前，不允许宣称“交易模块已经完成”：
1. BP-01 / BP-02 / BP-04 / BP-05 经过负责人审批，生效时间和规则版本清晰。
2. TP-03 指定实际财务权威；可核实付款来源、签名/人工复核流程和退款事件。
3. 数据库 V3.1-01 在隔离环境真实迁移通过，交易域约束有可执行服务实现。
4. TX-T09 至 TX-T36 的金额守恒、并发、发课及恢复用例均通过。
5. CRM 提供独立受控接口、可信学号映射、领域幂等与结果查询。
6. 安全和审计可按学生、员工、字段范围隔离；业务页面不暴露原始源码或敏感信息。
7. 真实备份恢复、故障处理及跨系统联合测试通过，记录实际部署版本。
8. 独立项目主分支审批与 PR 审核完成，避免直接在两个仓库的共享分支写入。
