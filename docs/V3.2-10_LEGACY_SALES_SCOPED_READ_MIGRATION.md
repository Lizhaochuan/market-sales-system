# V3.2-10｜现有销售接口的员工专属数据库读取改造

**仓库：** `Lizhaochuan/market-sales-system`  
**依赖：** V3.2-09（PR #13）及其未合并的上游 PR。  
**测试环境：** 独立 PostgreSQL 16 + Node 22 + 本机虚构学生、销售、主管与身份。  
**阶段定性：** 这是现有业务接口的**第一批实际迁移**，不是全部接口的生产级迁移，更不是 CRM/财务集成完成。

## 1. 核心问题与本轮真正解决的范围

V3.2-09 的五个新接口已经在员工专属受限数据库身份下读取学生、联系人、咨询、线索和商机，但已有中文管理界面调用的旧销售 `GET` 路径仍可能走机构级账号。这会形成两套不同的安全边界：新接口看不到其他员工，旧接口的主管却仍可能凭机构角色查看所有学生、商机或家长记录。

V3.2-10 为**原有 8 条查询路径**加入可选的严格模式：由可信服务器预先配置员工 ID 与独立受限数据库连接池的映射，对每次外部员工请求进行双重验证。只有数据库实际登录身份映射的员工、机构与经 RSA 验签的外部员工身份一致，才允许读取只读投影视图。

**严格模式未配置时**，此前的虚构数据演示行为保持原样，以免将尚未迁移的操作误称为生产安全。**严格模式一旦启用**，所列 8 条接口绝不会在缺少受限账号或审核证据时偷偷回落到旧的机构级数据库查询。

## 2. 已迁移的原有八条接口

| 原中文工作台已有路径 | 改造后可返回的信息 | 必须隐藏或禁止 |
|---|---|---|
| `GET /api/v1/students` | 本人负责或具体授权的学生列表 | 年级、他人姓名以外的负责人隐私、其他销售未共享学生 |
| `GET /api/v1/students/{studentId}` | 有权查看的学生编号、姓名、可公开的负责人信息 | 跨员工未授权详情 |
| `GET /api/v1/contacts` | 本人创建、本人线索或已授权学生相关家长姓名和拒绝联系状态 | 手机号、微信号、原始密文 |
| `GET /api/v1/contact-events` | **本人记录**的咨询类型和时间 | 其他销售的咨询、家长关系证明和原始来源材料 |
| `GET /api/v1/leads` | 本人负责的线索编号和状态 | 其他销售线索、其他孩子的咨询、家长私人资料 |
| `GET /api/v1/leads/{leadId}` | 本人负责的线索及**仍有权查看**的关联学生编号 | 其他员工线索和已撤销访问的学生 |
| `GET /api/v1/opportunities` | 本人负责且对应学生可见的商机 | 预测金额、合同、成交归因和其他销售商机 |
| `GET /api/v1/opportunities/{opportunityId}` | 本人有权查看商机的学生编号、阶段、状态 | 其他销售商机和财务字段 |

新迁移的接口在响应中保留必要的旧字段名称，防止把数据库字段或内部代码直接展示给员工。无法提供的敏感信息显示为 **“已隐藏”** 或空值，而不是泄漏源数据。

## 3. 数据库、服务及测试文件

- `db/migrations/014_legacy_sales_scoped_read_details.sql`：补充员工专属学生、线索、线索—学生关系以及商机的四个受限详情视图。只对 `ms_student_assignee_reader` 角色开放这些视图的 SELECT；不授予原始学生/联系人、线索/商机基础表或任何支付财务写权限。
- `src/scoped-legacy-read-adapter.mjs`：为原有八类 `GET` 操作设置固定视图查询，全部参数绑定，先确认受保护数据库登录员工与业务身份一致，再在只读快照中读取，不允许客户端任意构造表名或 SQL。
- `src/app.mjs`：新增服务器侧可选 `scopedReadPools`，通过静态可信员工账号映射选池；必须提供已经批准的 RSA 外部身份凭据，不因令牌中的 `role`、`org_id`、`staff_id` 声称改变权限。若缺少账号或映射错误返回 403，**没有旧机构数据回退路径**。
- `tests/sql/create_v3_2_10_manager_readonly_login.sql`：仅在虚构 CI 建立主管自己的非所有者、无基础表读取权的受限数据库登录；主管不是拥有全部业务数据的数据库管理员。
- `tests/security/legacy-scoped-read-migration.test.mjs`：使用原有 `/api/v1` 路径、真实 PostgreSQL、两位销售及主管、RS256 签名和独立审批，检查查询授权、细节拦截、角色吊销、数据共享与撤销、数据库池错误映射及财务权限拒绝。

## 4. 主管权限不等于全机构无条件查看

**规则：主管身份只授予管理操作所需的职能权限，不自动授予本机构所有学生、咨询、商机的查看权。**

启用严格模式后，主管本身也是一个独立员工数据库登录，只能读取自己负责或经过具体授权共享的学生。若获得某名学生的查看授权，也只在必要范围内看到该学生及相关联系人：不会因此获得其他销售记录的咨询、线索、商机、预测金额或成交归因。

撤销具体学生访问授权后，该学生和因这项授权而可见的联系人会在下一次请求消失。主管职能角色撤销后，原有 `/api/v1/me` 即时反映主管功能不再允许，**不能利用旧版主管全机构查询逻辑重新取得资料**。原有仍有效的具体学生共享授权是另一项独立权限，需要单独撤销，不会假装自动销毁。

客户仍以**学生为主单位**，已核实的真实兄弟姐妹可按需建立家庭关联，但不得因为家长身份相同而把所有学生合并成一个客户，也不得把一名学生的共享权限扩展到家长的其他孩子。

## 5. 测试边界与正式上线阻断

### 自动化需要证明

- RSA 签名有效但绑定尚未批准的令牌：旧接口 403；虚构 HS256 演示会话也不能进入严格模式读取。
- 销售 A 与 B 在八条原有查询路径看到不同的学生、家长、咨询、线索和商机；无权查看详情时返回 404，不暴露对象是否存在。
- 主管在严格模式下**不能**按原来的 `manager=true` 看全机构数据；精确共享后只能看已授权学生和联系人。
- 角色撤销和具体共享授权撤销产生的变化在后续请求即时生效。
- 删除、缺失、错配任何员工专属数据库池时直接 403，不调用旧机构级查询。
- 身份撤销后同一未过期签名令牌不能再查询原有八条路径。
- 员工专属数据库登录不能 SELECT 原始学生/联系人/财务表，也不能 UPDATE 业务记录。
- PostgreSQL 001—014 全量迁移、旧独立只读 HTTP 接口、原销售/家庭/身份双人审批、真实 Chromium 中文工作台、原 V3.1 技术合同均持续通过。

### 仍未完成，不得称为生产安全通过

1. **启用方式仍为隔离测试中的服务器端注入**。正式身份到专属数据库池的可信动态配置、账号生命周期、密钥轮换、会话管理及 HA 尚未实施。
2. **只迁移八条 GET 接口**。原有 POST 写入、主管家庭审批、员工身份管理、业务审计及其他模块仍未全部切换到同等级 SQL/字段范围最小授权；当前后端仍有机构级连接用于身份与写入，不能将其称为完整最小权限系统。
3. **主管团队可见性政策尚未正式批准**。当前采用“只看本人和具体共享学生”的谨慎默认策略。组织层级、团队负责人、临时代理、跨校区授权、学生转交及监督审计需要独立审批与政策定稿。
4. **正式企业 OIDC 登录、Authorization Code + PKCE、MFA、有效证据及人事目录**尚未实施，所有虚构签名和员工数据库账号都只是测试材料。
5. **家长和儿童个人隐私、真实核实证明与保存期限**需要法律和业务政策审查。按家长共享数据不等于获得其所有孩子数据。
6. **收款、退款、正式成交、业绩归因、CRM 课程单价和课时权益写入**继续关闭；没有修改老教培 CRM。

所有 GitHub PR 仍保持 Draft。在对应 HEAD 的 GitHub Actions 实际成功之前，不能宣称本轮完成自动化验收。任何安全或运行测试失败必须修复后重新执行。

## 6. 项目交付独立原则和 V3.2-11

V3.2-10 仅在 `market-sales-system` 独立仓库交付。老 `edu-management-system` 的数据、代码及技术文档不变；只有真实跨系统实现、财务政策审批、真实 GUI 和联合自动化验收完成后，才合并技术资料。

**后续 V3.2-11 优先级**：设计可审计的团队主管/员工授权模型，针对学生、家长、家庭证明、咨询以及销售职能建立细粒度策略和安全接入入口；随后逐步将 POST 操作和审批流程迁移到最小 SQL 权限。
