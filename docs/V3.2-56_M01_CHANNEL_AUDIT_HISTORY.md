# V3.2-56｜M01 渠道变更的权限隔离审计时间线

> 上游 V3.2-55 Draft PR #62 最新 HEAD `8497c2a24549d982303db8fff7ae2e3f65a5bc72`，GitHub Actions #43593610382 已 `completed/success`。本增量仍只在 GitHub 一次性 PostgreSQL 和虚构员工/渠道测试，不修改真实数据。

## 1. 核心原则：重用原审计，不复制历史

V3.2-54 真实隔离渠道维护函数在同一事务内使用 `ms.audit_events` 写入 `CHANNEL_CHANGE_REQUESTED`、`CHANNEL_CHANGE_APPLIED`、`CHANNEL_CHANGE_REJECTED`。本阶段**不增加另一套可修改的历史台账**，也不让任何销售员工直接 SELECT 原始审计表。

新增 `tests/sql/create_v3_2_56_scoped_channel_audit_history.sql`，在 CI 内创建只读 `ms.scoped_isolated_channel_audit_history` 安全屏障视图，依赖既有 `ms.scoped_isolated_channel_change_requests` 的授权范围过滤原审计事件。返回字段仅有事件 ID、申请 ID、事件类型、发生时间、动作、当前状态与员工编号，不包含原始 before/after JSON、证据引用、理由明文和收付款数据。

由于原审计表在代码业务约定上采用追加写入、非所有者账号无 UPDATE/DELETE 授权，本版只证明**受限员工不能修改审计历史**，并不声称数据库所有者或备份管理员无法篡改；正式不可抵赖、防篡改存储尚需独立平台设计及批准。

## 2. 读取授权边界

- **普通销售**：只看本人的渠道申请与其事件；其他员工、其他机构、无关主管的处理历史不可见。
- **销售主管**：看本人申请、本人实际审核过的历史；对其他员工，只能额外查看本机构**当前待审核**的申请及其提交事件。另一主管已处理完成的申请历史不在可见范围内。
- **已经批准或驳回的审核人**：后续仍可通过本人 `reviewed_by` 看到自己处理过的记录；不会因此获取同机构所有已完成申请的浏览权限。
- 所有范围在 PostgreSQL 以 `SESSION_USER` 绑定当前员工和机构，严格签名身份必须与独立受限只读连接一致，错误授权不回退宽权限演示连接。最多查询 100 条，超过上限拒绝整个结果，不截断成误导性的完整列表。
- 无论页面显示什么操作、JWT 如何自称主管，真正修改隔离渠道仍需 V3.2-54 独立销售主管审批函数在数据库中检查身份、角色、自批和业务快照。

## 3. 中文页面与失败保护

获客渠道页增加“渠道变更审计时间线”，按中文显示申请提交、独立批准执行或驳回、事件时间和申请类型。只使用文本节点，绝不把不可信渠道名、申请理由或审计 JSON 插入 HTML。

`GET /api/v1/marketing-channels/change-requests/audit-history` 返回失败、字段格式错误、超过 100 条，或严格渠道目录/请求列表无法核对时，前端清空旧时间线并关闭申请及审批表单。退出账号清除内存、事件 DOM、计数和表单选项，避免不同员工共享旧记录。
