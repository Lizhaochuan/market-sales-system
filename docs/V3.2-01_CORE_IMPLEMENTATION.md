## 1. 已实现范围

| 业务功能 | 新系统接口 | 业务规则 |
|---|---|---|
| 新建学生销售档案 | POST /api/v1/students | 一名学生一个业务主体；默认创建者负责；不能自动建家庭 |
| 查询学生档案 | GET /api/v1/students/{studentId} | 仅学生负责人、有该学生明确数据授权者或机构主管 |
| 新建联系人 | POST /api/v1/contacts | 仅姓名和拒绝联系设置，当前**不收集明文手机号和微信号** |
| 记录一次真实咨询 | POST /api/v1/contact-events | 记录真实咨询者、时间与来源；保留创建员工 |
| 关联学生和联系人 | POST /api/v1/students/{studentId}/contacts | 同一联系人可关联不同学生；不自动推断兄妹 |
| 新建未明确学生的线索 | POST /api/v1/leads | 保留原真实咨询，可暂不关联系统里的任何学生 |
| 查询线索 | GET /api/v1/leads/{leadId} | 本人线索或本机构主管 |
| 将线索关联具体学生 | POST /api/v1/leads/{leadId}/students | 一个咨询可关联多学生，但不会复制咨询次数 |
| 为学生建立商机 | POST /api/v1/opportunities | 默认继承学生负责人；主管可分派；学生及商机分开管理 |
| 查询商机 | GET /api/v1/opportunities/{opportunityId} | 商机负责人或机构主管 |
| 记录一次跟进 | POST /api/v1/interactions | 一次真实沟通可关联多个已授权业务对象 |
| 提交家庭关联核实 | POST /api/v1/family-groups | 主管提交两名以上学生的核实申请；**状态始终为待核实，不自动认定已核实家庭** |
| 查看业务审计 | GET /api/v1/audit?object_type=student&object_id=... | 每次只查看有权限的对象；返回中文描述与业务前后值 |
| 健康检查 | GET /api/v1/health | 仅表示隔离服务进程可接入，非生产可用证明 |

## 2. 安全设计（当前仅限隔离测试）

- **禁止生产启动**：必须设置 MS_STAGE=isolated-test 和32字符以上测试专用签名密钥；没有配置生产身份提供方，因此不允许当作正式应用公开上线。
- 进程只监听本机 127.0.0.1；签名测试令牌用 HS256、有效期1小时内、指定发行方/受众/员工编号/机构编号校验。
- 不存在匿名业务访问或公开登录/发令牌 API。测试令牌由隔离测试程序生成，正式员工登录方案必须另建安全审查任务。
- 每次通过 staff_users 检查账号启用状态及组织归属；查询和写入均检查当前员工对学生/线索/商机的权限。
- 主管身份来自数据库已授权的 role_grants，**不是由请求体角色自报**。本版只在单机构、隔离环境测试角色模型；不能声称完整多校区安全已完成。
- 同一联系人被两个孩子关联，不授予 A 销售查看 B 学生订单/商机的权限。
- 创建咨询与转化线索必须核对联系人和事件创建人；普通销售不能未经授权认领他人的原始咨询。
- 写请求强制 Idempotency-Key，数据库保留请求摘要和成功响应，**同键同负载重放只返回已有结果**；同键不同内容拒绝。业务操作与审计及去重回执在同一个事务完成。
- 业务 SQL 使用参数化查询，拒绝未知字段和不符合格式的身份标识；没有直接表读写、任意 SQL、CRM 全量导出或财务接口。
- 对应权限校验不充分的家庭确认和联系人手机号处理**未开放**；家庭只产生待核实申请，手机号/微信加密收集未来专项实现。
- 新建学生时无来自 CRM 的自动识别；正式 CRM 学员身份映射功能仍由 M13 后续开发，不按姓名/电话擅自合并。

## 3. 不允许做的事

**本阶段未实现也未开放：**标准课程真实价格、试听排课确认、报价、正式订单、收款分配确认、SaleEvent 自动成交、退款、业绩发放、CRM 实际课时包创建和撤销。

虽然 V3.1-01/04 含有收款及课时表结构，本业务服务**没有开放这些表的写入 API**。禁止人为将其解释成“钱已到账、自动成交已开发”或“CRM 课时已经开通”。

对普通销售的财务和教学字段默认无访问路径，避免尚未完成的交易权限错误暴露。

## 4. 新增数据库迁移

1. 001_initial_schema.sql：V3.1-01 原始数据模型。
2. 002_financial_integrity_draft.sql：V3.1-04 隔离审查用资金约束草案，不能正式上线。
3. 003_low_risk_api_idempotency.sql：低风险业务 API 写入防重复回执表，按机构、员工、请求键唯一。
4. 004_contact_event_owner_scope.sql：记录联系人创建人和原始咨询事件记录人，防止跨员工认领咨询。

**生产迁移政策尚未批准**。不得把这些初始化文件用于真实 CRM 或已有正式数据；历史迁移、备份恢复、密钥轮换及多组织隔离需独立完成。

## 5. 开发依赖及本地隔离运行方法

- Node.js 22 或更新兼容版本；PostgreSQL 16+。
- 测试服务依赖 pinned pg 8.16.3；GitHub Actions 内通过 npm 安装。
- 先在新建的**隔离数据库**按 001→002→003→004 的顺序执行迁移。
- 设置 MS_STAGE=isolated-test、DATABASE_URL（只指向虚构测试库）、AUTH_HMAC_SECRET、AUTH_ISSUER，然后 npm run start:isolated。
- 进程只在本机监听；没有可用的对外域名，也没有正式员工身份发行系统。
- 测试：`node --test tests/core/core-api.test.mjs`；合同测试 `node --test tests/contracts/contracts.test.mjs`。
- GitHub Actions 配置在 .github/workflows/v3-2-core-api.yml 中；它会在 PostgreSQL 16 容器里建表、跑模拟员工/学生 HTTP 测试，之后再跑合同测试。
- **测试结果以实际 GitHub Actions 日志为准**，没有日志不得标记 PASS。

## 6. 验收清单

| 用例 | 目标 |
|---|---|
| CORE-01 | 一名学生不自动建家庭 |
| CORE-02 | 两名不同学生可共享联系人，不自动合并客户 |
| CORE-03 | A 销售只能查看 A 的学生；B 销售只能查看 B 的学生 |
| CORE-04 | 没有明确学生的咨询可以成为真实线索，不创建假学生 |
| CORE-05 | 一次沟通事件可关联两个学生，事件只存一条 |
| CORE-06 | 同一有效请求重复提交不得创建第二个学生 |
| CORE-07 | 同键不同负载返回冲突，不能覆盖旧业务 |
| CORE-08 | 只有主管能发起家庭核实申请，但不会自动标记家庭关系已确认 |
| CORE-09 | 学生和商机负责人分别管理，不自动跨学生改变负责人 |
| CORE-10 | 审计界面返回中文业务含义与单位，不展示原始 JSON 或数据库字段 |
| CORE-11 | 不能凭请求体伪造组织或身份；未授权访问被拒绝 |
| CORE-12 | 正式订单、财务确认与 CRM 课时写入接口继续关闭 |

当前这些用例由隔离 HTTP 测试覆盖一部分；真实浏览器、微信开发者工具及人工 GUI 验收尚未进行。
