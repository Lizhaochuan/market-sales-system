# V3.2-55｜M01 渠道维护申请与独立主管审批中文工作台

> 基于 V3.2-54 Draft PR #61 已核实最新 GitHub Actions #43592191142 `completed/success`。本期只在隔离 PostgreSQL、虚构机构和本机签名员工测试环境中启用。不会把 CI SQL 导入任何生产数据库。

## 1. 本阶段新增的真实工作界面

中文“获客渠道”模块新增了严格员工模式下的两种界面：员工“渠道维护申请”和销售主管“独立主管审批”。员工通过网页选择新增、编辑或停用，填写名称、类别、上级、材料索引和理由；提交后会生成 `pending` 申请及审计，**绝不在申请阶段直接改变渠道**。另一位当前有效销售主管在专属审批卡中选择待办、批准或驳回并填写独立依据；只有批准成功后，V3.2-54 的 SECURITY DEFINER 函数才会在一个事务里执行真实隔离渠道表变更。

- 非严格的旧演示账号仅保留渠道目录只读页面；无法看到维护表单，HTTP POST 也会返回 403。
- 严格模式的普通员工可提交申请，只查看其本人发起的记录，不显示其他员工的名字、渠道申请或审批待办。
- 严格模式中来自经审核销售主管的 `review_channel_change` 能力只用来展示审批操作；是否允许批准必须由服务器的员工身份及 PostgreSQL 当前角色再次检查。申请人自己不能审批自己。
- 表单不使用原始申请台账，不调用宽权限租户 SQL，页面从 `textContent` 渲染所有渠道及申请名称（包括特殊 HTML 字符），退出登录清空内存、表单选项与审批 DOM。
- 新的只读列表拉取失败、字段异常或渠道树不可信时，清除旧记录、关闭变更表单，**不把先前的审批待办当作当前有效授权**。

## 2. 安全只读投影

新增 `tests/sql/create_v3_2_55_channel_review_read_view.sql`，仅在完整 GitHub CI 的一次性数据库安装，创建 `ms.scoped_isolated_channel_change_requests`（`security_barrier=true`）。

- 所有结果先按受保护的 `SESSION_USER` → 员工与机构映射限制。
- 员工只能读取自己的历史与当前申请；主管可额外读取本机构其他员工的**待审核**申请。主管自己的申请会显示为 `can_review=false`；普通员工没有任何来自其他人的待办。
- 输出字段仅限申请编号、操作、最小渠道信息、状态、申请时间、申请员工 ID、是否有独立审核资格；**不返回**证据引用、原状态 JSON、复核备注、防重复键、内部审计对象。
- 受限读取账户仍不能直接 `SELECT ms.isolated_channel_change_requests`、原始 `ms.marketing_channels`、订单、资金分配，也不能 UPDATE 审计表。
- `src/scoped-legacy-read-adapter.mjs` 新增员工专属 GET 映射，保持只读事务、数据库身份双重核验和最多 100 项的完整性上限。没有授权时拒绝，绝不回退至旧的宽权限池。

## 3. 两层实测

`tests/security/m01-channel-review-scoped-list.test.mjs`：真实 PostgreSQL16 的 A/B 两位普通销售和 M/M2 两位独立主管；包括同机构他人的 pending、已结束申请、跨机构伪造记录与主管自己的申请，逐一检查视图中每个人的最小可见数据、`can_review`、资金表和原始台账访问拒绝。

`tests/browser/m01-channel-approval.spec.mjs`：Chromium 真正完成模拟 RSA 登录、员工申请新增、主管独立批准、员工刷新确认渠道生效，随后执行编辑、停用的相同审批流程；每步都核对**审批之前数据库渠道状态不变**，最后检验历史状态及登录退出后审批 DOM 清空。测试只触碰虚构渠道，并在完成时清理临时对象。

## 4. 仍然不允许

- 生产部署、真正员工 IdP、真实获客渠道数据、外部 CRM/财务读取或写入、正式渠道成本与商机成交归因仍未实现。该界面**不是生产渠道管理系统**。
- 学生为主管理单位，家庭只在确有兄弟姐妹时按需关联。不能以渠道相同推断家庭，不能改变学生与订单/资金的独立归属。
- 真正错绑且已有订单、收付款、退款或履约记录时，必须继续 `hold_active`；原订单、支付、SaleEvent、消课/课时历史均不得修改。
- 16 项真实权威来源准入、R01—R10 仍未完成，正式财务/CRM 两份 OpenAPI 保持 `proposed-unimplemented`。
- `production_integration_allowed=false`、`execution_allowed=false`、`release_allowed=false`、`merge_authorized=false`、`deploy_authorized=false`。
- 数据库迁移严格保持 `001—038`，不新增 `039`；不合并、不部署，不修改 `edu-management-system`。
