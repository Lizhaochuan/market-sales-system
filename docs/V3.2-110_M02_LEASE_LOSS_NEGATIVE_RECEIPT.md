# V3.2-110｜M02 租约失效通知、SQL 原子撤销与负向回执契约

## 基线

基于 V3.2-109 Draft PR #116，HEAD `462eb7f35007b69928517e1e50243c08cca7a50c`。V3.2-109 的隔离 PostgreSQL Actions #43662996433、V3.2-100 聚合审查 #43662996372 均 completed/success。本阶段仍是 **CI-only 市场销售跨模块隔离设计**，不合并、不部署、不触碰现有 CRM 生产库。

## 核心结论

单纯依赖租约 API 报告 active 或对 SQL 账本进行重复读取，无法证明通知已持久记录，更不能证明一个真实跨业务系统的原子交接。V3.2-110 将**签名失效通知、不可修改的通知事件、单调通知序号与 SQL 租约状态更新绑定到一次 PostgreSQL SERIALIZABLE 事务**。测试时，只有签名通知合法、作用域/租约 ID/围栏 epoch/来源水位与数据库租约一致、序号连续且前链摘要正确，才允许对**隔离审计表**写入失效事件并将测试租约状态改为 revoked。

另建立签名负向回执接口：只能报告 `blocked` 或 `uncertain`，不得出现 accepted、committed、handoff_complete 或资金/教务审批。即使返回 `BLOCKED_CI_LEASE_LOSS_AND_NEGATIVE_RECEIPT`，唯一含义也是**隔离环境中的通知与负向回执一致**，全部业务许可始终 false。回执丢失或签名伪造时，SQL 事务可能已经完成；失败响应不能反推数据库没有变更。必须回读真实审计账本确认，而不能重放放行指令。

## 文件与接口

- `src/cross-module-lease-loss-negative-receipt.mjs`：接受 V3.2-109 的隔离租约核验入口、SQL 租约读取、独立签名通知来源、独立签名负向回执来源和通知账本。通知与回执分别使用不同的**临时测试 Ed25519 公钥**；签名正文严格绑定机构/异常、租约 ID、围栏 epoch、来源摘要、通知序号/前链摘要、模拟时间和类型。
- `tests/fixtures/v3-2-110-m02-loss-notice-sql.sql`：仅在一次性 `v106_isolated` 数据库创建 `lease_notice_heads` 与 `lease_notice_events`，使用已有 V106 租户 A/B 行级隔离策略。测试角色只能 INSERT/SELECT 事件，不能 UPDATE 或 DELETE 事件记录。**这不是生产迁移。**
- `tests/helpers/v3-2-110-m02-postgres-loss-notices.mjs`：在一笔事务中按机构/异常加 SQL 作用域锁，同时比对当前活动租约、通知 head 和前链摘要，执行“租约置为 revoked + 插入事件 + 推进通知 head”，提交前故障使全部回滚，序号错误或已撤销时拒绝重复追加。真实业务订单、收款和课时表不可读写。
- `scripts/v3-2-110-setup-loss-notice-sql.mjs`：限定数据库名称和管理员身份才能建立隔离测试表。
- `tests/integration/v3-2-110-m02-lease-loss-negative-receipt.test.mjs`：在真实的一次性 PostgreSQL 16 中直接组合已有 V3.2-104/106/109 实现和本期通知事务。

## 14 项独立测试

| 编号 | 验证要点 | 结果标准 |
|---|---|---|
| LOSS-01 | 正确签名通知与负向回执 | 租约撤销、事件持久保存，业务永不放行 |
| LOSS-02 | 伪造失效通知签名 | 进入 SQL 前拒绝 |
| LOSS-03 | 已签名但跨机构通知 | 作用域拒绝，不撤销原租约 |
| LOSS-04 | 过期通知与乱序号 | 拒绝，不写入事件 |
| LOSS-05 | 通知提交后伪造回执 | 拒绝回执，已提交撤销不反转 |
| LOSS-06 | 伪造成功、错摘要或跨机构回执 | 全部拒绝 |
| LOSS-07 | 合法签名但提交结果不确定 | 阻断，不允许业务行动 |
| LOSS-08 | SQL 已 COMMIT，但回执链路丢失 | 返回不确定，回查发现租约已撤销 |
| LOSS-09 | SQL COMMIT 前模拟故障 | 通知、head、租约修改均回滚 |
| LOSS-10 | 同时提交、重放同一签名通知 | 最多一个成功，历史事件不被覆盖 |
| LOSS-11 | 错误租户数据库角色 | PostgreSQL RLS 阻断 |
| LOSS-12 | 已撤销租约被重复用于出具回执 | 必须拒绝 |
| LOSS-13 | V109 核验后、通知记录前，来源发生变化 | 通知仍可安全撤销旧租约，但**不能证明跨系统来源版本已原子锁定** |
| LOSS-14 | 请求携带伪造资金许可或非法作用域 | 直接拒绝 |

## 本期能力边界

SQL 的“原子”只涵盖一次性 PostgreSQL 的**通知事件记录与本地租约撤销**，完全不涵盖真实销售、财务、教务来源的原子数据锁定和联合签收。拥有测试私钥的人仍可签署虚构的通知或回执，因此此处的签名只能核验本次 CI 测试主体，不能证明独立真实机构权威。尤其 LOSS-13 显示：此前租约核验结束之后来源状态可能更新；将租约置为撤销可以降低误用风险，但**无法凭负向回执反向证明原业务交易安全或已正式完成交接**。

真实资金归属、课时权益、历史订单、SaleEvent 和补偿记录不得原地覆盖。学生继续是主要管理单位，家庭仅按真实多个孩子同家庭关系按需关联。V3.2-100/105 的 16 项外部准入、R01—R10 和六种外部财务/教务/对账/三方/交接权威仍未验证。正式合同为 `proposed-unimplemented`，生产 PostgreSQL/Chromium/合同及真实三方 UAT 仍未完成。

本期固定 `finance_authorized=false`、`academic_authorized=false`、`handoff_allowed=false`、`compensation_write_allowed=false`、`release_eligible=false`、`hold_active=true`。既有生产迁移仍按规格 001—038 管理，没有生产 039。不修改生产应用入口、`edu-management-system` 或既有 CRM 技术文档，市场销售技术说明独立维护。
