# V3.2-29｜财务与 CRM 正式只读对接的来源登记审批与准入阻断

**交付性质：独立市场销售系统 PostgreSQL16 隔离测试，不属于实际连接。**
**上游：** V3.2-28 Draft PR #33，基线 `d120beca17a67be0a2f0c356d7064ae6a6babdf3`。
**边界：** 学生为主要管理单位，家庭仅在确有多个孩子时按需关联。禁止更改原订单、资金归属、已上/已消课时及解除隔离。旧 `edu-management-system` 和 CRM 技术文档不变，PR 保持 Draft。

## 一、核心结论

V3.2-24—28 已实现隔离纠错方案、三方审批、补偿对象清单、人工来源候选和**虚构来源签名测试**，但它们没有产生合法且可信的财务/CRM 授权。V3.2-29 对“未来能否连接”先引入**来源登记资料与分离职责的批准记录**。所有批准仅代表“准备材料供后续验证”，而非“已接通来源”或“具备执行权限”。

本期不持有任何外部真实凭据，也不创建实际 HTTP 连接器、付款冲正 API、CRM 发课/扣课接口、金额账本合并及销售隔离解除函数。

## 二、已实现的隔离数据库机制（migration 032）

| 对象 | 实际含义 | 不允许的结果 |
|---|---|---|
| `cross_module_source_onboarding_requests` | 同一错绑案件的已封存清单下，各提交一份**财务**与**教务**来源准备申请，记录拟议来源代号、租户代号、最小数据要求、业务身份映射、安全控制和异常恢复方案的**引用** | 不存储 token、银行凭据、真实密钥、学生隐私或外部系统 URL；不自动建立连接 |
| `cross_module_source_onboarding_reviews` | 先由财务/教务各自负责人员审核，再由独立信息安全审核员分别审查。签字与原材料只追加 | 不容申请人自批、其他机构代批、同人冒充两个业务部门、同人既业务审核又信息安全审核 |
| `request_cross_module_source_onboarding` | 原错绑案件的原申请人只能在最新三方审批、完整封存补偿清单、本地源指纹未变化、案件持续隔离的前提下提出登记 | 同部门同清单重复申请、新键重复创建、旧版资料覆盖 |
| `review_cross_module_source_onboarding` | 本机构有效财务/教务或独立信息安全角色按指定职责签署一次；审批人角色由受保护 PostgreSQL LOGIN 决定 | 同一部门二次签署、同一人代签、已驳回版本继续补签、不同内容复用相同操作编号 |
| `cross_module_source_onboarding_readiness` | 只读提供两部门的申请数、财务/教务批准数、安全审核数、拒绝/退回、最新版本、源指纹和**固定的禁止执行判断** | 无法把虚构准备审批翻译为生产只读连接、真实财务/教务认证或销售隔离释放 |

**独立账号：** `source_security_reviewer` 专用信息安全角色，CI 中用独立自然人和非所有者数据库 LOGIN `ms_source_security_reviewer` 验证。原销售、财务、教务仍仅有本机构既定受限权限。信息安全审核员不能直接读写业务表，也不能更改订单、金额或课时。

## 三、完整的准备审批顺序

1. **销售申请人：** 在现有错绑案件 `hold_active`、正确学生已独立核实、三方纠错计划同版本获批、补偿清单全部封存且本地事实未变化时，分别提交财务来源准备申请和教务来源准备申请。两项来源独立，不能仅由家庭联系人推定所有学生属于同一来源。
2. **财务责任人：** 核对收款、退款、分配、拒付的正式来源候选、机构账套、合同主体、数据最小化和业务用途；只有财务审核角色可签其部门的准备意见。
3. **教务责任人：** 核对 CRM tenant、学生唯一学号、课包、排课、实际授课、消课及余量所需的查询权限；仅教务审核角色可签其部门意见。
4. **独立信息安全审核人：** 等待财务及教务由不同自然人分别审查通过后，检查拟议来源身份、租户隔离、授权证据、凭据托管、签名与撤销方案、保留期限及故障恢复，然后对两份来源准备申请分别留存“可继续规划”或驳回/退回意见。
5. **状态检查：** 只有两份申请、财务和教务审核各一份、安全审核两份、最新方案、源指纹一致且没有拒绝或退回时，`planning_paperwork_complete` 才能为 true。这个状态**不允许**真实连接，也不意味着实际业务纠错完成。数据库始终固定：
   - `official_source_registered=false`
   - `official_credentials_installed=false`
   - `production_readonly_connection_allowed=false`
   - `finance_source_authenticated=false`、`crm_source_authenticated=false`
   - `execution_allowed=false`、`release_allowed=false`
6. **变化与驳回：** 如来源名、账套映射、学校/机构归属、资料、安全规则变化，或增加迟到付款/消课而导致本地指纹变化，当前版本不能继续使用；需要新方案、重新三方审核及准备审批。旧申请与批准不能删除覆盖。

## 四、正式接通前必须由业务负责人明确决定（本期不假设）

| 实际待解决问题 | 决策/证据责任人 | 未解决的后果 |
|---|---|---|
| 哪个系统才是收款、退款、拒付与分配的唯一权威？ | 财务主管、合同责任人（BP-02 / TP-03/04） | 禁止把人工收据或候选标为已到账 |
| 合并付款如何确认真实用途与合法重分配依据？ | 财务主管、合同责任人及必要时法务 | 不允许按家庭推断订单学生归属 |
| CRM 哪个系统提供已上、已消、剩余课时的终局回执？ | 教务主管、CRM 负责人（BP-01 / TP-05） | unknown 不等于未发课，禁止重新发放 |
| 哪些服务身份、证书、公钥、密钥轮换/撤销规则可用于正式只读？ | 信息安全负责人、财务/教务系统所有者 | 虚构签名验证结果不能升级为真实权威 |
| 请求签名/受众/机构租户如何绑定，分页水位是否能证明完整性？ | 真实系统技术负责人、信息安全 | 来源重复、迟到、漏页一律继续隔离 |
| 出错/断网/超时/数据不一致后如何恢复与留存证据？ | 财务、教务、信息安全与运维 | 不允许将失败视为成功或自动释放隔离 |
| 合同更正及业绩佣金责任人是谁？ | 销售、财务、合同法务（BP-05） | 禁止改写原订单与业绩历史 |

## 五、真实接口准入条件（全部必须独立验收）

- **来源登记**：所有者本人签字、唯一账套与 CRM tenant、机构边界、一致的学生身份映射、数据用途、数据驻留及留存期限确定。
- **访问控制**：只读范围最小化，凭据独立保管、轮换/撤销、密钥与代码分离、访问日志不可抵赖；不能在 GitHub 保存密钥或真实学生/银行信息。
- **协议正确性**：可信证书链及 issuer/audience/tenant、重放风险、双机构隔离、可信序号与完整水位、分页重试、并发/迟到退款及课时事实核对。
- **失败与恢复**：接口 401/403/429/500、断网、签名失效、源版本跳变、未知开课、跨系统半完成、灾备恢复与手动升级均以“继续隔离”收敛。
- **验收证据**：运行环境、真实权威服务所有者、经过审批的测试源、独立财务/教务/信息安全负责人、明确接口版本和完整审计；不能只给模拟 PASS。
- **真实执行权不随只读获准而出现**：任何资金、课包或合同更正都需要下一阶段独立专用领域操作、补偿历史、终局回执和跨模块执行后验收；本期不做。

## 六、自动化验收范围

应在本 PR 最终 HEAD 验证 PostgreSQL **001—032** 迁移、双机构真实受限数据库 LOGIN、源申请/审批权限、只追加、重复、退回、版本/迟到资金无效、安全独立签署、Node 全量安全与业务回归、原 Chromium 中文页面及 V3.1 合同测试。任何失败都需修复并重跑；旧页面回归不代表新增了 V3.2-29 正式业务审批页面。

**本阶段的所有来源名称、来源租户、密钥和审批人员都是隔离测试用虚构数据。** 无实际 API 连接、未接真实客户、未更改独立 CRM 原文档；Draft 不合并、不上线。
