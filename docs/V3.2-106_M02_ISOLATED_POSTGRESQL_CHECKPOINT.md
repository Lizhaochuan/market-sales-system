# V3.2-106｜M02 一次性 PostgreSQL 版本水位事务验证

## 上游与本期范围

基于 V3.2-105 Draft PR #112，HEAD `0bd2657e4364384fe510745066ec11faecd1b477`。其专属审查 CI #43661276084 与 V3.2-100 18 阶段聚合 CI #43661276022 均 completed/success。上游 V3.2-104 使用共享 Map 进行事务模拟，但未在真实 PostgreSQL 中验证。本期新增**GitHub Actions 一次性 PostgreSQL 16 测试服务**，只在测试数据库和测试角色上操作，绝不连接生产库或开发环境的现有 CRM schema。

## 新增交付

- `tests/fixtures/v3-2-106-m02-isolated-postgres.sql`：创建仅存在于测试库 `v106_isolated` 的 `v106_test` schema，按机构+异常组合主键存放签收水位 JSON 文本及 SHA-256 摘要。创建两个隔离测试租户的 PostgreSQL 登录角色；开启强制行级安全策略（FORCE RLS）。额外放置虚构付款数据表，只用于证明水位写入者无业务表 SELECT/UPDATE 权限。
- `tests/helpers/v3-2-106-m02-postgres-checkpoint.mjs`：V3.2-104 `checkpointStore.advance(scope,checkpoint)` 的隔离 PostgreSQL 实现。强制环境卫兵 `V106_ISOLATED_PG=YES_TEST_ONLY`、数据库名称 `v106_isolated` 和专用写入角色；在事务中按机构/异常加锁并查询当前水位、检查版本单调、旧 keyId 撤销证明、名册相同版本的摘要与同版本证据一致性，COMMIT 成功后才返回 accepted=true。事务失败 rollback，序列化冲突最多重试四次。
- `tests/integration/v3-2-106-m02-postgres-checkpoint.test.mjs`：在两个独立 PostgreSQL Pool 上执行并发冲突、应用重连重放、真实角色行级隔离、恶意跨租户请求、业务表无权限、密钥替换、撤销摘要改写和提交前故障注入。
- `.github/workflows/v3-2-106-postgresql-checkpoint.yml`：用 GitHub-hosted 临时 PostgreSQL 容器运行数据库测试，同时回归 V3.2-105 的准入审查和既有 18 阶段 Node 隔离安全测试。

**真实测试数据库不等于真实业务生产验收。** 该仓库无 `package-lock.json`，CI 使用现有 `pg@8.16.3` 运行时依赖，避免创建或更新生产依赖文件。

## DB-01—DB-08 检查口径

| 项 | CI 实际测试目标 | 仍缺少的生产证据 |
|---|---|---|
| DB-01 | 仅在名称固定的临时测试库和专用角色运行 | 企业独立 DB 管理与审批 |
| DB-02 | COMMIT 后新建连接/适配器能够读取水位，旧版本拒绝 | 数据库服务重启或灾备恢复 |
| DB-03 | 同一作用域相冲突的并发更新最多一个成功 | 多节点长时压力与分布式负载 |
| DB-04 | 相同治理版本改写名册摘要被拒绝 | 外部真实签名密钥权威 |
| DB-05 | 更换签名 keyId 需要更高名册版本及旧密钥撤销 | 真实 KMS/HSM 与人员审批 |
| DB-06 | 两个测试角色的强制 RLS 隔离，不能读取或修改模拟业务付款表 | 真实组织身份与租户角色映射 |
| DB-07 | 提交前注入故障后事务撤销，重新提交可恢复 | 真实断电、数据库主备切换和恢复 |
| DB-08 | 明确断言测试写入不授予任何真实业务权限 | Chromium、财务/教务、正式合同及三方 UAT |

DB-01—07 的结果只能称为“**一次性 CI PostgreSQL 合同测试**”。DB-08 的真实业务核验未完成，不得因本地测试通过而宣称 DB-01—08 已全面达到组织正式准入。

## 权限、数据与生产边界

适配器完全位于 `tests/helpers/`，不在生产 `src/app.mjs`、`src/server.mjs` 接线；数据库 DDL 位于 `tests/fixtures/`，没有新建生产迁移 039，也没有修改真实数据库。角色密码仅供临时 CI 容器测试，绝不可用于任何真实环境。源 Ed25519 密钥仍是模拟信任根。内存/测试数据库的版本证据依然不能证明现实订单、收款、课时数据正确，也不能独立解决跨系统因果快照问题。

所有业务权限保持 `finance_authorized=false`、`academic_authorized=false`、`handoff_allowed=false`、`compensation_write_allowed=false`、`release_eligible=false`、`hold_active=true`。16 项外部准入、R01—R10、6 类真实外部签名/对账/交接仍未完成，正式合同 `proposed-unimplemented`。学生为主单位，家庭按实际同家庭多个孩子时按需关联；原订单、收付款、SaleEvent、课时和补偿历史不可覆盖。保持 Draft，不合并、不部署、不修改 `edu-management-system` 和既有 CRM 文档。
