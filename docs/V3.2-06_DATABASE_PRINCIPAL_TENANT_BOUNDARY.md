# V3.2-06｜可信数据库机构身份与关联表行级隔离

**所属系统**：market-sales-system（独立市场销售系统）  
**版本**：V3.2-06，独立草稿；前置 PR #9 → #8 → #7 → #6 → #5 → #4。  
**执行范围**：一次性、虚构数据 PostgreSQL 16 测试库；本地 Node 22、自动化 Chromium。  
**不允许**：正式 CRM 数据库、真实身份凭据、真实客户数据、在线支付、教学课时修改或生产部署。

## 一、本次解决的核心问题

V3.2-05 引入了低权限数据库账户和首批 10 张业务表的 RLS，但机构筛选依据 `ms.tenant_org` 是普通 PostgreSQL 会话参数。连接该数据库的角色可以通过 SQL 主动修改此参数，因此前一版本不具备可靠的数据库级机构信任边界。

**V3.2-06 改为：一个真实数据库 LOGIN 对应一个由数据库管理员配置的机构。** RLS 用 PostgreSQL 的原始登录名 `session_user` 查询一个不向业务角色开放读写的机构映射表。普通 `SET ROLE` 不改变 `session_user`；在业务数据库账号权限内改写旧参数、提交另一个机构的 JWT 声称或调用 SQL，都不能借此切换到另一个机构。

数据库超级用户和迁移管理员仍能管理映射；这是预期的高权限安全边界，应由独立运维和审计管理。这个方案没有消除所有风险，也不能代替应用级 RBAC 或正式员工登录。

### 明确覆盖的 24 张表

- 基本机构与权限：`organizations`、`staff_users`、`role_templates`、`user_role_grants`、`data_scope_grants`、`field_policies`。
- 学生客户和来源：`marketing_channels`、`students`、`contacts`、`student_contacts`、`contact_events`、`leads`、`lead_students`、`opportunities`。
- 沟通与家庭：`interactions`、`interaction_subjects`、`family_groups`、`family_memberships`、`family_review_decisions`。
- 身份与审计：`staff_identity_bindings`、`identity_change_requests`、`identity_change_decisions`、`audit_events`、`api_write_receipts`。

这些表都继承 `ms_lowrisk_runtime` 的允许权限，但其行级政策必须同时允许所在机构；若没有机构映射，则查询应返回空集合，写入不得通过。关联关系的学生和联系人也需与当前数据库机构匹配，不允许通过仅有 ID 的方式引用另一机构的记录。

**区别于全部数据库表**：此处 24 张指已有低权限业务角色获授权访问的表，不是数据库中全部表。正式销售订单、收款、退款及 CRM 教学权益仍没有授权给低风险角色，也没有在本次开放操作接口。其他尚未授权但未来需要开放的表必须在授权前补齐同等级策略。

## 三、双机构验证方式

1. 迁移账号创建独立 `ms_isolated_api`、`ms_isolated_api_b` 两个非所有者登录，并分别绑定虚构 A、B 机构。**绑定操作不能由业务账户执行**。
2. 以 A 数据库登录启动本机测试服务 A，以 B 登录启动测试服务 B，两个服务使用相同后端实现，但不同数据库连接池。
3. A 学生 A 及联系人 A 只能通过 A 服务读写，B 学生 B 及联系人 B 只能通过 B 服务读写。
4. 以 B 数据库登录执行旧版 `set_config('ms.tenant_org', A机构编号, true)`，查到的数据库可信机构仍为 B，A 学生、联系人及员工不会因此出现。
5. B 执行 `SET ROLE ms_lowrisk_runtime` 时，`current_user` 发生变化，但原登录 `session_user` 保持 B，机构映射不能因此改变。
6. B 将 A 联系人关联 B 学生，数据库行级策略拒绝。
7. 两个运行账号均不能读取受保护的机构映射表、修改员工权限、读取销售订单；迁移管理员被启动安全闸拒绝用作业务服务账号。
8. 即使 JWT 是由本机有效演示密钥签发，其声称机构与数据库登录机构不一致时，员工查验也会拒绝访问。

## 四、不能宣布生产安全已完成的原因

**P0-1｜生产身份供应商仍未接入。** 当前的 HS256 演示会话和 RS256 外部令牌校验不等于正式 OIDC 登录。正式身份提供商、员工入离职管理、Authorization Code + PKCE、可信密钥轮换、MFA、会话风险控制仍待选择、实施与验收。

**P0-2｜尚未实施可信的机构连接池路由。** 当前只是两个独立测试服务各自配置不同数据库 LOGIN。真正一个正式入口如何根据可信员工身份把请求路由到正确机构数据库连接池，尚未开发。不能直接使用 HTTP 请求头、客户端输入的机构 ID 或未核验 JWT 声称作为连接池选择依据。

**P0-3｜数据库层不是完整业务授权。** 机构内管理员和销售数据范围、联系资料的敏感字段级保护、审计读取审批和高风险业务仍依赖后续最小权限与字段级 ABAC 审查。仅租户 RLS 不意味着机构内所有员工可以相互查看客户。

**P0-4｜数据库角色权限仍较宽。** 低风险角色继承多个核心表的 SELECT 或 INSERT。即使跨机构不能访问，获得任意 SQL 执行能力仍可能读取同机构内不应由该员工查看的联系人或员工资料。生产需要按字段与操作收紧 SQL 权限、审计 SECURITY DEFINER 函数、建立独立强制归属范围和行级员工策略。

**P0-5｜高权限数据库管理与生命周期未落地。** 账号与机构映射必须由独立的迁移/运维身份维护，正式凭据管理、轮换、日志、备份、恢复以及新增/注销机构的流程尚待设计。

**P0-6｜全系统功能与人工验收未完成。** 实际业务人员用中文页面验收、真实 CRM 集成、正式支付权威回执、退款及课程权益均仍未启用；不得把 CI 全绿等同于上线许可。
