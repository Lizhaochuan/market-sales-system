# V3.2-24｜错误学生关联已有订单、收款或履约时的跨模块纠错设计

**性质：独立市场销售系统的跨模块设计草案，尚未实现、尚未验收、不得上线。**
**基线：V3.2-23，提交 6689aafa597ee51f18439a26985d80cfa3640a6a，Draft PR #28。**
**边界：仅虚构数据与隔离环境；不修改 edu-management-system 原代码/技术文档，不连接真实收款、合同、课时或客户档案。**
本稿定义销售、财务、教务的权责、审批、历史保留、补偿与解除隔离门槛；**不授权对原订单、原收款分配、原课时记录直接改写**。

## 1. 核心业务决定

1. **一名学生、一笔案件**：案件键以原机构、正式线索、原关联学生、原申请关联及已存在的下游商机为范围。正确学生必须另行独立核实；同联系人/同家庭/同电话号码不足以推断身份或跨学生转移。其他孩子默认完全不受影响。
2. 已确认错绑并有订单、付款或履约记录时，继续保持 V3.2-22/23 的销售推进隔离（hold_active），不能通过原有 release_verified、撤回或作废功能绕行。历史案例中的 escalate_manual **不是纠错完成**。
3. **销售无权改资金，财务无权改教学，教务无权改合同或学生归因**；各模块负责人只能出具本模块签署结果，其他部门无法代签。
4. 已产生的订单、财务权威收据、分配、退款、SaleEvent、已创建课时权益、上课/消课流水、原始审核、原始来源与操作审计必须可追溯。错误通过新证据、失效说明、补偿或新业务记录纠正，而非覆盖或删除。
5. **签字不等于执行**：三方同意方案仅意味着可以进入独立的受控执行阶段；需每一个权威系统的真实执行回执、重新对账和二次验收后，才可能解除隔离。
6. 不因“有一份收款”自动把款转给正确学生；不因“家长是同一个人”自动更正订单；不得自动在 CRM 给正确学生补发课时或从错误学生扣课时。

## 2. 三方责任及审批边界（RACI）

| 事项 | 销售（S） | 财务（F） | 教务（A） | 不得越权 |
|---|---|---|---|---|
| 发现并提交错误关联 | 发起，提供原线索/商机/订单证据 | 被通知影响范围 | 被通知影响范围 | 销售不得承诺资金/课时已转 |
| 核实错误学生与目标学生 | **事实负责人**：独立核对原学生与建议正确学生、合法业务依据、CRM身份映射；经理批准 | 核对是否涉及付款人/合同主体 | 核对学员/课程身份是否一致 | 不能根据姓氏、电话、家庭或联系人自动推断 |
| 原订单、成交及销售归因影响 | **责任审核**：原商机/报价/订单、SaleEvent/业绩快照与建议业务更正；不得覆盖原订单 | 对金额、合同财务后果签署影响意见 | 对课程权益影响签署意见 | 销售无订单/资金直接重写权 |
| 实际收款、订单分配、退款、拒付 | 提供业务目的与客户沟通凭据 | **唯一资金责任审核**：原外部交易、账户、经济事件唯一性、金额守恒、冲正/补偿方案 | 只读最小必要结果 | 财务确认权不能由销售主管或超级管理员冒用 |
| 试课、排课、课包、已上课/消课 | 说明销售承诺与订单对应课程 | 确认退费与已履约财务影响 | **唯一履约责任审核**：CRM package_id/学号/课次、已消课、剩余权益、可执行补偿 | 教务结果未知时不得标记“未发课” |
| 执行后的核对与解除隔离 | 核实销售侧执行结果及归因 | 财务权威系统实际回执与净额对账 | CRM 实际权益回执、课消记录与余额核对 | 任何一方不得独自释放；技术管理员不得代替业务签字 |

**人员隔离：** 原申请人不得审批自己发起的方案；销售复核不得复用同一个人充当独立终审；销售、财务、教务三方必须为不同的自然人及独立的、已验证且本机构有效的专业角色。持多个角色的同一人不能签两个部门。原 V3.2-23 两主管意见继续独立保留，但**不得替代财务或教务批准**。角色不能仅凭客户端传入的员工 ID、role 或部门声明；跨系统真实授权尚未建立，所有正式审批接口仍为禁用。

**组织与外部系统边界：** 只允许本机构授权人员访问本机构案件；若涉及跨机构、不同合同主体、学校/账户权属、未成年人监护证明或其他公司财务系统，应进入人工例外审查，不自动转移数据或资金。权威事实以签署的财务/CRM源及其可信版本为准，销售数据库不能为第三方源“代确认”。

## 3. 必须清查的历史与风险

| 对象 | 需保留及复核 | 原则 |
|---|---|---|
| 线索/学生关联/商机/报价 | 原来源、原学生、申请和批准链、商机来源、每版价格 | 以新纠错关联或解释性失效事件引用原版本，原记录不消失 |
| 销售订单/订单明细/合同 | 原订单号、学生、签约主体、价款/折扣、时间和版本 | 已发生对价/签约的不可直接改 student_id；新合同、取消或合同更正由正式政策决定 |
| 收款/收款分配/退款/拒付 | 外部权威交易号、版本、币种、实际金额、原分配、争议、到账/确认/记账时间 | 原收据不可伪造转账；资金补偿须明确经济事件、借贷/来源/去向与原记录引用 |
| SaleEvent/销售业绩/佣金 | 原成交唯一性、业务时点、人员和渠道快照、已发佣金 | 原首次成交记录不删除；按批准口径增加调整和版本，不重复计算 |
| 试听/排课/CRM课时权益 | 原 CRM 学号、课包、排课、实上和消课、剩余、退款影响 | 已上的课不能因改绑删除；未确认发课结果不得再次创建 |
| 审计与各方审批 | 申请、材料摘要/引用、批准及驳回、实际执行、异常和撤回 | 只追加；证据不可因审计页面渲染而泄漏真实敏感数据 |

**快照不是权威余额。** V3.2-22/23 保存的影响计数是创建/审查时点的数量；案件执行前后必须按版本重新读取权威收退款、订单状态、业绩和教务事件。晚到账、退款、拒付、教师消课、补开权益或外部回执迟到均需触发重新核对与暂停执行。

## 4. 状态机及职责签署

建议新增独立的“跨模块纠错方案/执行”模型，不复用或改写旧审批决定：
- case status 维持原 hold_active，直到满足全部释放门槛后，才可由未来单独权限函数改为 proposed resolved 终态；本期**不新增可释放函数**。
- plan status（建议）：draft → sales_approved → finance_approved → academic_approved → jointly_approved → executing → reconciliation_pending → accepted_closed。可在任何待执行阶段进入 rework_required / blocked / rejected / cancelled；这些状态不能在未记录历史的情况下倒退或覆盖。
- 每个部门审核必须是不可变的 approval_event，字段包含 case_id、plan_version、部门、签署人、角色所属组织、审核动作 approve/reject/return、独立意见、证据引用、权威源版本、签署时间、最小摘要、幂等键。
- 审核不是“谁先签就能执行”：同一 plan_version 下三方有效批准齐备，且原销售主管独立复核链完整、无权限撤销、无新权威影响变化，才允许生成 execution_authorization。方案任何金额、学生、订单、课程、补偿清单或依据变化都提升 plan_version，原批准仍保留但对新版本失效，三方必须重新签署。
- 三方中的任何一方可对自己负责的部分 **拒绝** 或 **要求补材料**；任何未解决的拒绝、未知结果、权限撤销、新证据或来源版本冲突都一票阻断执行与释放。
- 签署人的授权到执行前要再校验；本期还不存在真实财务和教务员工目录/审批权威，因此不得声称系统能真正验证财务/教务身份。

## 5. 补偿方案——**先审批、后执行、再核对**

每项 proposed_compensation 独立标记对象类型、原始记录 ID、目标学生与原学生独立核实引用、原因、权威系统、资金单位/币种、原/目标订单、预计金额或课时、执行负责人、预期副作用、审批版本、幂等业务键和结果核验要求。**不允许无来源地填入“更正后订单归属”来覆盖原订单。**

### 5.1 销售侧
- 原订单和其错误关联存续，并增加“争议中/历史错误需更正”的独立可查询注记；不得向常规员工直接暴露不必要的身份与资金明细。
- 根据实际合同条款和批准结果选择：保留旧订单并追加解释；依法/按合同取消旧订单再创建正确学生的**新订单**；或用经批准的独立合同更正文书处理。绝不能静默把旧订单改成新学生，且不能未经授权把合同签约主体替换。
- 原 sale_event、业绩归属和佣金历史保持；如需调整，产生独立调整记录并引用原事件。BP-05 尚未批准，不能自动扣回已发薪资或重复计入成交。

### 5.2 财务侧
- 财务首先识别是否是 **仅学生关联标注错误**、**合同/订单用途错误**、**真实付款用途错误**、**退款或拒付争议**，不能一律按“退款+重收”处理。
- 原付款事实仍以外部权威为准。可能的补偿是：分配冲正加新分配、受控退款/重收、待分配挂账、经批准的合同更正文书关联；具体方式必须由财务权威和合同责任人决定。
- 对每个资金事实重新证明：外部经济事件唯一，不重复退款/拒付冲减；累计有效分配不超过有效来源；每一笔补偿金额等额、有因有据，退款与新分配都不能凭销售口述创建“已到账”。
- 保留撤销前后的两个版本或只追加分录；数据库投影变更须由财务专用安全事务实施。**不得直接 UPDATE 原 payment_allocations、refund_allocations 或 payment_receipt_projections 伪装成纠错**。若当前系统旧状态机只能提供受限状态变动，则需先补建合格的补偿事务及不可变历史再授权。
- 涉及家长合并付款或多个孩子时，必须对所有受影响订单的资金总和一并重算，但权限范围不因此扩展到其他学生的非必要档案。

### 5.3 教务侧
- CRM 先核实权益是否已经创建、归属学生、课包、已上课程、剩余课时、已排课程；超时/500/没有回执 = unknown，不能当成“未开课”。
- 未履约权益可以根据 CRM 正式政策提出冻结、撤销后重建或迁移请求；**已上课/消课必须保留**，可能需要独立人工计费、课堂归属说明或补课与退费协调。
- 只有 CRM 提供领域级业务唯一键、权威结果查询与实际回执，才能在专用服务权限下执行；不得直接修改现有 CRM 表、删除消课流水或更换幂等键重新发放课时。
- 教务对课程已执行事实负责；资金如何结算由财务签署，合同主体/承诺由销售侧或合同权威共同核对。

## 6. 解除隔离的严格条件（全部为 AND）

**条件 R01 — 原案件**：确属此机构、此正式线索、此原关联学生的 active hold；原 V3.2-23 已 escalate_manual 或具有等效保留隔离的独立记录；此前双主管结论、历史和原案件完整。
**R02 — 身份与合同**：原错误已由销售独立核实，目标学生 ID、原/目标合同及双方权利义务已核准；无推断性家庭合并；跨组织或监护权问题得到专项批准。
**R03 — 三方同版签署**：三名不同自然人、各持有效销售/财务/教务权威，针对同一最新版方案签署通过；不存在驳回、未批准的变化或角色过期；原申请人不能审批自己方案。
**R04 — 原始事实完整**：订单、收付款、退款/拒付、成交、业绩、排课、课包、已消课和原审批均有不可变历史以及原记录引用；来源不可确认则阻断。
**R05 — 补偿执行完成**：每项必要补偿不仅批准，且由对应权威系统执行，收到可验证终局回执；未知/待处理/失败的补偿不得按成功计。
**R06 — 资金守恒与无争议**：原始与补偿收退款、分配、新订单和余额已按可信来源版本对账，未分配或争议款按批准的隔离/待处理政策明确归属，不作为正确学生已付款；无未处理资金差异或双重成交。
**R07 — 教务履约确认**：CRM 实际学号与课包、已消和剩余课时完成一致性对账；没有重复发课、无学生错误权益未处理、无结果未知请求。
**R08 — 销售一致性**：原错误关系不会被继续用来新建订单/成交；新正确关系及业务归因已受控完成，既有 SaleEvent 不重复，销售业绩调整已按批准口径处理。
**R09 — 并发与权限**：执行末次以数据库行锁/版本号与来源最终水位再次核对；没有迟到新事实、未结执行、权限变更或新争议；跨机构与越权严格拒绝。
**R10 — 独立终审**：三方分别签署执行后对账结果，独立、无利益冲突的授权终审者批准关闭，审计追加不可变 release_decision；释放只影响**指定原学生—线索关联的销售隔离**，绝不自动更改订单、资金或教务记录。

如果任何 R01—R10 不满足：维持 hold_active，显示“跨部门纠错未完成，继续隔离”；必要时继续允许经过认证的外部财务/教务事实进入，但必须重新对账。即使**三方批准**，缺执行回执也**不能释放**。

**迁移兼容要求：** 原 V3.2-23 的 release_verified 只面向关联实际上正确且零资金订单下游的误报，不能重新解释为 V3.2-24 的三方放行；未来新 release 专门命令和状态需重新定义，并不得削弱现有数据库守卫。

## 7. 并发、审计和运行设计约束

- 锁定当前案件与原线索/学生对，再核对涉及的订单及外部权威来源版本；多个订单排序获得锁。提出方案、追加审批、签署和执行意图各自有独立的幂等键；相同键同内容重放应返回同一记录，不同内容冲突拒绝。
- 对单数据库内部的状态和审计使用同一事务；跨财务/CRM 的执行采用 outbox + 幂等消费 + 权威结果查询 + 逐步核对，不把“发送成功”当“对方执行完成”，也不假设跨系统分布式原子事务。
- 事件/表按机构 RLS，员工只获得严格字段投影；销售看到订单和风险概况而不是外部银行凭据；财务仅看到必要学生订单映射；教务仅看到课程与课包关联；证据附件使用独立访问控制、保留策略与脱敏。
- 高风险函数不授予原 ms_scoped_lowrisk_writer、原销售经理或超级管理员财务/教务实写权。必须引入经过验证的独立财务/教务身份和显式执行授权。不存在此机制时维持禁用。
- 任一审批、计划、补偿或 release_decision 的正式历史拒绝 UPDATE/DELETE；法定更正要求以追加指向原记录的事件承载。保护数据库 owner/迁移权限、备份及审计导出另有基础设施验收门槛。
- 不把英文 JSON、数据库字段名、内部栈作为业务页面主文案；中文主状态区分“销售隔离”“三方审批中”“方案已批准尚未执行”“财务/教务执行结果未知”“三方对账完成待终审”“纠错结束并安全释放”。
