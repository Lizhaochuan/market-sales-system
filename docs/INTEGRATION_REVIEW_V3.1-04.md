## 一、本阶段解决什么

前三个 PR 分别从同一 main 版本出发，互相没有包含对方文件。因此它们是三个独立草稿，不是已经融合的可运行软件。

本整合分支把原有设计文件以原始 Git blob 复制到**新的独立候选分支**，同时增加资金约束迁移草案、隔离数据库测试脚本、机器可读合同的静态检查和 GitHub Actions 隔离测试工作流。

**整合不等于批准。** PR #1/#2/#3 保持开放草稿，不直接合并或改写；本阶段单独 PR 提交给负责人和工程人员评审。如果确认以整合 PR 作为新的技术基线，之后需决定如何关闭旧草稿，避免重复合并或反向覆盖文件。

## 三、八项设计缺口整改矩阵

| 缺口 | 实际问题 | 本轮处理 | 当前状态 |
|---|---|---|---|
| GAP-T01 | 付款分配可覆盖状态且缺少完整追加历史 | 增加 payment_allocation_history、状态转换限制、禁止 DELETE、收款/订单原子计数器 | **部分改进**；DB 角色及更正操作凭据未完成 |
| GAP-T02 | 同一退款与拒付可能被双重冲减 | 增加 finance_economic_events，按外部经济事件键唯一；退款按原付款及原学生订单校验 | **部分改进**；真实财务经济事件判别与撤销/拒付处理仍阻断 |
| GAP-T03 | 旧权威事件覆盖新状态 | 收款和退款新增 source_revision 与递增校验 | **部分改进**；需财务来源实际提供可靠可比较版本 |
| GAP-T04 | 一个成交可能有多个同时有效业绩分配版本 | 增加 sales_credit_versions 与“每笔成交最多一份已批准版本”条件唯一索引 | **部分改进**；同版本比例 100%/按分守恒仍须事务命令 |
| GAP-T05 | 退款与 CRM 权益冻结/调整缺乏正式接口 | 状态机和验收保留强制人工复核；未擅自新增 CRM 实现 | **阻断**，需 CRM/教学政策 |
| GAP-T06 | 学生、报价、商机、订单、组织一致性不够 | 增加订单/商机、报价/商机及学生与联系人/家庭组织校验触发器 | **部分改进**；全量多租户外键/权限隔离仍未实施 |
| GAP-T07 | 财务权威未指定，付款事实可信来源不明确 | 任何正式成交需经核实财务来源；不以销售截图作为依据 | **阻断**，需明确财务负责人和实际来源 |
| GAP-T08 | 实际到账、确认与入账的三个时间口径不明确 | 状态机保留原始发生/确认/系统写入时间和历史归因要求 | **阻断**，需机构批准业绩期间口径 |

**另外发现的关键限制：**
- 当前金额分配计数器保护的是“有效分配金额不超收到的金额”，**不是**资金最终合法性证明。真实付款来源被撤销、拒付，或退款与拒付代表同一经济事件时，仍需要外部权威对账及同一事务更正机制。
- 历史日志表即使有触发器，仍需严格限制数据库业务账户 UPDATE/DELETE，才能称为真正不可篡改的追加记录。
- 新建的 sales_credit_versions 只保证有效版本最多一个，尚不能单靠 SQL 保证该版本所有销售人员比例刚好 100%。
- 新增的已确认收款/退款计数器尚未设计真实历史数据回填与重算程序；对已有生产数据不允许直接运行此迁移。
- 所有新 API 目前仍是接口设计，并非 CRM 已有的可用生产端点。

## 四、真实交易的额外审查任务

### A. 防重复现金分配
- 两个销售/财务人员同时试图分配同一笔实收款，需要在服务端事务和数据库原子计数器两层检验守恒。
- 收款来源状态转 disputed 或 revoked 后，不能依靠旧计数器自动继续确认新的成交。
- 新项目只能存“经授权的财务事实投影”，不得自行发明实际到账。

### B. 学生及家庭隔离
- 一人一学生订单、一个商机对应具体学生；同一联系人可与多个学生关联，但不会自动创建家庭或互相授予数据读取权限。
- 引用 CRM 学员、课程和权益都需核实真实身份与业务来源，不能因为共享电话就开错学生的课时。
- 真实多校区/多机构启用前还需对全部关系表执行租户一致性和 API 权限评审。

### C. 退款与课时权益
- 原 SaleEvent 不删除；追加核实的退款、收入/业绩调整。
- CRM 课时包一旦实际创建，网络断线不得第二次创建；退费若涉及已消课，应走 CRM 专用受控调整流程。
- BP-01 尚未审批前，未全额付款不提前自动发课。

## 五、验收与证据边界

| 验证层次 | 可证明的范围 | 不能证明的范围 |
|---|---|---|
| Node 合同静态检查 | JSON 可解析、内部引用存在、路径参数、状态机及表名一致 | API 已开发/安全、财务正确 |
| PostgreSQL 隔离冒烟 SQL | 表能创建、部分约束/触发器能在模拟数据下执行 | 真实付款核验、完整并发、安全合规 |
| PostgreSQL 多会话并发测试 | 对同时分配、重复成交和撤销的实际竞态 | 真实 CRM 发课/银行验证 |
| CRM stub 合同测试 | 接口语义、超时与幂等恢复的客户端行为 | CRM 实际代码已具备该能力 |
| 双系统 E2E 与实际 GUI | 完整业务过程、设备可操作性、字段可读性 | 没有部署/真机证据时不得标 PASS |

**此文件不是实施完成报告。** 只有实际测试输出、运行环境、Git SHA、脱敏日志和明确用例结果齐备时，才能给对应测试标 PASS。

## 七、下一阶段建议：开始低风险可运行代码

在完成整合 PR 的静态/隔离验证和审核后，优先建立**市场销售服务端工程骨架、用户权限、学生/联系人及线索模块**。这部分不依赖真实收款或 CRM 新增接口。

金融交易和 CRM 课程权益必须等真实来源、金额守恒、服务端幂等及双系统验收齐备后才开放。代码仍位于市场销售独立仓库；现有教培 CRM 文档保持独立，最终集成并通过联合验收后再融合。
