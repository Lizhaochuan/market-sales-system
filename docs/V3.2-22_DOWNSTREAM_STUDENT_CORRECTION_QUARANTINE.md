# V3.2-22｜已产生商机的错误学生关联：下游影响清查与纠错隔离

**市场销售独立技术文档。** 基线为未合并的 Draft PR #25；只用于虚构的 PostgreSQL 16 + 真实受限员工数据库账号测试。**不合并、不部署、不接真实学生、合同、教务、收款或旧 CRM。**

## 一、发现的客观数据关系

V3.2-21 已允许独立主管撤回错误学生与正式销售线索的关联，但若同一 `lead_id + student_id` 存在 `ms.opportunities`，现有函数会拒绝直接撤回。这不是权限错误，而是重要的一致性保护：

- 商机 `ms.opportunities` 保留 `originating_lead_id` 和 `student_id`。
- 报价 `ms.quotes`、订单 `ms.sales_orders`、试课 `ms.trial_bookings` 可能引用该商机；订单后续还会关联收款分配、退款分配、销售认定、业绩和权益履约。
- 仅撤掉线索—学生关系而保留原商机会造成业务认定矛盾；直接更新 `opportunities.student_id` 又可能把历史订单或资金错算给另一名学生。
- 因此**本期不宣称已完成下游纠错**，而是将受影响的**指定一名学生**进入跨模块保护队列，阻止进一步的销售推进，待下一阶段完成独立归因、订单和资金审核后才能处理。

## 二、处理流程

1. 原申请人必须仍然是这条 V3.2-19 独立创建的正式线索负责人，该学生已在 V3.2-20 经主管批准为 `pending_review`，或在 V3.2-21 进一步人工核实为 `verified`；并且数据库中确实存在**同一线索、同一学生**的下游商机。其他员工、其他机构、尚未关联的孩子不得报送。
2. 申请人提交纠错证据引用、原因和幂等编号。数据库锁定原线索，重新统计下游影响，建立**唯一有效案件**（`pending`），立刻对相关销售推进生效保护，**不等待主管审批才开始保护**。
3. 只提供影响数量而不展示资金明细或孩子敏感字段：商机、报价、订单、收款分配、退款分配、试课、销售认定、权益链接。快照在创建案件时留存；案件期间合法的财务外部事实可能继续增加，因此快照**不能当实时财务余额**。
4. 与原申请人不同的本机构有效主管独立复核，选择：
   - **确认维持隔离**（`hold_active`）：保持销售推进保护，留在跨部门待纠错状态。**原线索、原学生关联和下游商机尚未改动。**
   - **驳回隔离**（`rejected`）：撤销这次保护，保留不可改写裁决及原业务关系。是否原关联有错仍需业务判断，不是自动更正。
5. 下一阶段才能设计独立的“核实正确学生、商机历史处理、订单与财务权威系统复核、最终释放隔离”闭环。V3.2-22 **不存在任何自动解除已确认隔离、变更商机学生、删除订单或资金的函数**。

## 三、数据库保护覆盖与未覆盖范围

`db/migrations/026_downstream_student_correction_holds.sql`：

- 建立 `ms.lead_student_downstream_correction_cases` 及不可改写的 `ms.lead_student_downstream_correction_decisions`；提交、主管裁决和审计属于同一 PostgreSQL 事务。唯一索引禁止同一关联存在两条待处理/已确认保护。
- 数据库触发器对**精确的原线索—学生商机组合**执行检查，而非按联系人、姓氏或家庭扩大范围。直接锁定原线索进行并发协调。
- 对受影响商机的 INSERT/UPDATE/DELETE、报价及报价项目、折扣审核、订单项目、试课预约及销售任务的相关销售变更实施拒绝；订单的创建、删除或销售业务字段变更也被拒绝。已经存在的订单及其学生、商机引用**不能借此直接改绑**。
- **金融权威事实不静默丢弃**：支付收据投影、收款分配、退款分配、业绩事件等没有被当作“纠错回滚”自动删除；订单的 `payment_state`、试课的 `attendance_state` 仅改变这些权威/事实字段时没有被本期销售推进触发器阻止。必须在未来跨模块复核中重新核对期间新增的事实。因此本期属于“销售推进隔离”，**不是全系统支付/教务冻结**。
- 每个员工真实执行身份继续由受保护 `SESSION_USER` 映射。不给员工新表 SELECT 或 UPDATE 权限；只授予两个 `SECURITY DEFINER` 函数 EXECUTE，所有审查数据通过最小投影。
- 触发器保护应用在数据库层，不能通过旧业务 UI 中调用广域 SQL 或修改输入的员工编号进行绕过。未受影响的另一名学生/商机不应被误阻断。

### 阶段边界

此版本尚未提供正式学生身份重新核实、商机改正、业绩重新归因、合同作废/转移、财务退款、跨机构商机纠正或隔离解除。**禁止把“主管同意隔离”显示成“纠错完成”。** 任何真实世界的法律/财务义务继续由原权威系统负责。

## 四、严格员工接口及中文页面

| 接口 | 作用 |
|---|---|
| `GET /api/v1/downstream-student-corrections/eligible` | 本人已获准关联且存在下游商机的指定学生最小列表 |
| `GET /api/v1/downstream-student-corrections` | 本人案件、自己审核过的案件或主管待审案件与影响数量 |
| `POST /api/v1/downstream-student-corrections` | 提交单名学生的下游影响纠错案件；立即触发销售隔离 |
| `POST /api/v1/downstream-student-corrections/:id/decision` | 本机构独立主管确认维持隔离或驳回 |

中文页面显示“待主管核查（销售推进已阻止）”“已批准隔离（纠错尚未完成）”“驳回隔离”，以及报价、订单等关联数量，不显示原始数据库代码或财务金额。

## 五、验收

最新 HEAD GitHub Actions 必须全绿，含 PostgreSQL **001—026**、真实员工 LOGIN/双机构隔离、Node 全量安全和业务测试、Chromium 中文实际操作、V3.1 合同回归。

新增验证必须包括：指定学生关联及存在商机才能报告、A/B 员工和机构隔离、相同幂等键重放、并发只能一条有效案件、启动保护在主管审批之前生效、独立主管不能自批、商机/报价/订单/试课新销售推进被拒绝、现有订单及资金记录不被删除或改写、另一名学生的业务不受误伤、主管驳回后保护解除、通过的主管决定不可篡改、V3.2-21 的原错误关联撤回仍不能绕过已有商机保护。

## 六、建议 V3.2-23

建立**跨模块纠错处置的实际闭环**：核实正确学生和原始线索归因、商机/订单及业绩权威方双人审批、真实收付款影响清算、必要的历史失效和重建/更正审计、明确释放销售隔离的安全前提。必须额外增加跨模块负责人、不可变状态快照及高风险审批测试，才能允许对已有商机的学生关系做实际更改。
