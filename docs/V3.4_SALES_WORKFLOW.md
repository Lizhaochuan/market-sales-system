## 用户操作

日常从“销售 Leads”或“市场 Leads”进入，同一客户内使用四个入口：**记跟进、约面谈/试听、课程方案、办理报名**。

1. 接单时选择已有学生，或先只填联系人，随后补一次学生姓名；来源是获客来源。指定首次事项、方式和明确时间，负责人自动继承。
2. 记跟进时选择线上/线下、具体方式、本次结果。未接通只展示相应原因和下一步；微信待回复必须设置检查回复的日期和时间。失败不会推进销售阶段。
3. 已完成沟通时才填写沟通目的/销售进展；实际发出但尚未回复的微信邀请也可记“已发邀请，待回复”，不能选家长已同意。
4. 确认到校时间时直接保存面谈预约，作为下一步，不再重复建普通任务。时间未定、不方便或拒绝本次邀约，仍须安排后续动作，不自动流失。
5. 面谈与试听分别管理。实际完成、未到场或取消都要关联已有后续活动或安排新的活动。改期保存原时间、原因、操作人及历史，不计作完成一次跟进。
6. 试听可在本系统录入课程、地点、日期时间，可独立改期和确认实际完成。不会因日期过去自动完成；不依赖 CRM。
7. 课程方案可包含多门课程，课时数乘每课时价格自动计价。标准价来自主管维护的本地价目；销售不能伪造标准价。优惠或未列价课程需另一位主管批准当前版本。
8. 办理报名从有效方案生成订单，关联已签资料。协议要由独立主管核实；收款登记由销售提交，到账只由独立核款员确认。
9. 有效协议＋首笔正额有效到账即报名成功；有余额时仍保留下一步。全额有效净收款、全部有效订单及异常检查通过后，才能确认 Closed Won。
10. 明确拒绝才按允许原因、客户反馈和依据办理 Closed Lost。无回应/信息无效等特殊原因需主管核实。客户要求不再联系时，停止常规待办。
11. 负责人转交先由主管申请、另一主管复核，再由接收人确认。接手前原负责人和任务保留；接手后活动原子继承，学生独立身份和原作者不改写。
12. 现场未完成的信息可“先保存草稿”；草稿仅该员工可见，可恢复，但不产生已完成跟进。登录到期时另有同员工同模式的 JS 内存恢复；不写 localStorage/sessionStorage。附件须重新选择。

## 跟进链条与存储

复用 `ms.leads`、`ms.students`、`ms.opportunities`、`ms_workspace.records/history`、`ms.audit_events`，不新建第二套 Lead/学生/待办系统。

新增 `ms_workspace.lead_workflow` 是以原 Lead ID 为主键的一对一流程扩展，保存版本、当前进展、终态和主要下一步活动。待办仍是既有 `records.kind=tasks`；面谈/试听是 `appointments`，通过同一活动读取和历史能力管理。

新增迁移：[039_v34_sales_loop.sql](../db/workspace-migrations/039_v34_sales_loop.sql)。它只用于显式 opt-in 的隔离 workspace，执行在已有 fixture 之后；不改写 001—038，不向现有严格员工 LOGIN 授予权限。

数据库提交时执行延迟约束：每条受管理的 Open Lead 必须指向一条同机构、同 Lead、同负责人、有事项、方式和时间的有效任务或预约。记录完成/删除也触发反查，不能先关闭最后一条活动再提交空链。

HTTP 写请求沿用既有事务及 Idempotency-Key 回执。每次业务转换先锁 Lead，再核对 workflow 版本；并发完成只成功一次。创建后续失败时整个事务回滚，旧有效任务保持。已有有效预约可以被引用；同一客户同一类型、时间、地点、课程的有效预约不重复创建。

旧数据不自动生成活动，不把历史“准备报名”猜为意向或成功。没有流程扩展的旧活跃 Lead 显示“待补安排”；旧明确关闭/无效状态保留为待人工核实的旧终态，不静默重开。旧数据中无负责人或负责人已失效的客户进入主管处理范围；补全时明确指定人员和时间。

## 独立财务与报名标准 B

复用原 `sales_orders`、`payment_receipt_projections/payment_allocations`、`refund_projections/refund_allocations`、`finance_economic_events` 和 `sale_events`；原全额净付款成交数据库触发器不放宽。

本地方案、报名协议和业务明细保存在有版本的 workspace 记录，订单金额落在原订单表；不伪造 CRM 课程编号或教学权益。

- **协议有效**：独立主管核实签署资料，不能核实自己提交的协议。
- **到账有效**：`finance_verifier` 角色核实实际到账，不能自核自己提交的款项；销售或普通主管不能通过页面/API自行确认。
- **资料上传**：支持 PNG/JPEG/PDF，单文件不超过 1 MiB；检查内容头、类型及大小。资料与独立查验依据分别保留。上传图片不是到账。
- **先到账后协议**：到账事实可先核实，记为待协议确认挂账；不认定报名成功，不绕过原订单资金约束。协议核实后才进行相应挂账。
- **报名成功**：有效协议且有效净收款大于零；首次成功事件只生成一次。
- **缴费进度**：应付、已核实净收、未结清分别显示；部分首款不算结清。
- **Closed Won**：所有有效报名订单有效且净款全额，没有未决款项/纠正，再按原强约束写唯一 SaleEvent。原成交负责人快照保留。
- **退款/取消**：先申请，独立主管核实，实际退款再由核款员确认。结案后的纠正必须有审计并重开有明确下一步的处理链。原成功/成交事件不删除；退款与净额调整追加记录。
- **待核实资料**：核款员可明确退回，不将未核实款计入收款。存在未决财务事项时不允许用流失结案把问题隐藏。

这些是本系统的授权人员查验流程，不是自动银行验证，不宣称任何真实演示款已到账。

## 权限与界面边界

销售只能操作本人 Lead；主管沿用本机构管理范围。收款核实员只增加本机构财务队列及相应核实动作，不获得查看所有客户详情、改销售进展或自行创建销售客户的能力。

新演示账号使用独立保留命名空间；不会给原销售或主管增授核款角色。角色撤销、账号停用仍按每次请求重新检查。角色可以组合，但自审/自核仍拒绝。

跨负责人转交不自动移交学生全局所有权、家庭关系或其他 Lead，只转交已批准 Lead 业务及其活动；原学生审批和其他记录权限保持。待接手队列只披露已批准请求的必要信息，接受前不能读取原负责人的客户详情。

所有新界面业务文字通过 textContent 构造。凭证只能下载，不以内嵌 HTML 执行。敏感联系方式仅在已授权客户详情展示，不进入普通队列/报表。

## 统计口径与提醒

- 所有报表先按本机构和当前数据范围裁剪；不把家庭人数当客户数。
- 沟通事件保留本次实际学生主体快照；多学生须明确选择，未知学生的 Lead 单列，不能凭后续关联倒推以前讨论了谁。
- 活动次数与去重学生人数分开。待回复表示当前仍 Open 且最近一次结果待回复。
- 面谈到访/完成、实际试听只依据对应事实记录。取消/待确认试听不充作有效试听预约。
- 面谈/试听后报名转化要求实际完成时间不晚于首次报名成功时间；不把先报名后试听算作试听促成报名。
- 净收款、余额从已核实资金及退款衍生；登记待核实资料不计入收入。
- 当前有效报名订单与唯一历史成功事件分开；取消或异常不抹除原成功历史。
- 今日任务按 `Asia/Shanghai` 自然日计算；逾期为时间标识，不覆盖实际活动状态。
- 责任人报表用于当前可见客户的业务过程：Open/Won/Lost、有效报名订单、已核实净收、本人沟通次数、逾期及缺安排。不是多人业绩比例或佣金结算表。
- 页面在线时每分钟刷新待办与提醒；任务时间与状态持久保存，关闭网页不删除活动。只产生本系统内部提醒，不自动发送微信/电话、认定到访/试听、核实资金或自动结案。

## 接口与开启方式

统一入口：`/api/v1/isolated-workspace/workflow`。

- GET 根：当前权限内客户、下一步、异常、待接手队列；POST 根：接单＋首次活动。
- GET `options/metrics/finance`：选项、本地标准价、经营数据、财务核实队列。
- POST `catalog`：主管维护本地标准价。
- GET `{leadId}`、`{leadId}/history`：授权详情与版本历史。
- POST `{leadId}/followup|draft|arrange|appointment|activity|quote|enroll`：日常业务。
- POST `approve-discount|confirm-agreement|submit-payment|verify-payment|reject-payment`：独立审批及款项核实。
- POST `close-won|close-lost|reopen|request-transfer|approve-transfer|accept-transfer`：结案及接手。
- POST `request-correction|approve-correction|submit-refund|verify-refund`：异常、取消与退款。

上述 POST 除首次创建/旧缺口补全外均携带 `expected_version`，并沿用 Idempotency-Key。新记录不能从旧的通用 workspace 编辑入口绕过链条；旧资料仍可从“历史与管理”查看。

在已有**本机隔离数据库**上：

```sh
MS_STAGE=isolated-test DATABASE_URL='本机隔离数据库URL' node scripts/upgrade-v34-workspace.mjs
# 仅虚构演示时可另设 MS_V34_DEMO_SEED=1，创建独立核款演示账号及示例价目。
MS_STAGE=isolated-test MS_ENABLE_ISOLATED_WORKSPACE=1 MS_ENABLE_V34_WORKFLOW=1 node src/server.mjs
```

启动仍需原有数据库及签名/演示口令配置。严格员工模式与此演示工作台不能同时开启。默认未开启 V3.4 的旧服务行为保留，用于兼容回归；原 CRM 仓库不在本轮修改范围。

## 人工依赖及本轮不实施项

1. 生产 IAM/KMS/HSM、WORM、EXT-001 真实外部证据、生产 UAT 与运行授权仍未验收；`EXT-001=UNVERIFIED`、`HOLD=true`、`release_eligible=false` 不变。
2. 真实签署有效性、到账与退款证据需要授权人员实质核实，不能由测试截图或虚构测试材料代替。
3. 原有多人业绩分配/退款佣金政策未另行批准，本轮不私定佣金冲回比例；保留唯一成交与退款净额及追加调整审计，不伪称佣金结算完成。
4. 跨学生共付款自动分配、零价报名、半课时计费、收款撤销/拒付与退款重叠政策仍需明确；继续不自动分配、不自动冲正未知经济事件。普通单学生多订单与已核实退款可独立运行。
5. 不开发 CRM 接口、跨系统同步、教学排课资源占用或课时权益。销售的预约及实际完成记录已能独立使用。
6. 不实施生产部署或后台外部消息发送。当前提醒是持久待办＋登录期间内部刷新，网页关闭时不会发微信/短信或给家长打电话。
